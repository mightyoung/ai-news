## A. OpenAI：Pando，给 monorepo 用的新 Git 后端

**一句话结论**：OpenAI 用 Rust 重写了 monorepo 的 Git 服务端（Pando）。它放弃「全仓库同一时刻快照」，改成每个分支各自按顺序更新；拉取时直接发预先存好、可复用的 packfile 链接，像 CDN 一样分发。客户端仍是标准 Git，只是装了 OpenAI 自己加过补丁的 Git 版本。数字全是 OpenAI 自报，Pando 本身没开源。

### 机制拆解（白话）
1. **Git 服务端原来卡在哪**【自报】：monorepo 有上百万个分支，光「告诉客户端有哪些分支」（ref advertisement）就能超过 100 MiB。几千个客户端同时推送，旧系统要给全仓库排队，可靠性有时掉到 90% 以下。
2. **不保证全局快照，只保证每个分支有序**：可以想成银行每个账户各自记账，不用整个银行一起结账。推不同分支互不阻塞；推同一分支照样排队。代价是 fetch 时 A 分支和 B 分支的「时间点」可能不一样。原文叫它 causal consistency（因果一致）。
3. **packfile 当作不可变文件存**：Git 传输的单位是 packfile（打包压缩的一堆对象）。Pando 把推上来的 pack 原样存成 blob，不再为每个客户端现算一个包。拉取时返回「下载这几个 pack 的链接」（Git 已有的 `packfile-uri` 协议），客户端直接从缓存下载。每个客户端可能多下一点它已经有的对象，换来缓存命中率 >99%【自报】。
4. **元数据像 LSM 树一样分层合并**：许多小 pack 会定期在后台合并成大 pack（文中说 L0–L4 分层，上层覆盖下层，起「跳表」作用），客户端不用下载成千上万个小文件。
5. **推送只广播主干**：推送时服务端只告诉客户端主干（trunk），不列出全部百万分支。OpenAI 给 Git 加了「explicit haves」，让 `--force-with-lease` 这类推送也能以主干为基准构造 pack。目前只在 OpenAI 自己的 Git 版本里有。
6. **怎么让这套东西靠得住**【自报】：一套兼容性测试；确定性仿真测试（把并发和故障变成可重放的实验）；agent 用 Lean 和 TLA+ 写形式化模型，持续跑了数百小时。迁移时 Pando 先做旧系统前面的读写代理，再逐步切流。防御侧还提到：用「Daybreak-capable models」的 agent 全天候对 Git 和 Pando 做红队测试。

### 风险与存疑
- 所有性能数字都是 OpenAI 自报，没有外部基准，也没公开测量方法（例如中位数在什么时间窗口、和旧系统哪一版比）。
- 「agent 写的」「10 周」这类叙事和 Codex 的宣传强相关【推断】。原文没给人工审查量、代码规模或缺陷数据。
- 每个分支各自一致，代价是跨分支看到的状态可能不同步。依赖「同一时刻多分支状态一致」的 CI 或工具要自己处理【推断】。
- 客户端要装 OpenAI 自己的 Git 版本才能用到全部收益（并行索引、explicit-haves）。用标准 Git 只能兼容，不一定达到同样性能【推断】。
- 追踪页是 OpenAI 自己做的，「已进上游」的状态我没能用上游来源独立核对。

### 机制拆解（白话）
1. **权重是什么**：神经网络就是一大堆数字。平时改模型靠训练：喂数据、算梯度、一点点调。这次不训练，让 Astra 当「读汇编、打二进制补丁的人」，直接看数字、改数字。
2. **小网络实验（实验 1–6）**【自报】：
   - 4 个玩不同小游戏的 PPO 策略网络（每个约 1.7 万个权重），Astra 看权重说出各自是哪个游戏；
   - 从扩散模型的权重画出形状轮廓（只画出了外框，没画对实心）；
   - 3 个字符级语言模型（716 万参数，只给中间层），两轮都 3/3 认对语言，置信度 0.48–0.62；
   - Kinetix 小车策略改 3.5% 的权重，1,024/1,024 次成功；
   - MinAtar 游戏直接一次性写出权重，Breakout 得 517.4（PPO 训 1 亿步 15.8，5 亿步 25.3）；Seaquest 53.1（PPO 5.6 / 88.9），Asterix 53.2（25.8 / 55.2）；
   - 9×9 围棋网络（148 万权重），50 次前向预算内超过同规模 PPO。
3. **失败案例（实验 7）**【自报】：想去掉 Gemma 3 270M 的谄媚倾向，只看权重 0/4 失败，允许看注意力模式后才成功。
4. **Qwen 这一项（实验 8）具体做了什么**【自报】：
   - 问题：Qwen3.5-0.8B 开思考模式后，基线 93% 的回答写满 32,768 token 也停不下来，答案根本没输出；
   - Astra 只能用 10/25/50 次前向调用（不能用 GPU 训练、不能算梯度），练习题来自 GSM8K/MATH 训练集（前 96 道练习里 85 道撞上限）；
   - 它找到第 15、19 层 MLP 往残差流里写的一个方向，在各 64 个输出列里把这个方向减掉。可以理解成拔掉「一直想下去」的油门。这在可解释性里叫方向消融（directional ablation）【推断：术语对应】。
5. **为什么分数会暴涨**【推断】：原来大多数题是「没写完就被截断」，不是「写完写错」。只要能停下来交答案，分数就会大幅上升。所以 7.9 → 48.1 主要衡量的是「能不能结束」，不是「会不会做数学」。作者用 Gemma 3 270M 做了侧面印证：它本来很少死循环（8.5%），同样流程改完几乎没提升（6.8 → 7.0/7.6/7.7/7.0）。

### 风险与存疑
- **缺对照**【推断】：没报告这些对照：
  1. 同样大小的随机方向删除；
  2. 只改解码就能做到的事：调高 presence penalty、加重复惩罚、检测到循环就截断重来、关掉思考模式、用官方推荐的 temperature 1.0；
  3. 标准做法（差均值方向消融）作为基线。
  没有这些，就分不清「Astra 找到了巧妙的修改」和「任何能止住循环的改动都有这个效果」。
- **曲线不单调**：10 → 25 次前向时 IFEval 从 49.0 掉到 39.9，GSM8K 也略降；IFEval 在 10 次时就翻倍，但撞上限比例几乎没变（93 → 87%）。可能是噪声，也可能是改法不同，原文没给方差【推断】。
- **基准选择**：思考模式 + 32k 上限正好最容易暴露死循环；非思考模式（官方默认）不会。拿最差设置当基线，「6 倍」会显得很大【推断】。
- **「LLM 能原生读写权重」说法偏大**：失败案例（Gemma 谄媚 0/4）和 Neel Nanda 的评论都说明，这更像是 LLM 熟练使用已知可解释性技巧；在大模型上能走多远还不知道。
- **复现状态**：只有 akhaliq 用作者协议对改后权重复跑。「Astra 能否再次找到这个改法」没人复现过。打分代码不完全可运行。
- **安全（防御侧）**：能直接改权重，意味着开源模型的权重补丁需要像软件补丁一样做回归测试和来源校验（用 sha256 比对张量）。

### 应用清单
**今天就能试**
1. 用 Qwen3.5-0.8B 跑几道 MATH 题，分别开和关思考模式，看撞上限的比例。本地 CPU 也能跑少量题。
2. 不改权重，先只改解码：调 presence_penalty（0–2）、设较小的 max_tokens 加流式循环检测，记下准确率。这是最该补的对照，成本最低。
3. 读 Qwen 官方卡关于 thinking loops 的提醒，再读 Neel Nanda 的评论，练习「先找失败模式，再看提升从哪来」。

**要有数据或机器再试**
4. 下载作者的改后权重，用 vLLM 在 MATH-500 上同时跑原版和改后版（各 4 次采样），看能否复现 7.9 / 48.1 和撞上限比例。需要一张 GPU。
5. 自己做一个随机方向、同样大小的删除作为对照；再用差均值方法找「循环方向」比一比。
6. 改完一定做回归测试：MMLU-Pro、IFEval、安全拒答等，看有没有别的能力被弄坏。

**暂时别碰**
7. 别把改后权重直接放进产品，没有回归测试、许可和来源核对就上线风险很大。
8. 别把「LLM 能改权重让模型变聪明」写进汇报或项目规划。目前只证明了「能在小模型上去掉一个明确的故障」。
