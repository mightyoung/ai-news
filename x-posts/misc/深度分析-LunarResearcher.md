## 机制拆解（5 点）

**1）契约先行：把模糊意图变成可验收的任务**
文章给的契约是 5 问：要什么结果、范围内是什么、什么不能动、什么证据证明完成、哪些动作要人批。示例是一段 yaml（objective / scope / constraints / acceptance / approval_required）。
- 价值：把"agent 说完成"换成"验收项全过"，这是后面第 7、13 节的前提。
- 局限：契约本身谁来写、写错了怎么办，文章没讲。验收项如果写得弱，整套证据链就是空转。【推断】

**2）上下文做"地图 + 按需展开"**
文章的主张是先给小地图（项目地图 → 子系统 → 具体文件 → 局部指令），不要把整个仓库灌进去，目标是"每个 token 的信号最大"。
- **与原文对照**：这就是 OpenAI 2026-02-11 那篇的原话思路——AGENTS.md 只当目录（约 100 行），指向结构化 docs/ 目录，OpenAI 还试过"一个大 AGENTS.md"并说明为什么会失败（挤占上下文、变成非指导、腐烂、难以机械校验）。Lunar 的文章没有引用它，也没有给出这些失败原因。

**3）脑 / 手 / 历史 三分**
Brain 负责计划，Hands 在受控环境执行工具，History 存持久事实、决策和运行状态。
- **与原文对照**：这和 Anthropic 2026-04-08《Scaling Managed Agents: Decoupling the brain from the hands》的 session（追加式日志）/ harness / sandbox 三分基本同构，连"brain、hands"这两个词都一样。Anthropic 的原文多了三件**可落地的硬东西**：①harness 无状态，崩溃后用 `wake(sessionId)` + 读事件日志从最后一条事件恢复；②沙箱当"牲口"不当"宠物"，坏了就重建，失败当成工具调用错误返回给模型；③**凭证放在沙箱够不着的地方**（vault + 代理，harness 也不接触凭证；Git 用仓库令牌在初始化时配好 remote，agent 不碰令牌）。Anthropic 自报效果：按需创建沙箱后首 token 延迟 p50 降约 60%、p95 降 90% 以上【自报】。Lunar 的文章只讲了"分开更好修复"，**没有讲凭证隔离，也没有给任何延迟/可靠性数字**。

**4）完成靠证据，验证靠"攻击"，策略放在推理环路之外**
- 第 7 节：声明→证据对照（"bug 修了"→原失败测试现在通过；"迁移安全"→dry run 和回滚都通过），并给出"最便宜的确定性检查先跑"的阶梯：语法→类型→聚焦测试→集成测试→人工审阅。"能用编译器/schema/测试回答的，不要再用模型。"
- 第 8 节：worker 和 verifier 目标不同，verifier 有明确的拒绝标准、可以只拒绝不修复，最好用新上下文。Anthropic 的 cwc-long-running-agents 仓库自述也用只读、没有写权限、看不到构建上下文的 evaluator 子 agent 做同一件事（只读了仓库 README 摘要，没有逐文件核）。
- 第 9 节：风险四档（低风险自动 / 可逆改动自动加 trace / 外部影响要明确批准 / 不可逆或敏感要硬闸或禁止）。"模型提议、策略授权"。与我们此前的稿子（10/11 §A，Nadella 的"控制放在模型之外"）是同一思路，见下面"旧稿指针"。

**5）恢复、观测、回执、衰减：把失败变成基础设施**
- 恢复：按失败类别选动作（超时→退避重试；参数错→修复调用；缺上下文→定向检索；权限拒绝→申请批准或走安全路径；需求矛盾→升级给人；**同样的失败重复→停止循环**），每个循环有预算（次数、时间、花费、破坏范围、升级条件）。
- 观测：trace 记录状态迁移、上下文来源、工具输入输出、环境变化、验证结果、重试原因、审批决定、成本延迟，目的是从第 18 步的检查点重启而不是重放全程。
- 回执：运行结束出一份"系统能证明什么"的摘要（改了什么 / 验证了什么 / **没验证什么** / 决策 / 风险 / 待批准）。"没验证什么"这一栏是整篇里最实用的小设计。
- 衰减：旧模型的补丁会拖累新模型，每个组件都要问"还挡得住什么失败、现在还多久发生一次、删掉会怎样"，"为删除而建"。**与原文对照**：Anthropic 那篇开头就举了同一个例子（Sonnet 4.5 的"上下文焦虑"靠上下文重置解决，换到 Opus 4.5 后这个行为消失，重置成了累赘）。

## 工程落地（8 条）

1. **先写任务契约再放权。** 每个自动任务强制 5 个字段（outcome / scope / constraints / acceptance / approval_required），缺哪个就不给 agent 自主权。契约放仓库里，随任务一起版本化。
2. **入口只放地图。** 一个约 100 行的入口文件，指向 docs/ 里的架构、命令、发布规则；用 CI 校验链接和新鲜度，再加一个定期"文档园丁"任务找过期内容（这是 OpenAI 的做法，文章没提）。
3. **工具网关带前置条件、证据和风险等级。** 每个工具声明：输入、前置条件、成功证据、失败行为（不允许半截覆盖）、风险类别。模型只能提议，网关校验后才执行。
4. **会话日志追加式、放在 harness 和沙箱之外。** 崩溃后可以从最后一个事件恢复；原始记录留着审计，执行用的是编译好的 facts / decisions / progress / lessons。
5. **凭证永远不进沙箱**（补文章的缺口）。用代理/金库在调用时注入；Git 用初始化时配置好的 remote。这条比任何 prompt 规则都重要。
6. **完成 = 验收项全过。** 把"最便宜的确定性检查先跑"做成流水线；另配一个只读 verifier（独立上下文、有拒绝标准、不能顺手修）。回执里必须有"未验证"一栏。
7. **失败分类 + 预算 + 熔断。** 实现那张"失败→动作"表；对"同一失败连续出现且条件没变"强制停止；每个循环设最大次数、时间、花费、破坏范围。
8. **每季度清点 harness。** 每个路由、评估器、记忆层、重试规则都记录"防哪种失败、现在还发生多少次"，换新模型时先做删除实验。度量用"被接受的工作 / 人工审阅时间"，成本换算系数自己定。

中小团队的起步顺序：文章第 16 节的 6 级里，**先做 1（有边界的任务）、3（受控动作）、5（证据）**，这三级对应的失败最常见、成本最低；多 agent 编排放最后，"复杂度要用观察到的失败来换"。

## 风险与局限

- **没有证据。** 没有基准、没有对照实验、没有哪怕一个真实团队的数据；"harness 改变每一次尝试"是论述。别把它当作"已被验证的最佳实践"转述，只能说"与大厂公开做法一致的清单"。
- **来源不署名。** 与 OpenAI/Anthropic 文章的重合没有引用。想深入应直接读原文（链接见核实清单），它们有具体做法和（自报的）数字。
- **安全面不完整。** 缺凭证隔离、提示注入、沙箱出网控制；把"策略放在推理环路外"写成了原则，但没有写怎么实现。
- **适用范围没界定。** 第 19 节说了"简单任务不需要重 harness"，但整篇的闸门建议没有区分吞吐和风险等级；与 OpenAI"少阻塞合并"的取舍相反，团队要按自己的情况选。
- **营销成分。** 文首文末两处引流 Substack，标题是"Complete Guide"，但内容是概述级；"书签 1,759"反映的是收藏习惯，不是质量背书。
- **评论区噪音与诈骗特征（防御面）。** 11 条回复里：2 条是 9/23 的陌生账号声称"替你发了 PUMP 代币，交易费全进你的 GitHub 账号，可以直接领取"（@AllexonD、@DraculeArc，各带一条链接），另 1 条只贴了一串类似 Solana 合约地址的字符（@checksol777）。这是典型的"币圈引诱"套路；**不要点链接、不要连钱包、不要授权**，作者本人没有回应。其余是 threadreaderapp 展开请求、Grok Bot 被呼叫（10/11、10/15）、一条 10/16 的使用感想（自己拿 AI 搭 harness，Claude 加了文件/图片支持后更好用，未给出可核对的细节）。
