### 机制拆解

1. **加在采样上，不改文本表面。** 每一步把模型的下一 token 分布拆成几组调整过的分布，由密钥和上下文窗口选一组再随机采样；按 key 平均后等于原分布（无偏）。所以文本里没有任何可见或隐藏的「标记物」，信号只是统计上的偏向。报告专门解释了为什么不用 Gumbel-max：那种做法在同一 key 和同一上下文下总选同一个 token，同一 prompt 会反复生成一模一样的回答，伤 best-of-n 和多样性。textGrain 用熵损失预算在「可检测性」和「多样性」之间连续调。

2. **检测权等于持有密钥。** 检测器只需要文本 + 密钥 + 同样的分词和分块规则，不需要模型。这让检测成本很低，也决定了谁能检测：密钥在 OpenAI 手里，所以「不公开检测器」等于下游任何人都没法自证或验货。接入方能控制的只有「打开」这一步。

3. **信号容量 ≈ 可选余地 × 长度。** 可选词越多、文本越长，证据越多：200→400 token，检出率从约 80% 升到 95%。数学、事实性短答、照抄给定文本、代码，可选余地小，信号就弱。这也是 Code of Practice 豁免 <200 token 和代码片段的原因。

4. **编辑会线性冲掉证据，翻译基本归零。** 同义词替换会破坏「上下文窗口 → 伪随机数」的对应：替换 10% 时检出率掉到 66%，25% 时掉到 17%。翻译会整体重写 token 序列，官方只给了「可能检不出」的定性说法，**没有数字**。语言之间也有差异（69.0% 到 42.2%），靠强度旋钮补，代价是多样性。

5. **零比特、按地区灰度、按项目选择。** 水印只回答「有没有」，不带用户或组织 ID。产品侧在欧盟地区默认开，API 侧由客户自选，而法律义务在 provider 身上。等于把「是否、对谁开」交给了在欧盟面向用户的 API 客户自己判断。

### 工程落地（8 条）

1. **先定角色，再决定开关。** 用 OpenAI API 做面向欧盟用户的生成式产品时，你可能就是第 50(2) 条的 provider。由法务判断，工程侧准备好「组织默认关、欧盟面向项目单独开」的项目拆分（Project Settings → Text provenance）。
2. **留可审计的配置证据。** 检测器拿不到，响应里也没有公开的水印标志，所以合规证据只能靠自己留：哪个项目、哪些模型、哪天开的、谁改的。把控制台改动纳入变更管理，同时在调用日志里记模型名和项目 ID。
3. **水印≠可见标签。** 帮助中心原话：不替代可见标注。属于第 50(4) 条（公共利益文本），或者 UI 上需要告知「你在和 AI 交互」（第 50(1) 条）的场景，照样要做显式披露。
4. **按覆盖缺口设计预期。** 短答（<200 token）、代码、数学、照抄类输出，本来就可能不带或检不出水印。结构化输出（JSON、表格）的可选余地同样小，这是**按机制推断**，官方没有单独给数，不要把它当成已覆盖。
5. **自己回归一次质量和多样性。** 官方只公布了 Astra 的基准。你用的模型、语言（尤其是罗马尼亚语这类检出偏低、强度被调高的语言）、n>1 采样，都要做开和关的 A/B：业务指标 + 重复采样的多样性。
6. **云渠道单独核对。** 通过云伙伴访问 OpenAI 模型时，博客写的是「coming weeks」，可用性因伙伴而异。不要假设 OpenAI 控制台的开关会自动同步过去。
7. **禁止把检测结果当判决。** 官方明说「检测不到≠人写的」。教育、招聘、内容审核这类场景，内部制度要写明：水印信号不能当唯一证据，没有信号也不能推出是人写的；何况检测器本来就不公开。
8. **欧盟区 Codex 用户提前告知。** eligible 的散文类输出（PR 描述、文档、commit 说明）会被加水印；代码片段在 Code of Practice 下不要求。对代码正确性的影响**官方没有单独评估**，只有 Astra 基准里 DeepSWE、Terminal-Bench 的对照。

### 风险

- **误报率是按目标设的。** 1% FPR 放到大规模扫描里，绝对误报数并不小。报告也承认重复上下文会让误报率偏离理论值，不同 key、不同应用的误报率不保证一样。
- **法律时间线拿的是二手源。** 12/2 宽限期来自律所解读，OJ 原文没核对，上线排期要让法务确认。
- **口径漂移。** 帮助中心（现在时、只提 ChatGPT）和博客（coming weeks、ChatGPT + Codex）不一致；模型列表、云伙伴覆盖都还在变。
- **开源以后对抗研究会加速。** 官方自己的数据就显示中度改写会大幅削弱信号，别把水印写成「防滥用」的安全承诺。
- **隐私表述的边界。** 官方说水印不关联用户或 prompt，这是对水印本身的说法；平台层面的日志和保留政策要另看。

### 机制拆解

1. **隔离单位 = git worktree × 线程。** 每个托管 worktree 绑一个线程（owner）。`/fork` 进新 worktree 会带上对话历史，`/new` 进新 worktree 不带。「换个方向试试」就是同一段上下文分叉到另一份 checkout，两边的文件互不干扰，共享 `.git` 里的提交和分支元数据。

2. **两层编排要分开看。** 会话**内**是 subagents：并行子线程，受 `max_concurrent_threads_per_session` 限制，继承权限。会话**间**是 command center：按项目、状态、模型看多个独立会话。文档没写 subagent 会各自拿一个 worktree，按「checkout 绑在线程上」的设计推断，**同一会话里的子 agent 共用一份 checkout**（这是推断）。要真正并行改代码，应该开多个 worktree 会话，而不是在一个会话里开多个子 agent。

3. **worktree 隔离文件，sandbox 管权限。** worktree 只防兄弟会话互相踩文件；能不能联网、能写哪些目录、什么时候停下来问，仍然由 sandbox_mode、approval_policy 和 reviewer 决定。0.158 修过「writable roots 之间的 Git 元数据保护」，说明共享 `.git` 本身就是一个需要保护的面。

4. **安全闸门在「建」和「删」两头。** 建：不信任的来源拒绝，主会话不空闲拒绝，指令不一致不让 fork。删：只删干净的、只删托管的、不删当前 checkout。CLI 不自动回收，就是宁可占磁盘也不误删未合并的探索分支。

5. **语音是控制面，不新增权限。** 语音只负责发起、查询、转向任务，执行权限跟随被指挥的任务。真正的风险在桌面端的 screen context / appshot：可能带走窗口滚动区外的文字。

### 工程落地（8 条）

1. **一任务 = 一 worktree = 一线程。** 定方案后在 worktree 上建分支（团队统一用 `codex/` 前缀），然后 push 开 PR。不要让同一分支同时在主 checkout 检出（git 会报 `already used by worktree`）。
2. **A/B 方案用 `/fork` 进新 worktree。** 两个方案各跑同一套最小测试，比 diff 和测试证据。胜出的建分支开 PR；落选的提交清理后在 Browse worktrees 里删掉（有未跟踪或被忽略文件时会被拒，这是设计如此）。
3. **磁盘要有人管。** CLI 不自动清理，又和桌面共用一个池。每周固定用 `/worktree` → Browse worktrees 清一次，或者写一个只读的 `git worktree list` 巡检脚本报给负责人（只读，不自动删）。
4. **CI / 批处理用 `codex exec --worktree`。** 非交互模式下需要新审批的动作会直接失败回报，正好拿来当闸门：失败就停，不要为了跑通把 approval 调成 `never` + full access。
5. **先定权限再派活。** 子 agent 会继承父会话的实时覆盖，包括 `--yolo`。父会话保持 `workspace-write` + `on-request`；只读调研单独做一个 `sandbox_mode=read-only` 的自定义 agent（`.codex/agents/*.toml`）。
6. **并发显式设上限。** 在配置里写死 `agents.max_concurrent_threads_per_session`（默认值没公开），配合 command center 的 token / USD 估算（Biz / Ent）做每日预算；硬上限思路见 10/5 稿 §C。
7. **审批前看清来源线程。** 多线程时审批可能来自后台线程，团队约定先按 `o` 打开再批，尤其是联网和越界写这两类。
8. **`.env` 不要默认复制进 worktree。** `.worktreeinclude` 能复制被忽略的密钥文件，但文档明写的是桌面 app 行为，CLI 没写。宁可在 worktree 里用最小权限的测试凭据，也不要把生产密钥铺到每一份 checkout 里。

### 风险

- **视频没取回。** 「跨项目」具体演示的是哪个视图、语音是否触发 worktree，只按文档和 PR 推断。
- **同会话子 agent 共用 checkout**（推断）：并行写同一文件会冲突。
- **`--yolo` 继承**会把父会话的放权扩散到所有子线程。
- **磁盘膨胀**：每份 worktree 都有自己的依赖和构建缓存，CLI 又不自动回收。
- **daemon 版本不匹配**会让 worktree 创建失败，团队要统一 CLI 和 daemon 版本。
- **桌面文档和 CLI 行为混写**（15 个上限、快照恢复、`.worktreeinclude`），照抄进 CLI 运行手册前先实测。
