## 1）Anthropic：削弱针对 Claude 的蒸馏攻击 ★

**链接**：https://x.com/AnthropicAI/status/2109795898909950247 · 博客 https://www.anthropic.com/research/distillation-defenses

**一句话结论**：Anthropic 的防线集中在「推理链（thinking）拿不到」这一点上，分三层：推理摘要化加 preserved thinking 限制流向；两段式分类器拦截提取请求；对屡犯账号限流和封号，并对被拦请求计费。【自报】博客写的效果是被提走的推理 token 下降 10–100 倍，误报率低于 0.1%。代价是部分正常集成要改造，被误拦的请求也要付费。

### 机制拆解

1. **保护对象是推理链，不是最终答案**。博客明确说推理转录是蒸馏最有价值的数据，所以防线几乎全押在这里。80.4%→71.8% 这组数说明，只给摘要就能让蒸馏出来的学生模型掉约 8.6 个百分点。注意这是 Anthropic 自己设计的实验，不是第三方复现。
2. **流向控制（preserved thinking）**：把推理块锁在原会话、原模型、原组织里，堵住「跨会话、跨模型、跨账号挪推理块」这类路径。这是架构层的约束，不依赖识别意图。
3. **内容层分类器**：复用滥用防护那套两段式分类器，配合红队测试和快速补丁的循环。博客只公开到类别层面，本稿也只写到这一层。
4. **经济和身份层**：限流、封号、对被拦请求计费，抬高代理网络批量试错的成本。蒸馏方是靠规模取胜的，所以「让每次失败都要花钱」是关键杠杆【推断】。
5. **度量口径**：衡量的是「Anthropic 自家平台上被提取的推理 token 估计量」，是估算值。不覆盖第三方云和推理平台，博客自己也说蒸馏流量分散在多个平台。

### 工程落地（对 API 提供方 / 下游用户）

1. **API 提供方**：把「推理可见性」当成和权限一样的资源来管，包括摘要、按组织隔离、禁止客户端改写历史 thinking 块。只上分类器是不够的，Anthropic 自己说简单防线被绕过了。
2. **API 提供方**：异常检测要按「账号簇 / 代理网络」聚合，单账号阈值不够；处置要能在小时级完成（博客自报不到 2 小时）。
3. **API 提供方**：误报率要有公开口径，再决定是否对被拦请求计费。Anthropic 只在误报率 <0.1% 的领域计费，这个前提可以借鉴。
4. **下游正常用户（agent / 多轮集成）**：如果你的客户端会回传、改写、拼接历史 thinking 块，8/31 后建的账号可能要改集成。博客承认部分开发者已经被迫改造。建议原样回传 thinking 块，不做裁剪或修改【推断：具体 API 报错和行为看官方文档，本稿未核】。
5. **下游正常用户（合成数据、评测）**：不要依赖原始推理链做数据集或评测，能稳定拿到的只有摘要。评测要以最终答案和工具轨迹为准。
6. **下游正常用户（跨模型流水线）**：「A 模型的推理给 B 模型读」这种设计在新模型上不可行（较弱的旧模型读不到），多模型编排时推理只在单模型内部用。
7. **企业合规**：用 Claude 输出训练自有模型的，先对照商业条款中关于开发竞争模型的限制。**条款原文本稿未核到**，须由法务查原文。另外，被分类器误拦的请求也会扣费，需要在成本监控里单列。
8. **平台方（云 / 中转）**：博客点名平台也要承担检测和清退责任，转售 Claude 的中间商可能面临更严的 KYC 要求【推断】。

## 2）OpenAI Devs：标注 + WebMCP，给浏览器里的 agent 补页面上下文 ★

**链接**：https://x.com/OpenAIDevs/status/2109716341490106869 · 文档 https://learn.chatgpt.com/docs/webmcp 、https://learn.chatgpt.com/docs/annotations-extensibility

**一句话结论**：ChatGPT 桌面端内置浏览器里有两套网页侧 API。**Browser Annotation API**（`document.oai.annotation`）是 OpenAI 私有的，负责把用户选中的内容和反馈变成结构化上下文；**Site tools** 是 OpenAI 对提案标准 WebMCP（`document.modelContext.registerTool`）的实现，让 agent 能调用页面自己的业务逻辑。前者负责「看什么、要什么」，后者负责「能做什么」。

### 机制拆解

1. **标注 = 上下文通道（用户 → 模型）**。不写代码也能用：用户进入 Annotation mode，选中元素或文字，写评论，发到 Codex 或 Work。开发者可以定义「选中单位」（整张卡片、canvas 内的对象），附带不可见的元数据，还能挂预览控件（比如把间距从 16 调到 24），标注会记下前后值。**打开标注不会自动发送，只有用户能提交。**
2. **WebMCP = 动作通道（模型 → 页面）**。页面用 JS 注册带 JSON Schema 的工具，`execute` 直接调用应用里已有的逻辑，复用用户当前的登录态。agent 不必模拟点击 DOM，准确率更高、步数更少（文档说法）。
3. **两者如何拼**：标注负责把「改这里、改成这样」精确送进对话，site tools 负责用应用的接口把改动落下去，正对应帖子里「编辑场景、更新报销」的例子。
4. **和普通 MCP 的区别**：MCP 是 AI 应用连本地或远程服务器，不依赖打开的网页；WebMCP 的工具属于当前页面，离开页面就失效，也不用安装服务器。文档说一个站点可以两者都做。和 10/2 「ChatGPT 内建/部署 MCP」的区别 → 指针：10/2 稿「顺带一句」Tibo 条（那条讲的是服务端 MCP 的托管）。和 Apps SDK（iframe 组件经 MCP 下发）的区别 → 指针：10/8 稿 §1 末尾。
5. **信任模型**：文档明确说网站提供的工具定义和返回结果都是**不可信内容**，`readOnlyHint` 不能证明工具真的只读；每次调用前浏览器会做安全审查，后果性动作仍走确认策略；每次调用都绑定到发起页面和对应的注册。

### 工程落地：自己的网页应用接入

1. **先做只读工具**：比如 `get_selection`、`get_chart_data`，先上 `readOnlyHint: true`；用特性检测 `typeof document.modelContext?.registerTool === "function"`。
2. **工具粒度对齐现有 API**：`execute` 里调用后端已有的接口，沿用原有的鉴权、授权和校验，不要另开一条「agent 专用」的后门。
3. **schema 收窄**：`additionalProperties: false`，用枚举和长度上限；返回值要包含能核对结果的信息（id、新值）。
4. **写操作标 `consequentialHint`**：支付、删除、发信、改权限这类操作，服务端再做一次确认或二次授权，不要只靠浏览器弹窗。
5. **UGC 输出标 `untrustedContentHint`**：评论、外部抓取内容等返回前要做定界和转义，防止间接提示注入。
6. **工具注册在顶层页面**：iframe 里的不会被发现。微前端架构要把工具提升到 shell 层。
7. **标注元数据当作公开内容**：`oai-annotation-metadata` 会同时给用户和模型看，不要放 token 或内部 id；不超过 6 个键、2048 字节。
8. **降级与测试**：没有 API 的浏览器必须照常可用；按文档的 7 步测试清单走一遍（选择、请求、控件预览与复原、canvas、保存与重开、发送、无 API 回退）。权限审计清单 → 指针：10/11 稿 A（权限与审计检查清单），直接逐项套用即可。

**适用场景**：人和 agent 要看同一画面的应用，比如画布或设计编辑器、仪表盘筛选、文档批注、报销或行程表单。纯后台批处理更适合普通 MCP。

### 风险

- WebMCP 是提案标准，ChatGPT 只实现了子集，API 可能变动；`document.oai.annotation` 是 OpenAI 私有 API，其他浏览器不可移植。
- 恶意站点可以注册名字看起来无害的工具；同一会话跨站浏览时，有被站点诱导泄露上一站信息的风险。文档说「网站指令不授予 agent 共享无关信息的权限」，但这是策略层面的承诺，不是保证。
- 复用登录态意味着 agent 拥有用户的全部权限；应用侧没有细粒度授权时，后果性操作的风险会被放大。
- 帖子和文档对模型版本的写法不一致（文档写 GPT-5.6 Sol / GPT-6 Sol），以文档为准，6.1 是否支持**未核到**。
