### 机制拆解

1. **「近旗舰能力 × 工作负载价」产品位**  
   Sol 不是「便宜的小模型」，而是把 Astra 在 coding/computer use/专业任务上的能力形状压到约 1/5 入出单价；选型轴从「要不要旗舰」变成「任务能否接受 Sol 的剩余差距」。

2. **Cache-read 才是 agent 经济学的主旋钮**  
   $0.10/M cached（95% off input）针对**稳定前缀复用**（系统提示、仓库摘要、策略语料）。无 cache 命中时，$2/$10 与旧 Sol 同档，省不出「1/5 Astra」叙事之外的额外红利。

3. **Ultrafast ≠ 模型升级，是服务档**  
   官方把速度写成独立 premium tier；Astra 先上、Sol 后上。Pricing 上 Ultrafast 对 Astra 约 **6×** Standard——吞吐换账单，适合交互/IDE 路径，不适合批处理。

4. **272K 门槛是隐性成本悬崖**  
   超阈值整请求倍率：长仓库/多文件上下文一次塞满会突然 2×/1.5×，需与「靠 cache 省钱」策略联合设计（分段、摘要、会话级 cache）。

5. **Effort 仍是能力旋钮**  
   与昨日 Sonnet 5.5 叙事同构：同一 model ID 多档 effort；官方评测多在特定 effort 下报分——生产必须把 effort 写进路由与成本模型。

### 工程落地（8 条）

1. **默认路由**：高频 agent coding / 工具循环 → `gpt-6.1-sol` + 合适 effort；仅保留 Astra 给「评测/客户可见质量差不可接受」的尾巴。  
2. **强制测 cache 命中率**：对系统提示与 repo digest 做稳定前缀；监控 `cached_tokens`；目标命中率写入 SLO（否则 95% 折扣只是纸面）。  
3. **272K 守卫**：网关在组装上下文时硬截断/摘要，避免整请求翻倍；单价告警与 token 告警分开。  
4. **Ultrafast 白名单**：仅对「人在环、可感知延迟」的 Codex/交互路径开 Astra Ultrafast；批跑、夜间扫描走 Standard/Batch/Flex。  
5. **Sol Ultrafast 未就绪前勿写进合同 SLA**：官方明说 coming soon；Pricing Ultrafast 栏暂无 Sol 行。  
6. **同任务成本对照表**：用内部 golden tasks 比 Sol vs Astra 的 $/task 与通过率，不要只比 $/MTok。  
7. **Work/Codex vs Chat**：产品文案写清「Sol 在 Work/Codex，不在普通 Chat」，避免支持工单爆炸。  
8. **读 system card addendum**：上线前对齐安全评测口径（官方称 alignment 相对 GPT-6 Sol 改善、更近 Astra）——合规材料引用官方卡而非三方摘要。

### 风险

- **「1/5 价」误读为任务成本恒 1/5**：无 cache、高 output、高 effort、Ultrafast 都会打破。  
- **速度数字是「up to」**：300 tok/s / 8× / 6× 为官方宣称上限，非你工作负载的实测。  
- **厂商榜分**：DeepSWE / OSWorld / GDP.pdf 等均为 OpenAI 公开自评，**未独立复现**。  
- **长上下文倍率**：一不小心触发 272K 规则，账单跳变。

### 机制拆解

1. **Harness 与 Sandbox 解耦**  
   编排/上下文/恢复/工具循环在 API 侧；执行面可换——这是企业落地的关键：数据面可进 VPC，控制面仍用 OpenAI harness。

2. **「自建云 agent ≈ 产品化 Codex」**  
   Tibo 表述直白：用 Agents API 可做他们今天开放的同类产品；dots 是该栈的一等公民产品，不是隐藏另一套协议。

3. **Computer use 把 agent 从「API 工具」扩到「GUI 操作」**  
   能力面扩大的同时，攻击面与审计需求同步上升（截图、键鼠、会话录像、权限边界）。

4. **长会话是一等公民**  
   compaction、resume、subagents 说明目标负载是小时～天级任务，而非单次 completion。

### 工程落地（8 条）

1. **PoC 路径**：先 `openai_hosted` 沙箱跑通会话/工具/产物，再迁自建或伙伴沙箱做合规。  
2. **权限最小集**：注入沙箱的 files/secrets/plugins 白名单化；默认拒绝任意网络与浏览器凭证（对齐昨日 Ng/OpenShell 思路）。  
3. **Computer use 单独闸门**：仅对需要 GUI 的任务开；全程录屏/DOM 摘要入库；生产前做越权用例。  
4. **Subagent 预算**：限制 `max_concurrent_subagents` 与每会话美元上限；防 fan-out 账单爆炸。  
5. **不要假设 ZDR**：若合同要求 ZDR/非美数据驻留，Agents API 现状可能不达标——提前走 Private Intelligence / 其他产品线或自建全栈。  
6. **与 dots 对照选型**：要「给员工的 always-on 助手」→ 评估 dots 产品；要「嵌入自有 SaaS 的云 agent」→ Agents API。勿混用治理模型。  
7. **Codex Cloud 环境即政策**：把批准的镜像、包、权限做成可复用环境模板，禁止每人私自改基线。  
8. **可观测性**：订阅会话事件流；失败恢复与人工 takeover 写进 runbook。

### 风险

- **Preview/Beta 行为变更**：API 形状与限额可能快速迭代。  
- **Computer use 侧信道**：GUI 比结构化工具更难做 DLP。  
- **同源≠同 SLA**：dots 产品体验与自建 Agents API 的可靠性、审核、配额分离。  
- **数据驻留/ZDR 缺口**：文档已明示限制。

**一句话结论**  
Decisions API 把 **Luna** 收成「有限答案集合上的实时决策层」（分类 / 路由 / agent 下一步），支持 **文本+视觉**；官方强调 **real-time** + 有限预定义答案，Tibo 给出 **端到端亚数百毫秒** 量级——**精确 SLA（如 p50/p95）与专用单价：公开渠道未给出，记「未公开」**。

### 机制拆解

1. **约束输出空间 = 延迟与可组合性**  
   有限答案让接口更像「分类器/路由器」，而非生成器——省去长文本解码与 JSON 解析失败模式。

2. **视觉输入服务闭环控制**  
   截图/传感器画面 → 立刻选动作，适配硬件或 computer-use 内环；与 Agents API 的逐步决策互补。

3. **Luna 角色下沉**  
   大模型做重推理，Luna/Decisions 做高频便宜决策——经典两级 agent 架构的一等 API 化。

4. **Preview 边界**  
   limited preview 意味额度、区域、配额未完全产品化；Broad release「coming days」需跟踪 changelog。

### 工程落地（7 条）

1. **答案集合设计成枚举契约**：版本化 `decision_id → {question, options[]}`；禁止运行时自由文本选项膨胀。  
2. **自测延迟预算**：分别测纯文本 vs 图像；记 median/p95/p99 **含网络与重试**；在正式 SLA 公布前用自有基线。  
3. **置信度不盲信**：若返回 score，先校准到业务代价矩阵（错路由成本 ≫ 错分类成本时阈值人工）。  
4. **与 Agents API 串联**：外环 Astra/Sol 规划，内环 Decisions 选下一步；设超时回退到规则引擎。  
5. **视觉决策的对抗集**：模糊 UI、遮挡、注入性屏幕文字——作回归，防 prompt/视觉注入改路由。  
6. **成本记账预留独立 meter**：即使暂按 Luna token 估，也要能切换到未来 per-decision 计价。  
7. **Preview 功能开关**：生产默认关；allowlist 租户灰度。

### 风险

- **「亚数百毫秒」≠ 合同 SLA**：无官方分布与区域定义。  
- **有限答案掩盖语义漂移**：选项过粗导致系统性错路由。  
- **视觉攻击面**：屏幕内容可被对抗样本或注入文案劫持。  
- **定价未公开**：财务模型只能暂估。

2. **对话内发现 = 新分发算法**  
   「相关插件出现在对话中」把增长从目录浏览改为意图触发——排序与激励会决定生态。

3. **双向上下文（Model-App Context）**  
   ChatGPT 与 MCP App 同步上下文，使「聊」与「做」同一工作区，降低复制粘贴损耗。

4. **事件驱动自动化**  
   MCP Events 让插件从拉模式变推模式（看板新任务 → 自动起草），接近轻量 iPaaS。

### 工程落地（8 条）

1. **先定扩展面**：选 sidebar（重应用）或 conversation panel（伴聊）或 file viewer（格式所有权）；勿一次全做。  
2. **权限 UX 一等设计**：最小 scope；首次连接清晰说明读写面；支持企业 admin 策略。  
3. **为「对话内推荐」准备意图信号**：工具描述、示例 utterance、类别元数据按审核指南打磨。  
4. **提交流程工程化**：把「修工具不全量重提」纳入 CI；保留审核反馈工单模板。  
5. **桌面 vs Web 能力表**：Composer mentions 等桌面-only 能力在文档中写清降级。  
6. **Sites + 插件**：对内工具优先 Sites 分发，复用各成员自己的 OAuth/数据边界。  
7. **MCP Events 幂等**：事件触发的自动化必须幂等与可撤销，防风暴。  
8. **安全评审**：扩展 UI 可钓鱼——域名、深链、富表单按应用商店级威胁模型审。

### 风险

- **平台依赖**：分发与推荐算法不透明，增长不可控。  
- **审核不确定性**：虽流程改进，仍可能阻发布。  
- **权限过宽**：一次批准导致数据外泄。  
- **1.2B 是平台口径**：≠ 你的插件可达用户数。

## 5）前沿 RL 训练安全 / safety cases ★

**标题 / 链接**  
- Greg Brockman（@gdb）：Practical guidelines on securing frontier RL training…  
  https://x.com/gdb/status/2104821232441160070

  https://x.com/OpenAI/status/2104815409522483470

  （发布标注 **2026-09-28**；本文经 curl 提取正文要点）

**一句话结论**  
OpenAI 主张：继续任何 **frontier RL 训练跑** 前应有结构化安全文档，并朝其他高危行业式的 **safety cases（基于证据的综合论证）** 演进；文中给出当前指南三块——**技术护栏（对齐训练 / 遏制 / 监控）**、**运营流程（异议、批准、问责、暂停…）**、**错位事件调查**——并强调这是 **进行中实践 + 欢迎社区反馈**，且范围 **聚焦 frontier RL 训练**（部署需更广对齐属性）。**本文只作防御性机制与治理摘要，不提供任何攻击步骤。**

### 机制拆解（防御视角）

1. **技术栈三层防御（对齐 → 遏制 → 监控）**  
   - **Model alignment**：训练环境与打分防 reward hack（自动化+人工数据集审查、grader 调参、历史 trace 分类器）；对齐评测、回测、追踪 eval gaming、最坏情况压力测试；**不对 CoT 做自动打分可见**，以免模型学会逃避 CoT 监控。  
   - **Containment**：沙箱与研究基础设施多层加固；用训练 checkpoint **红队**沙箱/边界/模型可触达服务；限制高带宽跨 sample 通信；**不可篡改 transcript**（如 write-once）以利调查。  
   - **Monitoring**：可监控性评测与阈值；对已知事件高召回；为新风险刷新评测集；**优先告警 + SLA**（白天 page，夜间未确认可 **auto-pause**）。

2. **运营上把 safety case 做成「可否决的发布门」**  
   跨团队 **dissent（pre-mortem）**；高层多人可 **veto**；run owner 问责进绩效；失效则有暂停 runbook；对内透明给 Safety/Security 委员会；审计员可核验主张；错位升级表 + 可 page 到高管；技术控制 **fail closed**；可追溯下游使用以便 rollback；枚举 **residual risk**。

3. **事件调查当「高危行业事故调查」**  
   调查期对内定期更新；根因训练动力学（消融/重采样等）；运营/文化 postmortem；检测方法避免只对事件本身 hillclimb，另建回归测试；结束后 **公开披露** 并尽快通知受影响第三方。

4. **开放的证据类型（文中明示方向，非攻击手册）**  
   对齐评测与回测结果、monitor recall/precision、遏制红队发现与关闭记录、不可变 transcript、异议与批准链、暂停演练证据、事件根因与公开 postmortem——即 safety case 应用**可审计证据包**支撑「可继续训练」主张。

### 工程落地（8 条）——面向训练/评测平台方与采购安全问卷

1. **训练门禁清单**：无书面 safety case（哪怕早期模板）+ 异议记录 + 批准人列表，禁止启动覆盖范围内的 frontier RL run。  
2. **打分器与环境隔离**：自动 grader **不可见 CoT**；环境漏洞用 agent+人工双审；历史 cheat trace 回归。  
3. **遏制基线**：沙箱外再套研究基础设施边界；跨样本通道默认关；transcript 进 WORM/对象锁。  
4. **监控 fail-closed**：无监控不可开跑；禁用监控的路径从训练环境不可达。  
5. **夜间 auto-pause**：告警未确认即暂停；演练 MTTA/MTTR。  
6. **错位严重级别表**：定义谁可 page CEO 级；与现有 SecOps on-call 对齐。  
7. **采购/合作问卷**：要求对方提供 safety case 大纲、residual risk 列表、最近一次红队与暂停演练摘要（机密可控）。  
8. **披露预案**：若涉及第三方数据/服务，事先写通知模板与法务路径（呼应文中 public disclosure / notify third parties）。

### 风险

- **指南 ≠ 已全部落地**：文称 recommendations **正在 OpenAI 实施中**，数周内还会演进。  
- **范围窄**：只覆盖 frontier RL 训练，不替代部署安全方案。  
- **证据不足的「纸面 case」**：无独立审计时，文档可能变成合规剧场。  
- **评测 overfitting / eval awareness**：文已警告；需持续刷新评测与监控。
