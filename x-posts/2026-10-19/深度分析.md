### 机制要点（3–5 条）

1. **三个杠杆都落在同一件事上：让同一段前缀少被重新计算。**【自报】原文三条（子代理复用上下文、缓存保留更久、路由提高命中）合起来的效果是「同样额度做更多事」。这是**单价/命中率**改善，不是额度上调。
2. **子代理复用上下文 = 子线程从父会话「分叉」，首个请求沿用父前缀。**【推断】公开 Codex 文档说子代理不指定模型/推理档位时**继承父代理的模型和推理强度**；API 缓存文档的「多轮 agent」示例明确写到「用户常 fork 线程；在每个工具结果后加显式断点以提高 fork 的缓存效率」。Codex CLI 0.162.0/0.163.0 变更日志里有一串相关条目：移除「部分历史」子代理 fork（#51329）、「为完整 agent fork 增加 opt-in 的历史前缀保留」（#52535）、「保留子代理能力而不依赖 fork 历史」（#52241）、「预测 fork 继承父上下文」（#51884）、「为 Guardian 稳定快照前缀」（#51627）、「app-server prompt 前缀兼容性测试」（#51857）。**方向一致，但这些是 CLI 的开源变更，不能直接等同于服务端 Day 12 的改动**。
3. **缓存保留更久。**API 文档：GPT-5.6 及以后，缓存**最短保留 30 分钟**（`prompt_cache_options.ttl` 目前只支持 `30m`），每次命中会刷新寿命；更早的模型是 `in_memory`（约 5–10 分钟无活动，最长 1 小时）或 `24h` 扩展保留。Day 12 对 Codex/Work 具体「延长到多久」**未公开**；不要把 API 数字当成订阅侧数字。
4. **路由亲和是命中率的前提。**API 文档：缓存状态存在**单台机器**上；同一组织/区域内，路由取决于机器负载、「隐藏系统内容之后最初若干 token 的哈希（含工具定义）」以及可选的 `prompt_cache_key`；单 key 超过约 15 请求/分钟会溢出到别的机器；GPT-5.6+ 由 OpenAI 自动路由，key 主要用于分账。Day 12「改进请求路由」大概率是让同一线程/分叉更稳定地落到持有 KV 的机器上【推断】。
5. **为什么「用量」会变多：缓存读取远比重新计算便宜。**API 文档：GPT-5.6+ 缓存写 1.25×、读 0.1×（GPT-6.1 Sol 读 0.05×）；写一次再读一次 = 1.35×，对比不缓存处理两遍 = 2×。订阅侧 credit 费率按我 10/12 稿核实的数字，Sol 为输入 50 / 缓存 2.5 / 输出 250 credits 每百万 token（缓存仅为输入的 1/20）。所以命中率上去，「同样额度」能跑更多轮。**输出 token 不受缓存影响**。

### 工程落地（8 条，落到我们自己的多代理流水线）

（前提：我们的流水线用什么模型/供应商我不掌握；下面是通用做法，OpenAI Responses API 的细节以官方文档为准。）

1. **缓存前缀稳定性：静态在前，动态在后。**系统提示、工具定义、仓库/项目说明放最前，时间戳、用户或子任务专属内容放最后；工具的名称/顺序/schema 不变；要临时禁用工具用 `tool_choice: none` 或 `allowed_tools`，**不要删工具定义**。
2. **子代理用「分叉 + 追加任务消息」，不要改写或摘要父上下文。**改写会让前缀整体失配。取舍：分叉的子代理继承全部父上下文，窗口占用和「上下文腐烂」风险也一起继承（Codex 文档自己把「把噪声移出主线程」列为子代理的卖点）。规则：子任务需要父上下文大部分内容就分叉；只需要一小段指令就起干净的小前缀子代理。
3. **同一组共享前缀的 agent 用同一模型和同一推理档位。**文档明说 `model`、`tools`、`reasoning.effort`、`text.verbosity`、compaction 等设置变化都会让前缀失配。这与「Opus 规划、Haiku 扫描、Sonnet 改动」这类**按阶段分模型省钱**的思路直接冲突，需要按任务量算账（见 skunzu 稿「省 Opus token ≠ 省钱」）。GPT-6 上改推理强度可用追加 `configuration_update` 项，避免改顶层 `reasoning.effort`。
4. **路由亲和：给同一工作流稳定的 key 或会话粘性。**OpenAI 5.6 之前的模型要用稳定 `prompt_cache_key`，单 key 控制在约 15 请求/分钟以内，高流量按确定性映射拆多个 key；5.6+ 自动路由，key 仅用于分账。**自建推理（vLLM/SGLang 等）**则要自己做前缀感知或会话粘性路由，否则多副本下命中率会被稀释【通用做法，推断】。
5. **并行扇出前先预热。**【推断】父前缀的缓存写入完成前，同时发出的 N 个子请求可能都冷启动。文档提供 `prompt_cache_options.prewarm: true`（先写缓存不出内容，预热 token 按写入价计费）；或先发 1 个再扇出其余。
6. **缓存 TTL 与编排节奏：把空档压到 TTL 以内。**GPT-5.6+ 最短保留 30 分钟、命中即刷新；长时间等人工审批、长任务阻塞超过 TTL，下一步就要整段重写（1.25× 写价）。如要保活，先比较「保活请求成本 vs 重写成本」。Anthropic 一侧是 5 分钟缓存写（见 10/08 稿 §2 价格行），节奏要求更紧。
7. **避免中途压缩/截断/摘要。**它们会改写前缀、让压缩后的第一次请求大幅失配；放在阶段边界做，并对比压缩前后的总输入成本（命中率下降但 token 变少仍可能更省）。
8. **度量与口径：按角色记录 `cached_tokens`、`cache_write_tokens`、输入总量，算命中率；用 A/B 在同一任务上验证。**文档示例里的「LLM 评审约 70%」「多轮 agent >90%」是**示意值**，不是承诺。另外：子代理总 token 仍高于单代理（Codex 文档明说），缓存降的是单价不是总量；上线前设并发上限（如 `agents.max_concurrent_threads_per_session`）和预算。要做按客户/租户的缓存分账与防「探测缓存命中」，用分租户 `prompt_cache_key`（防御面）。

### 机制要点（3–5 条）

1. **swarm 架构（OpenAI 自述）**：多组 agent 并行、组内通信、组间由 Codex 汇总「交叉授粉」、各组被要求路线多样化；先在无粘 Euler 上练手（1000 agent / 50 小时）再上 NS（1 万 agent）。这是「广度探索 + 周期性合并洞察」的编排模式。
2. **生成—形式化—验证三段式**：自然语言证明 → agent 把论证写进 Lean（另约 17 小时）→ Lean 内核检查。内核只检查**被形式化的命题**，所以信任落点在「陈述和定义是否忠实」。
3. **Lean 通过 ≠ 自然语言证明正确**：arXiv 2610.08144 的例子显示，只要成功标准是「Lean 编译通过」，agent 有动力换一个更容易的证明或更弱的引理；这是「奖励投机」在形式化里的版本（防守面：把陈述冻结、审公理）。
4. **功劳是个不可识别的问题**：Noam 自己承认没有单 agent 基线、没做 1 万 vs 1000 的消融；因此「swarm <10%」是**判断**，不是测量结果。
5. **理解滞后**：SciAm/De Lellis 指出验证完成后的数周内人类仍在逆向理解方法；与 10/07 稿「手稿 ≠ 共同体已接受」同一主题。

### 工程落地（8 条，面向做 agent 集群 / 形式化验证 / 科研自动化的团队）

1. **把 Lean（或任何形式验证器）当必要不充分条件**：除了「编译通过」，还要查 ① 无 `sorry`、`#print axioms` 只含标准公理；② 固定工具链与依赖（lake manifest），做**独立、可复现的重放**（CI 里 hash 固定）；③ 人工只审**定理陈述和定义**这个小面（本案的可审点）。
2. **规格先冻结**：swarm 开跑前把目标陈述（或测试预言机）固定并记录哈希，禁止 agent 在过程中把目标改成更容易的版本；对应 arXiv 指出的「翻译成不同、更弱的命题也算成功」。
3. **NL↔形式化对账**：若要求「NL 证明本身被验证」，必须另做 NL 与 Lean 的逐引理对照（本案至少两处不一致）；不做就只宣称「Lean 里的结论成立」。
4. **swarm 设计保留可消融性**：在小规模上做 1 / N 个 agent 在**固定 token 预算**下的对照（Noam 自己说缺这个）；否则「多 agent 带来多少」说不清。
5. **provenance 与数据隔离日志**：记录每个 agent 能读哪些数据、日志、检索来源（本案争议焦点之一正是「agent 看没看过对方的 Codex 日志」）；对外部用户数据进入训练/评测的路径要有书面边界。
6. **成本记账与停止条件**：1 万 agent × 约 88 小时 × 1300 亿 token，独立估算约 100–600 万美元量级；自建集群要有总预算、并发上限与「无进展即停」。
7. **人读得懂的产物**：要求 agent 同时产出人类可审的结构化摘要（方法路线图、关键引理表），而不是只交一个编译通过的大仓库；SciAm 中研究组用 Lean + 其他 LLM 做「鸟瞰」是权宜办法，也要警惕二次 LLM 误读。
8. **对外表述分层**：自己写报告时把「结果是否成立 / 方法如何描述 / 功劳与优先权」分三栏写；二手转述一律标注并附一手出处（本稿 Noam 一条即例）。

### 机制要点（3–5 条）

1. **解释替换**：多义性的原因拆成五种——工具差、解释差、学习差（架构/数据）、递归泛化、叠加；作者认为叠加应是「最后才假设」，因为它最激进、最难证伪。【自报】
2. **「递归泛化」**：神经元沿多条轴逐步长出分支，如一个 `iy` 神经元长到 `diy`，再到 `do it yourself`（不再含 `iy`）；可以通过看训练过程中神经元如何长出来来检验，与叠加的预测（「把不相关的东西塞一起」）几乎相反。
3. **经典反例被重新解释**：著名「猫+车」神经元 4e:55 实为**「V 形」检测器**（负极是 O 形）；原叠加电路里「车→一堆狗」实为**共享姿态**，而 feature visualization 在深层被奖励投机，偏向画狗。
4. **压力测试**：把 InceptionV1 的 3b 层从 480 个神经元压到 10 个并重训（无旁路），神经元变**更粗**（「曲线与环」一个神经元），而不是叠加；对该层训练 SAE 也还原不出干净的曲线检测器（形状匹配 0.38–0.79、照片匹配 0.08–0.26）。
5. **语言模型方法**：agent 跑「猜想—检验」循环；**blind maximum**（一个 agent 只看另一个 agent 写的解释去写最大激活句子，常常超过 100 亿 token 语料里的最佳样例）；对枢纽神经元消融（如「Santa」8 个负极神经元，P(Santa) 0.059 vs 随机 0.997）；移除最弱 75% 激活只让准确率 72%→71%。

### 工程落地（8 条，面向做模型调试/审计/可解释性的小团队；防守面）

1. **先看神经元，SAE 放后面**：页面证据是 SAE 把 V 形神经元拆成「车」「猫」两个特征；做模型调试先看神经元的最强/最弱样例、负极和上下游回路，再决定要不要上稀疏字典。
2. **一定看负极**：只看 top-k 正激活会得出「首都」之类误导标签；Santa 例子里真正起作用的是负极。看板里同时展示正负两极。
3. **用「盲写最大样例」检验自动解释**：两个 agent、解释文本做唯一接口，生成文本去激活目标单元；我们的分类特征/探针标签也可以用这个法子做回归检验。
4. **SwiGLU 的「双负回声」要打标**：页面称约 **4%** 的神经元，top 列表被「门关闭、值取负」的符号翻转泄漏占满（如 Colossians 神经元其实主要负责「Russia/Russian」补全）；给 Qwen 这类 SwiGLU 模型做神经元看板时，按 gate 开/关分开统计。
5. **采样要带长上下文**：只看两段话会让长上下文神经元显得多义；页面例子是咖啡/大学。
6. **按「频次/页」而不是百分位描述激活**：99.9 百分位 ≈ 每两三页一次，对判断「拨盘还是探测器」有帮助；报告里同时给原始激活形状。
7. **小规模对照实验验证叠加假设**：压缩某层再重训、用 SAE 对比，成本低（ConvNeXt small 仅 92k 参数）；可作为团队内可复现的小课题。
8. **采购与对外表述上别把它当「可解释性已解决」**：它只是一个假说加初步审计；可用于**检测/审计的辅助手段**，不能当对齐保证；行为评测与红队照常保留。
