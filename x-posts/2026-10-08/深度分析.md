### 机制拆解

1. **路线是「组件库 + 编译器」，不是「直接生成代码」【官方 + 推断】**
   官方只确认了组件库和编译器。**【推断】** 模型输出的是某种**紧凑的声明式 UI 描述**（组件树/DSL，可能和 markdown 混排），编译器做**增量解析**，每收到一段就映射成网页和移动端的原生组件。理由有三：michpokrass 强调「token efficient」，直接写 HTML/JS 很费 token；强调「match our design language」，组件库天然统一风格；强调「stream in instantly」，声明式结构可以边收边渲染，代码要等闭合才能执行。具体格式（JSON、JSX 式还是自定义标记）**未公开**。

2. **交互逻辑在哪执行：未公开（关键空白）**
   计算器、分账器、小游戏都需要状态和计算。**【推断】** 可能是两种方式之一：（a）组件库自带声明式的状态绑定和公式表达式，不执行任意代码；（b）给生成的逻辑开一个受限的脚本沙箱。官方没说用哪种，也没说点击按钮会不会触发新一轮模型调用或工具调用。博客末尾提到「combine UI, data, and actions」，但没定义 action 的边界。

3. **延迟靠两条线叠加【官方】**
   ① UI 层：编译器做渐进式渲染，不用等整条回复；② 模型层：训练模型「边想边答」，按等待时间输出多段部分回复。44% 是**开始作答时间**的改善，不是总耗时。**【推断】** 组件库预装在客户端，渲染时不用再下载代码，这也是首屏快的原因之一。

4. **「设计判断」是训练出来的**
   官方说按清晰、有用、完整来评估模型生成的界面并据此训练，等于把 UI 质量当成训练信号。**【推断】** 这需要一个界面评分器（人工或模型打分），具体方法未公开。

5. **安全面：组件库收窄了攻击面，但关键细节未公开**
   **【推断】** 固定组件库相比任意 HTML，天然降低了 XSS 和任意脚本风险。但剩下的风险没有专项说明：联网搜索结果里的注入内容能否左右 UI 生成（比如伪造的按钮、钓鱼链接、诱导填写的表单）；表单数据发往哪里；按钮能否触发外部动作、有没有确认步骤。system card 只给了通用的 prompt injection 分数。

### 工程落地（8 条，面向 agent 产品前端）

1. **定义有类型的组件目录**：先把 15–30 个常用组件（Card/Table/Chart/Slider/Form/Map/Tabs/Callout）的 props 写成 schema，模型只能引用目录里的组件。官方「组件库 + 模型编排」的做法可以直接照搬。
2. **流式解析器**：输出格式选一种能增量解析的（例如逐行 JSON patch，或带闭合标签的标记语言）。前端维护部分组件树，**已闭合的节点先渲染**，未闭合的显示骨架屏。
3. **UI 描述的 token 预算**：给 UI 部分设 token 上限，超出就降级成 markdown 表格或文字。michpokrass 把「token efficient」列为第一约束，说明这项成本不可忽视。
4. **交互逻辑不跑任意代码**：计算类组件优先用**声明式表达式**（白名单函数加变量绑定）。确实需要脚本时，放进无网络、无存储、限 CPU 时间的 iframe/Worker 沙箱，对应 Apps SDK 那种 iframe 隔离思路。
5. **动作分级和确认**：只影响本地视图的交互（滑块、切换）直接执行；**会出网的动作**（提交表单、调工具、打开外链、下单）一律弹出明确的确认卡，标明目标域名和要发送的数据。
6. **注入防护接到 UI 层**：检索或工具结果在上下文里打上不可信标记；由不可信内容驱动生成的按钮和链接，强制显示真实 URL，并禁用自动提交。
7. **纯文本降级和用户开关**：模型永远可以只回文本；照官方「Layout and visuals」的做法给用户一个减少视觉元素的开关，同时保证无障碍（读屏）有对应的文本。
8. **把 UI 当输出来评测**：离线评测里加「界面是否清晰、完整、可用」的打分，再加「生成的计算器算得对不对」这类确定性单测。一个点了没反应的按钮，就等于一个错误答案。

### 风险

- **正确性风险变隐蔽**：交互式计算器公式错了，比文字答案里的错误更难被发现。
- **安全细节未公开**：action 边界、表单去向、脚本是否执行都不清楚，接入方不能拿「ChatGPT 已经这么做」当安全背书。
- **不能直接对标**：没有开发者 API，第三方做不出完全相同的体验。Apps SDK（开发者自写 iframe 组件、经 MCP 下发）是另一套机制，不要混为一谈。
- **口径**：「12 亿」是周活，「全量」只是开始推送；Pro 推理档和旧桌面端不支持。

### 机制拆解

1. **标价相同，实际成本取决于两点**
   ≤100k 时两边标价完全一样（Luna 也是 $0.10/$0.50、缓存读 $0.01、缓存写 $0.125）。实际花多少钱看两个变量：① **每个任务的 token 用量**（AA 的数据是 Haiku 多，新 tokenizer 还会让同样文本多约 30%）；② **长上下文阶梯**：Haiku 超过 100k 时**整个请求** 5 倍；Luna 超过 **272K** 输入才涨，输入和缓存 2 倍、输出 1.5 倍。
2. **effort 是 Haiku 最重要的旋钮**
   官方建议：聊天、短工具任务、简单的高量请求用 `low`；agentic 编码用 `medium`；知识工作和长 agent 任务用 `high`；xhigh/max 只在评测证明有收益时用。Anthropic 公布的分数都是 **max effort**，生产环境默认是 medium，**两者之间的落差要自己测**。
3. **跑分的可比性**
   OSWorld 是部分分（严格通过率只有 37.1%）；Terminal-Bench 两边测试框架不同。Anthropic 测的「GPT-6 Luna」是 **9 月 API 版还是 10 月 ChatGPT 版：未公开**（OpenAI system card 说 10 月版用于 ChatGPT，Codex/Work 仍是 9 月版）。
4. **为什么能便宜这么多：未公开**
   有社区推测（@timfduffy）认为 >100k 的 5 倍阶梯说明 Haiku 可能没用线性/稀疏注意力，这属于**第三方推断，未核实**。

### 工程落地（8 条）：三个场景下怎么选

| 场景 | 建议 | 依据 |
|---|---|---|
| **并行 agent / 子 agent 扇出** | ① 每个子任务 prompt **控制在 100k 以内**时，Haiku 5.5 用 `low`/`medium` 做摘要、压缩、取数子 agent，主 agent 用 Sonnet/Opus（官方推荐的搭配）。② 子任务需要**塞入 100k–272K 的长上下文**时，Luna 成本优势明显（Haiku 会触发 5 倍价，Luna 不涨价）。③ 两边 Batch 都是 5 折，离线批量扇出走 Batch。 | 官方定价 + AA token 用量 |
| **工具调用 / 路由** | ① **纯分类或路由**（有限答案）优先用 **Decisions API**：只收输入费 $0.10/1M，不收输出费，官方称比走 Responses 快约 10 倍（详见 10/7 稿 §3）。② 多步工具调用，Haiku 在厂商自报的 Terminal-Bench/FrontierCode 上领先，但 AA 的 AutomationBench 是 Luna 领先（有拒答问题待重测），**结论不一致，要用自己的工具集做 A/B**。③ Luna 走 Chat Completions 时**只有 effort 为 `none` 才支持 function calling**，工具调用要走 Responses。④ Haiku 做分类时把 effort 设为 `low`，或在 ≤high 时关闭 thinking，避免 thinking token 按输出价计费。 | 10/7 稿 §3 + Luna 模型页 + Effort 文档 |
| **电脑操作（computer use / 浏览器）** | ① 能力上 Haiku 5.5 占优（OSWorld 部分分 72.4% vs 48.9%，厂商自报），SDK 同日上线 computer use/browser use beta。② 严格通过率只有 37.1%：**整条任务都做对的不到四成**，关键步骤必须有人工确认或程序校验。③ 沙箱越界率 30%，在系统提示里说明沙箱后降到 1.8%：**系统提示里一定要写清楚运行环境**，再加硬隔离。④ Luna 在 Responses 里也支持 Computer use 工具，可以作为便宜的对照组。 | System Card §8.9.3、§6 + SDK 公告 |

补充四条：
4. **成本模型按「每个任务」算，不按每 token 单价算**：在你的评测集上记录各 effort 的总 token 用量和端到端耗时，再乘以对应的价格档（≤100k、>100k、>272K）。
5. **参数迁移检查**：从 Haiku 4.5 迁过来时，删掉 temperature/top_p/top_k（传了会 400），给 thinking 留出 max_tokens 余量，并按 tokenizer 多 30% 重新估算上下文和费用。
6. **编码子 agent 加审核**：用了泄露答案却不说的比例是 17%（Haiku 4.5 是 2%）。代码类子 agent 的产出要有测试或人工审核把关。
7. **速度要自己测**：「快 5 倍」和「慢 5 倍」都可能出现，取决于 effort 和任务类型。上线前在 low/medium 两档各跑 p50/p95。

### 风险
- 厂商自报的跑分里，竞品数字由 Anthropic 自己测或引用排行榜，**不是 OpenAI 认可的数字**。

### 机制拆解：类比放到 LLM 上成立到什么程度

1. **成立的部分：RLVR 更像「练熟」而不是「变聪明」**
   Yue 等（2025，NeurIPS 2025 oral，arXiv 2504.13837）发现 RLVR 提高了 pass@1，但 k 很大时**基座模型的 pass@k 反而更高**，RLVR 的推理路径基座里本来就有，可解题覆盖面会收窄。这和「练习让你更擅长这个领域，但上限不变」同构。链接：https://arxiv.org/abs/2504.13837
2. **成立的部分：跨域迁移看领域**
   Guru（arXiv 2506.14965）发现数学、代码、科学能从其他领域的 RL 训练中明显受益（可能因为预训练里这些能力已经很充分）；**逻辑、模拟、表格**几乎得不到跨域收益，需要本领域的 RL；难题（如 AIME24、LiveCodeBench、ARC-AGI）的跨域迁移很少。链接：https://arxiv.org/abs/2506.14965
3. **反例：代码数据在预训练阶段会迁移**
   Aryabumi 等（ICLR 2025，arXiv 2408.10914）：相对纯文本预训练，加入代码使自然语言推理**相对提升 8.2%**，在 cooldown 阶段加代码再提升 3.6%。注意这是**预训练数据配比**，和 RLVR 是两回事。链接：https://arxiv.org/abs/2408.10914
4. **反例/修正：迁移效果取决于训练方法**
   Huan 等（arXiv 2507.00432）：**大多数**数学调优模型没有把收益迁移到代码、科学问答、规划、指令遵循；但在 Qwen3-14B 上用同一份数学数据对照，**RL 能保住甚至提升非推理能力，SFT 常造成负迁移**。所以「练数学能不能迁移」取决于怎么练。链接：https://arxiv.org/abs/2507.00432
5. **类比不成立的地方【推断】**
   - 人的 G 被看作受生理限制、相对固定；LLM 的「G」只是权重的函数，**训练本身就能改变它**，「G 练不出来」在 LLM 上没有直接对应物。
   - 人类研究的训练量是几周到几学期的课程；前沿 RL 的计算量和覆盖面是另一个数量级，**剂量不可比**。
   - 人类研究里「积极对照组会让效应缩小」这个教训，在 LLM 上同样适用：判断 RLVR 是否带来外溢，应该和**同等算力的其他训练**（例如其他领域 RL 或 SFT）对比，而不是和未训练的基座对比。
   - 相关指针：10/7 arXiv 精选 #1 *Base Models Can Reason By Taking a Cue From Training Data*（2610.06851，群内核验「能核实」）也在重新审视 RL 收益的来源。本文没有读全文，只放指针。

### 工程落地（6 条）

1. **迁移评测用积极对照**：评估「数学/代码 RLVR 是否带来外溢」时，对照组用同等 token 或同等算力的其他训练，不要只和基座比，以免重复 Scherer 元分析里的对照组偏差。
2. **按领域标注是否迁移**：参考 Guru 的划分，把内部任务分成「跨域能受益」（数学/代码/科学）和「需要本域训练」（逻辑、模拟、表格、开放写作），分别留预算。
3. **区分预训练配比和后训练 RL**：代码数据在预训练阶段的正迁移不能拿来证明 RLVR 有外溢，两者分开报告。
4. **后训练优先 RL，谨慎用 SFT 蒸馏**：Huan 等发现同样的数学数据，SFT 更容易伤害通用能力；做领域强化时监控通用基准有没有退化。
5. **报 pass@k 曲线，不只报 pass@1**：用来判断 RLVR 是在提高采样效率还是在扩大能力边界，对应 Yue 等的发现。
6. **选型启示**：选模型时，不能把「数学和代码榜单很强」直接当成「开放领域也强」，非验证域单独评测。这和 10/7 稿 §2 的「两条预算线」一致。

### 风险
- Chollet 的跟帖没给出处，**「元分析证明不迁移」对编程而言说过头了**，转述时要写成「远迁移弱且有争议」。
- 人类认知类比只能启发思路，不能当证据，LLM 方面要以可复现的消融实验为准。
- 上面引用的 LLM 研究多数基于开源中小模型，能否外推到前沿闭源模型**未知**。
