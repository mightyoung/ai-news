## A. Gemini 4 Carbon：长程 agent、评测与可用性

**帖**：[@OfficialLoganK 2115489284404940898](https://x.com/OfficialLoganK/status/2115489284404940898)（2026-10-28 17:02:03 UTC = **10/29 01:02:03 CST**）｜[@GoogleDeepMind 2115489356437651654](https://x.com/GoogleDeepMind/status/2115489356437651654)（17:02:21 UTC）｜[@ArtificialAnlys 2115494553780367384](https://x.com/ArtificialAnlys/status/2115494553780367384)（17:23:00 UTC = **10/29 01:23:00 CST**）

### 机制 / 定位（长程 agent）

【自报·博客】Carbon 自称「最强 frontier」，核心卖点：**网络安全防御生命周期**（找洞→可利用性验证→打补丁）与 **long-horizon / 持续 agent 工作流**。内部叙述：团队见过 Carbon **跑数日**、跨大代码库与底层系统做根因与补丁；WebDev Arena **+89 Elo → #4（1768）**。对齐侧：Terminal-Bench 4.0 成功作弊 **0.0%**（试图作弊 0.4%）；高严重错位告警约 **-80%**；无支撑断言约 **-2×**；越权 **-26%** / 服务不足 **-29%**；Gray Swan IPI **0.0%** ASR。【自报·内部/合作方数字】安全代码生成成功率相对 Argon **>2×**；Chrome 称高质量补丁相对「另一家大 frontier」**>10×**（未点名对照）。

**Gemini 家族指针**：Argon 两周前已发；Genie 4 里 Omni / 3.8 Flash 在环分工见 **10/28 A**，不重复。

### 幻觉 4%→11%（核实口径）

【第三方·AA】指标在 **AA-Omniscience v1.1**：Knowledge/幻觉基准。Index 对该评测权重 = **准确率 10% + (1−幻觉率) 5%**。Carbon：**准确率 58%**（较 Argon **+10 点**），**幻觉率 4%→11%**，Omniscience 总分 **54**（仍 #1，领先 Opus max 48）。相对 Opus/GPT-6 Astra 的约 **50%** 幻觉率，11% 仍是**第二低**（仅次 Argon）。

【推断】更敢答 → 正确率升、同时错答（幻觉）占比也升；不是「整体更胡言」。【自报·Google】另称内部「无支撑断言」约减半——**与 AA 幻觉率不是同一指标**，勿混写成官方承认幻觉翻倍。

### 可用性 / 模型卡要点

【自报】**尚无面向开发者/消费者的公开产品面**；本周起先给 **Fairwind** 一部分网络防守方，再扩受信伙伴；参与美方自愿预发布测试。AA 图标注 **No publicly available API**。【第三方·AA】上下文 **1M**；输入 text/image/video/speech，输出 text。

### 工程应用清单（防守向）
1. 仅把 Carbon 当**防守侧**评测叙事：补丁质量、安全代码生成、IPI 抗性——勿当公开攻击工具说明书。
2. 选型时并行看：**AA Index**（综合）vs **Coding Agent Index**（harness 敏感）vs 官方单项（GraphWalks/SEC 等）。
3. 报价换算：introductory $2/$10 vs 标准 $4/$20；AA 成本图用标准价。
4. 幻觉：看 Omniscience **准确率+幻觉率双栏**，别只看 11%。
5. 长程「跑数日」仅【自报】轶事，落地需自建超时/检查点/人审闸。

## B. AA Intelligence Index v5 与私有基准之争

**帖**：[@ArtificialAnlys 2115265133467635877](https://x.com/ArtificialAnlys/status/2115265133467635877)（2026-10-28 02:11:22 UTC = **10/28 10:11:22 CST**）｜[@natolambert 2115428494515777629](https://x.com/natolambert/status/2115428494515777629)（13:00:30 UTC = **10/28 21:00:30 CST**）｜[2115437422146130032](https://x.com/natolambert/status/2115437422146130032)（13:35:59 UTC）
**源**：[Announcing AA Intelligence Index v5](https://artificialanalysis.ai/articles/artificial-analysis-intelligence-index-v5)（2026-10-27）｜[methodology](https://artificialanalysis.ai/methodology/intelligence-benchmarking)｜[Artificial Analysis v5 and the benchmarker's dilemma](https://www.interconnects.ai/p/artificial-analysis-v5-and-the-benchmarkers)（2026-10-28）

### v5 结构与「60% 私有」核实

【自报·AA】九项、四大类各 **25%**：
- Knowledge：Briefcase 15 / AutomationBench-AA 5 / GDP.pdf 5  
- Coding：FrontierCode 2.0 **15** / Terminal-Bench 4.0 10  
- Science：Terminal-Bench-Science 15 / CritPt v2 hard **10**  
- General：Omniscience v1.1 **15**（准 10 + 非幻觉 5）/ HLE-Diamond 10  

「**60% 基于 private test sets 或 held-out answers**」【自报】可与权重对齐为：Briefcase(15)+AutomationBench(5)+FrontierCode(15)+CritPt(10)+Omniscience(15)=**60**（公开子集另发 HF，但 Index 用私有/剔除公开污染后的集）。新：FrontierCode 2.0、TB-Science；升级 HLE-Diamond、Omniscience v1.1、CritPt hard；去掉 GDPval-AA、SciCode、AA-LCR。另发 **Progress Index v1**（跨年能力尺）。

### 开闭源差距 3→12【核实】

【自报·AA v5 文】相对 v4.3，开源权重差距由 **3 分扩到 12 分**：当时榜首 Opus 58；Kimi K3.1 Pro（**权重尚未释放**）46；已释权重 DeepSeek V4.1 Flash / GLM-5.3 最高 **32**（落后榜首 26，且低于 Haiku 5.5 的 36）。科学域落差最大（TB-Science、HLE 等）。**注**：Carbon 发售后 AA 榜首变为 Carbon 59，12 分口径以 **v5 发布帖当时榜首**为准；对 Carbon 再算会更大，勿混。

### Lambert 综述要点【第三方】

- 单一 Intelligence Index 难覆盖「锯齿状」用途；编码开源更有竞争力，知识工作更弱。  
- 旧 Index **偏抬开源**；v5 更贴「前沿 agent 协作者」则放大闭源优势——方向可辩，但可能漏掉开源经济引擎（商品化推理、私有化部署）。  
- **私有基准**：减污染、防 benchmax；代价是**无法靠社区找 bug**，信任全集中在评测方；自称对私有/开放 **50/50**。  
- 闭源大厂早已不全围着公开榜转；中小厂仍靠榜面品牌。解法：更多**分域指数**（如 CursorBench / Vals）。  
- AA 商业模式含实验室付费验证——准确与「最公平」之间有张力。

### 选模型 / 自建评测启示
1. **不要只用 AA 总分**：至少拆 Coding Agent / Omniscience / 科学 agent。  
2. **私有集**：采购/合作评测时要求抽样可审计或影子公开子集（AA 已对 Omniscience 放 Public v1.1）。  
3. **自建**：用内部真实工单 + 固定 harness + 版本钉死；公开榜只作校准。  
4. **开源选型**：v5 落差≠「开源无用」——看延迟/成本/可微调/数据驻留。  
5. **Effort 档**：v5 高低 effort 分差加大（Opus low 35 vs max 58）——报价必须绑 effort。

## C. GitHub Copilot Fusion：运行时多模型编排

**帖**：[@ArtificialAnlys 2115477376981508419](https://x.com/ArtificialAnlys/status/2115477376981508419)（2026-10-28 16:14:44 UTC = **10/29 00:14:44 CST**）
**源**：
- [Changelog: Route and orchestrate…](https://github.blog/changelog/2026-10-28-route-and-orchestrate-models-with-github-copilot-fusion/)（2026-10-28）
- [Docs: About Copilot Fusion](https://docs.github.com/en/copilot/concepts/models/copilot-fusion)
- [AA 文](https://artificialanalysis.ai/articles/github-copilot-fusion-orchestrates-anthropic-and-openai-models-to-balance-performance-and-cost)
- Devin 对照：[Devin Fusion](https://cognition.com/blog/devin-fusion)（2026-06-29）｜[local-fusion / Desktop&CLI](https://cognition.com/blog/local-fusion)（2026-09-11）  
旧稿：本系列 **无 Devin Fusion 专条**（10/06 仅顺带提 Devin 为 ChatGPT 登录伙伴）；此处直接对照 Cognition 原文。HydraFusion 研究预览见 GitHub 2026-09 博文，现并入 Fusion GA。

### 路由策略（机制拆解）

【自报·GitHub】Fusion **不是一个模型**，是运行时 **router + orchestrator**（HydraFusion 编排 ∪ Auto model selection）。用户选 **Standard / High / Max** effort，不选手动模型。每请求选：

| 模式 | 行为 |
| --- | --- |
| **Single** | 单模型直接完成 |
| **Cascade** | 便宜模型起草 → judge 接受或升级到更强模型重做 |
| **Critique** | 起草 +（可并行）批评 → 原模型修订 |

还考虑能力信号（推理/codegen/调试/工具）、系统健康与可用性；在**缓存边界**与复杂度跃迁处分段，避免无质量收益的 cache miss。计费按**实际调用的底层模型标价**；付费计划限时 **Fusion 模型费 30% off**。企业可按策略限制 Fusion 可用模型池。AA 观测池含 Opus 5.5、Sonnet 5.5、GPT-6 Astra、GPT-6 Sol 等。

### 数字（近前沿、成本/token 约减半）

【自报·GitHub】Coding Agent Index：Fusion Max **60**，距 Claude Code Opus 5.5 Max 约 **2 分**；约 **一半** API 成本/task、约一半 token、约 **-40%** 时延。【第三方·AA】CLI max：**$5.59**/task vs Opus Claude Code **$11.42**；**7.2M tok**/task ≈ Opus 一半、比 Devin Fusion（Opus max+Luna high）约 **-30%** token；TB4 **71** 领先；FrontierCode **51**（第三，落后 Opus 56 / Devin Fusion 54）；SWE-Atlas-QnA **57** 偏弱。Devin Fusion 同榜：**62 @ $8.00**。

### vs Devin Fusion

| | Copilot Fusion【自报·GH】 | Devin Fusion【自报·Cognition】 |
| --- | --- | --- |
| 结构 | 每请求选 Single/Cascade/Critique；模型池动态 | **双并行 agent**：frontier **lead**（计划/歧义/终审）+ 便宜 **sidekick**（实现/测）；只交换 brief/结果，各自持久缓存上下文 |
| 用户接口 | 对用户呈现单次最终答复 | 用户始终对 lead 对话 |
| 选型 | Effort 三档 | 显式选 lead + sidekick（推荐 Opus 5.5 + GPT-6 Luna） |
| 哲学 | 能单模就单模；必要时才多模 | 「frontier 始终掌舵」，避免一次性路由赌错 |

### 自建 agent 路由落地建议
1. **先分层**：计划/审查 vs 机械实现——Devin 式 lead/sidekick；简单 CRUD 用 Cascade。  
2. **保留终审在强模型**：勿把「一次路由」当地狱难度任务的唯一闸。  
3. **缓存友好**：换模尽量在任务边界；避免整段历史跨模重放。  
4. **自建评测**：同一 harness 比「单 Opus」vs「编排」的 **$/任务、tok、通过率**；勿只报总榜。  
5. **策略层**：企业白名单模型池 + 默认 Standard，复杂任务才 Max。  
6. **观察面板**：记录每步模型与模式（GH 可看进度）；便于审计成本。
