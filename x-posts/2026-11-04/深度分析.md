### 机制拆解（白话）
**1. 证明系统是什么**【自报，博客 Inside the system 和报告第 2 页】
- 类型是 zkSNARK（零知识简洁知识论证）。白话：服务方交一张「数学收据」，你几秒到几十秒就能验完，验的过程学不到权重。
- 搭法是标准配方：先设计一个「交互式预言机证明」（IOP，可以理解成验证方随机抽查、证明方回答的问答协议），再用哈希函数把它压成一个文件（Fiat–Shamir 变换：用哈希代替验证方随机提问）。只用哈希，不用椭圆曲线配对，博客说因此「even post-quantum security」（抗量子）。
- 积木：Reed–Solomon 编码（纠错码，把数据扩成冗余版本）+ 码距离测试（检查一串数据离合法码字够不够近）+ 查找论证（lookup，用查表证明非线性运算，比如激活函数和 softmax）。
- 权重先「承诺」：按行编码、混入随机掩码、算 Merkle 树（层层哈希，根哈希就是公开指纹）。客户端一次性下载约 6.5 MB 的承诺文件（博客；报告写 6.24 MB，可能是 MiB 和 MB 的换算差【推断】）。
- 证明的命题：「承诺的这组权重，在这个提示上，贪心选出的下一个 token 就是这个」。

**2. 开销**【自报】
- 一次性：承诺约 39 分钟（报告表 3：2,323.77 秒）；一份承诺大约能用 1,600 万个请求，之后要重新承诺（博客）。报告表 2 写每份副本最多 688,127 个批次，乘 24 条一批约 1,650 万，两边对得上【推断】。
- 每批：24 条一批约 223 秒，折合 110 prefill token/s；每份证明 18.78 MB。
- 验证方：不用 GPU，24 线程 17 秒，单线程 21 秒；Lean 版验证器要 20 多分钟（报告第 42 页）。
- 对比常规推理：GPU 时间约为 vLLM 的 70–95 倍，不含承诺和服务。
- 为什么能单卡跑：MoE 每个 token 只用约 17B 参数（报告精确值 16.15B），证明的工作量只跟用到的专家成正比，同时仍然隐藏选了哪些专家；权重分段流式读入，一张 80 GB 卡加约 290 GB 主机内存（报告表 8 记最多 278.3 GB）。

**3. 信任假设：你还得信什么**（这是昨天群里没讲的新角度）
- **密码学假设**：安全性在随机预言机模型里证明，也就是把哈希函数当成完全随机的函数来分析【自报】。
- **可靠性（soundness，防伪造）只依赖验证器**。只要验证器写对了，证明方可以完全不信任。Anthropic 给了两个验证器：Lean 写的慢验证器有机器证明，只接受定理里允许的证明；C++ 快验证器「carries no formal guarantee」，只是在他们的测试里和 Lean 版结论一致。日常用的是 C++ 版【自报】。
- **零知识（不泄露权重）只依赖证明器**。证明器太重，没有 Lean 版。博客说这部分要靠服务方自己做 agent 或人工审计【自报】。
- **完备性（诚实证明一定通过）**：靠测试，不是攻击模型【自报】。
- **Lean 定理要人工读**：定理陈述是否表达了想要的意思，得人对着可视化工具审【自报】；Lean 4.29.1 早于修复内核漏洞的 4.32.1（报告第 7 页）。
- **不覆盖的威胁**：侧信道（比如测证明耗时推断权重）不在范围内；不隐藏架构；Hollow-LLM 攻击（声称大模型、实际只做小模型计算）挡不住（报告第 50 页）；证明只说明硬件在做推理，不能说明它没在旁边偷偷训练（博客脚注 2）【自报】。
- **语义缺口**：证明的是「整数模型 + 贪心解码」，浮点推理或采样输出会在某些位置偏离；博客说整数版「generally expected and empirically tested」接近浮点推理，但「does not cover adversarially designed prompts」【自报】。
- 白话总结【推断】：用户不用信服务方，但要信三样东西：①哈希函数够随机；②自己用的验证器写对了（用 C++ 版就是信它和 Lean 版一致）；③被承诺的那个整数模型就是你关心的模型。第③条目前最弱。

### 局限和风险
- 所有数字都是 Anthropic 自报，没有第三方复现；仓库标「Not maintained」【自报】。
- 只支持 MoE 架构、最长 1,024 token 上下文，和真实聊天几十万 token 的上下文差距很大（博客 Limitations）【自报】。
- 论文、代码、测试几乎全由 AI 写、AI 审，作者说没人独立检查（报告第 51 页）。对密码学代码来说，这是最需要外部审计的一点【推断】。
- Anthropic 10-19 起把 RSP 里的目标改名为「inference verification」，说达成目标的是另一个「签名 + 可信服务器重算」的项目，FlashProve 是另一条路线（博客脚注 3）。别把 FlashProve 说成 Anthropic 线上流量已经在用的方案【自报】。

### 应用清单
**马上能用**
- 写安全方案或评审时，把信任边界写清楚：验证器是信任根，证明器决定是否泄露权重。验收：能在一页纸上说明 C++ 验证器和 Lean 验证器各保证什么。
- 读仓库的 `docs/what-is-not-hidden.md`、`docs/limits.md` 和 `lean/STATEMENTS.html`（报告第 2、44、51 页提到），整理「证明了 / 只测试过 / 没覆盖」三栏表。

**需要投入**
- 有 1×H100 80GB、24 核、约 290 GB 内存的机器，按仓库说明跑一轮「承诺 → 证明 → 验证」。验收：证明约 18.7–18.8 MB，C++ 验证器接受。承诺一次约 39 分钟，预计要租半天以上。
- 如果你在做模型网关或路由，可以先把「模型承诺 ID + 证明文件」设计成可选的响应字段，留好接口【推断】。

**观望**
- 生产环境的模型身份认证、合规审计：等支持浮点或采样输出、长上下文、有独立密码学审计之后再说。

### 关键趋势（白话）
1. **「局部 + 全局」注意力混搭成了默认**：大部分层只看附近几百个 token（便宜），每隔几层放一层全局注意力看全文。6 个模型用「滑窗 + 全局」（Kolibri、Muse、Dory、Reflection、Flint、LFM3）；Ling 的 7:1 是「线性注意力 + 全局 MLA」，思路相近【推断，按表计数】。
2. **全局层不加位置编码（NoPE）**：Kolibri、Muse、Reflection、Flint、Mistral 都这么做，常见解释是有利于长上下文外推【推断】。
3. **专家越来越多、越来越细**：384、512 个专家，激活比例 4–10%【自报，按表】。
4. **LatentMoE**：Muse 和 Nemotron 把专家放到更窄的潜空间里算，省计算和通信【自报】。
5. **小模型走混合架构**：LFM3 用短卷积，Dory 用循环复用层，目标是端侧和省显存【推断】。

### 局限和风险
- 帖子和画廊都只讲结构，不讲效果；画廊附带的 Artificial Analysis 分数是第三方评测，不在本次核对范围【第三方】。
- 「上下文长度」有两种口径：宣称值和 config 值（Ling 宣称 1M、config 262,144；Flint config 262,144、支持 512k），引用时要写清是哪一个。
- Muse Spark Open 的 config 读不到，它那一行没能用官方 config 交叉核对。

### 应用清单
**马上能用**
- 选型时先看三个字段：激活参数（决定推理速度）、KV 缓存每 token 大小（决定长上下文显存）、许可（Apache/MIT 最宽松）。画廊的 diff 工具和显存计算器可以直接用。
- 端侧或小卡：LFM3 1.7B（稠密、KV 22 KiB）、Dory 4B 可以先试。

**需要投入**
- 长上下文服务：比较 Ling 3.1 Flash（7:1 线性注意力，KV 10.1 KiB）和 Mistral Large 4（稀疏注意力）在自己数据上的显存和准确率。需要多卡，推理框架要支持对应算子。
- 自己训小模型：参考「滑窗 RoPE + 全局 NoPE + QK-Norm + Sandwich RMSNorm」这套配置做消融实验。

**观望**
- 循环 Transformer（Dory）、LatentMoE：生态和推理框架支持还少，等 Raschka 承诺的深度长文和社区复现。
