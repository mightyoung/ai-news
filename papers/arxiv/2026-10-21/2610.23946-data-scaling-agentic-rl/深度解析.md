## 1. 一句话要点与用处

把智能体 RL 的训练数据拆成三个"数量轴"，再加一个控制变量：
- **任务数** D_T：有多少种不同的任务描述。
- **环境数** D_E：有多少个结构不同的环境实例。
- **轨迹数** D_τ：每个"任务-环境"组合采样多少次。
- 奖励稠密度（稀疏/稠密）作为控制变量。

对每个轴分别拟合幂律，结论是缩放指数排序为 **环境 > 任务 > 轨迹**（Qwen3-8B 数学+代码：0.41 / 0.26 / 0.11），在 21 个设置中都成立。

论文再用这些指数给各种数据合成方法"定价"，推出一个类似 Chinchilla 的预算分配公式。在一个留出点（Qwen3-14B，C=32C0）上，这个公式比"只堆轨迹"高 8.4 个点，作者换算为 **最高 1.7 倍算力效率**。

**用处**：如果你在搭智能体 RL 数据管线，它给出的直接建议是"别把预算主要花在对同一批任务反复 rollout 上，先增加环境（尤其是不同的'世界'：仓库、应用、网站）和任务的多样性"。

## 2. 实际痛点/场景

- 现在的智能体 RL 数据可以分别合成：环境生成器（AWM、GenEnv 等）、任务生成器（AutoPlay、SCA 等）、轨迹生成（自博弈、反复 rollout）。三者成本差别很大。
- 主流做法往往是固定一小批环境和任务，加大 GRPO 的 rollout 数。论文图 1 显示：同样的 token 和 FLOPs，只是分配方式不同，Qwen3-8B 的成功率能差 14 个点。
- 工程问题因此从"再收集多少数据"变成"合成预算该花在哪个轴上"。

## 3. 方案思路与步骤（白话）

1. **定义三个轴**：
   - 任务按句向量余弦距离 > 0.15 去重。
   - 环境以"结构签名"区分，即对工具/API 接口、状态结构、转移语义、校验器接口做哈希。只换随机种子或内容不算新环境。
   - 轨迹数 = 平均每个已覆盖的"任务-环境"格子有多少条 rollout。
2. **测试环境**：
   - 数学+代码（ZeroTIR 式工具调用，测 AIME24/25、MATH500、AMC23）。
   - SWE（SWE-Gym 训练，SWE-bench Verified 评测，训练仓库与评测仓库不重叠）。
   - Web（WebArena-Lite，只做到任务级留出，同样 5 个站点）。
   - UI/工具（AppWorld、ALFWorld）。
   - 搜索域作为稳健性检查。
   - 模型：Qwen3-4B/8B/14B 基座，外加 Llama-3.1-8B、Qwen2.5-7B。
   - 算法：GRPO（默认，组大小 8）和 PPO。
   - 每个配置 1,000 步，3 个随机种子。
3. **度量**：用 L = −log(成功率) 当作"损失"，拟合 L = K·D^(−α) + L∞。
4. **单轴扫描**：另外两个轴固定在 (D_E, D_T, D_τ) = (256, 10,240, 8)，目标轴在 32 倍范围内取 6 个点，扩展检查用 8 个点。论文还检查了训练信号是否被对齐：
   - 扫 D_E、D_T 时，rollout token 数变化 < 4%。
   - 只有扫 D_τ 时 token 数会增加 32 倍。把 token 或 FLOPs 拉平后，α_τ 会降到 0.07–0.08。
5. **交互项**：环境少的时候，加任务几乎没用，"环境多样性是任务多样性起作用的前提"。加入乘性交互项后，拟合 R² 从 0.93 提升到 0.98。
6. **拆分环境轴**：把环境拆成"世界"（不同仓库、应用、网站）和"同一世界内的结构变体"。世界指数 α_W = 0.44，结构指数 α_V = 0.28，后者与任务指数相当。只换种子的"内容变化"指数只有 0.07，相当于安慰剂。
7. **给合成方法定价**：
   - κ（折扣因子）：合成数据相当于多少真实数据。
   - r*（崩塌比例）：合成/真实比例超过多少时，成功率比纯真实数据低 5%。
   - 三个轴的 r* 分别是：环境 ≈ 9.4，任务 ≈ 3.4，轨迹 ≈ 1.4。作者的解释是：环境是可执行代码，每一步都会被解释器校验；轨迹只受模型自身分布约束，最容易"自我强化偏差"。
8. **预算分配**：用线性成本模型加拉格朗日乘子求解，得到 D_E* ∝ C^0.34、D_T* ∝ C^0.27、D_τ* ∝ C^0.13、N* ∝ C^0.26。
   - 留出验证：只用 4B/8B 在 1–8 C0 上拟合，预测 14B 在 32 C0 处的最优配置。
   - 预测成功率 51.7%，实测 51.3%。
   - 同预算下，"只堆轨迹"为 42.9%，"Chinchilla 平分"为 47.3%。

## 4. 如何读实验与识别夸大

- **"1.7 倍"只来自一个数学+代码留出点**：Qwen3-14B、32 C0、3 个种子，对比对象是"只堆轨迹"。对比 Chinchilla 式平分只有约 1.4 倍。小预算（≤ 4 C0）时三种配方相差约 1 个点，"配方选择几乎无关紧要"。
- **作者只承诺指数的"排序"，不承诺数值**：原文写的是 "we claim the ordering of their exponents, not their values"。换用其他模型家族，数值会偏移最多 0.05。
- **环境轴领先并非处处成立**：
  - 用 SWE 的成本系数重新推导时，环境和任务的配方指数变得无法区分（0.28 vs 0.29），作者明确说"不声称 D_E 处处占优"。
  - 环境的优势主要来自"世界多样性"，而世界数只扫了 1–8 个（web 上 1–4 个），只跨了一个数量级。
- **web 只做到任务级留出**，评测与训练用的是同样 5 个站点，泛化含义比 SWE 和 AppWorld 弱。
- **"轨迹最差"有一部分取决于口径**：只有扫 D_τ 时 token 数增长 32 倍。把 token 或 FLOPs 拉平后，α_τ 从 0.11 降到 0.07–0.08，排序不变。
- **我的判断：算力口径看起来有对不上的地方，建议读附录 L/Q 时留意**：
  - C0 被定义为"一次 Qwen3-4B GRPO 跑 1,000 步"，约 2.4×10¹⁸ FLOPs、约 5 个 H100 小时。但默认设置是每步 256 个 prompt × 8 条 rollout、最长 8,192 token，1,000 步就有约 205 万条 rollout。按 6·N·D 粗算，2.4×10¹⁸ FLOPs 对 4B 模型只够处理约 1 亿 token，平均每条 rollout 约 50 token，这与 AIME 级别的工具推理不太相符。
  - 附录 Q 说单轴扫描共约 32,000 GPU 小时（18 格 × 6 点 × 3 种子，约 324 次运行，平均每次约 100 GPU 小时）；附录 D 又说每个格子消耗 0.5–20 GPU 小时。两处不一致。
  - 可能是我理解的口径不同（比如 C0 只计算梯度、"格子"另有含义），**论文未说明清楚**。
- **v2 新增了大量实验**：附录 Q 写明原研究约 48,000 GPU 小时，v2 新增约 13,000 GPU 小时（B–D、G、I、J、L 等附录），总计约 61,000 H100 小时，另有约 3,500 GPU 小时的合成算力和约 2,800 美元 API 费用。
- **README 描述**："环境 > 任务 > 轨迹"与原文一致。"最高省 1.7 倍算力"措辞不够准确：原文是"1.7 倍算力效率"，即达到"只堆轨迹"的成功率只需约 0.6 倍算力，并且只在一个留出点上验证过。

## 5. 落地分层

**今天能试**
- 盘点自己的 RL 数据：有多少个"不同世界"的环境、多少种任务、每格多少条 rollout。如果大部分预算花在加 rollout 上，可以先试着把预算挪到环境和任务上。
- 区分"真新环境"和"换种子"：论文显示只换内容几乎没用（0.07）。
- 合成轨迹要谨慎：合成/真实比例超过约 1.4 就开始崩，合成环境能撑到约 9。

**需要资源**
- 想拟合自己的指数，需要成百上千次 RL 训练。论文总计约 61,000 H100 小时。
- 真实世界（新仓库、新应用）配上可用的 harness 和校验器，成本往往高于论文估计的"约 40 美元/世界"临界线。作者建议用自己的成本重算。

**可跳过**
- 直接照搬 C^0.34 / 0.27 / 0.13 / 0.26 这组数字。作者说数值只适用于他们测量的范围，换硬件、软件栈或数据管线需要重新标定。

## 6. 与已知概念的挂钩

- **Kaplan / Chinchilla 缩放律**：本文把"数据 token 数"这个标量拆成多个轴，给出类似的计算最优配方。
- **ScaleRL、RL 后训练缩放研究**：沿用它们用 −log(成功率) 作为损失的做法。
- **模型崩塌**（用合成数据递归训练导致退化）：r* 是它在智能体 RL 中的"分轴版本"。
- **课程学习、无监督环境设计**（GenEnv 等）：作者说两者互补，本文决定"每个轴分多少预算"，课程学习决定"轴内按什么顺序喂"。
- **GRPO 的组内采样**：增加 D_τ 等价于在同一 prompt 上多采样，主要作用是降低优势估计的方差。

## 7. 疑点、局限与成本

论文自己写的局限（附录 R）：
- 只覆盖开源、非前沿规模的模型，留出验证只做了一个更大规模点。
- 三个轴不完全正交。
- 世界数太少。
- 成功率不能代表智能体质量的全部。
- κ 和 r* 是把合成数据质量压缩成了几个标量。
- 成本模型是线性一阶近似。
- 只覆盖奖励清晰的基准式任务。

我的疑点：
1. 上面提到的 C0 与每次运行 GPU 小时之间的口径不一致，影响对"算力效率"数字的理解。
2. 很多结论的置信区间只来自 3 个种子；κ 和 r* 也依赖具体的生成器、校验器和过滤流程，而这些是作者统一 harness 下的实现。
3. 环境轴的"结构签名"由作者定义，签名库上限只有 384 个。留出验证需要 500 个环境，其中 116 个是"已有签名放到别的世界上"。
4. 成本：完整复现大约需要 6 万张 H100 小时，个人或小团队只能借鉴结论，无法自己重新拟合。
