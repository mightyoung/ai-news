## 1. 一句话先懂它

遇到一道模型偶尔能做对、但没法自动判断答案对错的难题时，这篇让同一个模型分饰两角：一个围绕这道题出一串「小练习题」（自带测试用例，能跑代码判对错），另一个去做这些练习并用强化学习更新。练完再回头做原题。在一组竞赛编程难题上，没有判题器时它比现有方法明显更好。

## 2. 值不值得读：五个 C 速览

**类型**：新方法。**上下文**：接着两条线，一是测试时扩展（test-time scaling：部署时多花算力换效果），如拒绝采样、多数投票 FMV、提示词进化 ACE；二是训练期的非对称自博弈（一个出题、一个做题），如 Absolute Zero、R-Zero。作者把后者搬到「单道目标题」上。**关键假设**：①有一个能执行代码的环境，合成题可以靠执行参考程序得到标准输出；②基座模型对目标题已经有不可忽略的命中率，作者自己划的线是基座 mean@512 大约 0.1 以上（第 9 页）。第二条很关键，作者也承认低于这条线基本无效。**贡献**：一是把「目标题没有判题器」的测试时设置讲清楚，并用七档验证器强度做系统比较；二是 TTSP 方法本身；三是给出它什么时候有效、什么时候无效的边界。**清晰度**：正文清楚，超参在附录 B 列全，但没有代码，也没报算力。建议**看到第 5 节**；如果你在做代码 Agent 的「难题攻坚」模式，值得读原文第 4–5 节。

## 3. 它在解决什么麻烦

部署时想让模型在一道难题上做得更好，常见做法有三种：多采样几次、用判题器挑出对的（拒绝采样）；采样很多次，看哪个答案最常见（多数投票）；或者用执行反馈不断改提示词（如 ACE）。前两种和第三种都依赖一件事：你得能判断一个候选答案对不对。在竞赛编程里，这通常靠测试用例；可现实里，测试用例经常很少、很弱，甚至没有。

在你熟悉的场景里，这种麻烦很常见：代码 Agent 接到一个新需求，仓库里没有现成的单元测试；或者只有题面给的两三个样例，能通过样例的错误程序一大堆。此时多采样几十次也没用，因为你挑不出对的；多数投票只有在「正确答案本来就是最常见的那个」时才管用。

TTSP 换了个思路：既然原题判不了，那就别在原题上拿信号，改在「围绕原题生成的、能判对错的小题」上训练。它像是给模型现场编一套专项练习，练到相关技能变稳，再回去做原题。如果真管用，意味着在弱测试、无测试的场景里，测试时多花的算力终于能转化成正确率，而不是白白多采样。

## 4. 他们怎么做的

**核心思路**：原题没有可靠反馈，但「出题人」可以围绕原题写出带参考程序的合成题，执行参考程序就能得到标准输出，于是每道合成题都有确定的判题器（第 3 页）。出题方被奖励去出「做题方刚好半会半不会」的题，做题方在这些题上用 GRPO（Group Relative Policy Optimization，组相对策略优化：同题采多条回答，按组内得分高低定奖惩）练习，相关能力就会迁移回原题。

**两个角色**（第 4 页）：在同一个冻结的 Qwen3-8B 上挂两个 LoRA 适配器（只训练少量额外参数的轻量微调），一个当出题方，一个当做题方。分开的原因是作者观察到共用一个适配器时梯度互相打架；显存开销接近一个 8B 模型。

**一轮循环**（Algorithm 1，第 4 页；第 5–6 页）：
1. 构造出题提示：放入原题、最近几道合成题和做题方在上面的通过率。
2. 出题方分两步写题：先写解法草稿和 Python 参考程序，再据此重写干净的题面、输入输出格式、样例和保留测试输入；保留测试的标准输出靠执行参考程序得到。
3. 过滤：超时、运行报错、测试全重复、输出恒定的题丢掉，出题方为此吃 −0.5 罚分（Table 7，第 20 页）。
4. 做题批次：16 道新题加 32 道从历史里重放的题，只重放通过率在 [0.1, 0.8] 区间的（太简单没信号，太难全是 0）。每题采 8 条回答，通过全部 10 个保留测试才得 1 分。
5. 出题方奖励：一个三角形函数，做题方通过率在 0.5 时奖励最高，0 或 1 时为 0（式 1，第 6 页）。
6. 两个适配器都用 GRPO 更新，DAPO 式非对称裁剪 (0.20, 0.28)，KL 系数 0，学习率 1e-4，每道目标题训 50 步（Table 6，第 20 页）。
7. 训完用做题方对原题交 8 份答案。

注意：原题的判题器全程不参与训练；但合成题上仍然靠代码执行拿奖励。

**如果让你复现**，骨架大致如下：

```python
proposer, solver = LoRA(base), LoRA(base)          # 共享冻结的 Qwen3-8B
history = []
for step in range(50):                             # 每道目标题 50 步
    new = filter_valid(proposer.write(target, history[-3:]))   # 坏题罚 -0.5
    batch = new[:16] + replay(history, window=(0.1, 0.8), n=32)
    rates = {p: mean(run_tests(solver.sample(p, n=8), p)) for p in batch}
    grpo_update(solver, rewards=pass_fail)          # 合成题上执行判分
    grpo_update(proposer, rewards=[1 - 2*abs(r - 0.5) for r in rates.values()])
    history.update(rates)
answers = solver.sample(target, n=8)               # 原题判题器只用于最后评测
```

## 5. 证据怎么看、别被什么忽悠

**评测口径先讲清**（第 6–7 页）：题目来自 LiveCodeBench v6 的 131 题（2025 年 2–5 月发布，晚于 Qwen3-8B 知识截止），只保留基座 mean@512 在 0 到 0.7 之间的，叫 HardLCBv6。指标 mean@8：每个方法交 8 份答案，先用某档「评测时验证器」筛一遍，再算留下来的答案里有多少真正通过全部公开加私有测试。验证器分七档：v0（全放行，等于没有验证器）、v25/v50/v75（人为校准到能拒掉 25%/50%/75% 的错误答案）、仅公开测试、仅私有测试、公开加私有（即标准答案级）。

**图一：Figure 1（第 1 页），头条结果。** 想证明：验证器越弱，TTSP 相对基线的优势越大。比的是 Qwen3-8B 直接拒绝采样、FMV（按执行行为聚类投票）和 ACE；TTSP 与 ACE 用收敛后的 checkpoint。结果：在 v0 下，图中标注 TTSP 的 mean@8 绝对提升 +0.35，即摘要里的「35% 绝对提升」；作者称每一档验证器下 TTSP 都最好，且曲线大致平坦（第 8 页）。限定：这是 Qwen3-8B 在 HardLCBv6 上、v0 档的结果；HardLCBv6 只有 28 题。

**图二：Figure 6 与 Figure 7（第 9–10 页），什么时候灵、什么时候不灵。** Figure 6 按「正确答案在基座输出里排第几常见」把题分组：正确答案最常见时，FMV 略胜 TTSP；排第二时 FMV 大跌、TTSP 反超；排第三及以后，FMV 基本找不到正确解，TTSP 还保有一定正确率。Figure 7 把 28 题拆成 MidHard（19 题，基座 mean@512 在 0.1–0.7）和 VeryHard（9 题，≤0.1）：前者在弱验证器下增益很大，后者几乎为 0，强验证器下甚至略负。这说明 TTSP 只是把「偶尔会」变成「稳定会」，不能让模型学会它原本完全不会的东西。

**训练动态：Figure 4（第 8 页）。** 大部分提升出现在前 10 步，之后基本平稳；阴影是对目标题做 bootstrap 的 90% 置信区间。

**水分检查**：①样本量：只有 28 道题，而且是按 Qwen3-8B 的表现挑出来的，换模型就要重挑。②种子与误差：置信区间是对题目重抽，训练种子数论文未说明。③算力不对等：TTSP 每题要跑 50 步双角色 RL，而拒绝采样只交 8 份答案；作者在 Figure 3（第 7 页）把基线的采样数加到 512、ACE 迭代到约 60 步，显示弱验证器下基线加算力也涨不上去，这部分回应了质疑，但没有给出等 GPU 时长的对比。④「无验证器」的含义：只是不用目标题的验证器；合成题上仍靠代码执行拿奖励（附录 A，第 17 页），所以它依赖可执行环境。⑤只有一个领域（竞赛编程）、一个基座模型，没有代码可复现。

## 6. 可信度与核验限定

**主张对照**：①「v0 下 mean@8 绝对提升 35%」：Figure 1 与摘要，证据对得上，但样本只有 28 题。②「每一档验证器下都是最优」：Figure 1、第 8 页文字，证据是汇总曲线，逐题看（Figure 5）在强验证器、低覆盖题上拒绝采样会赢。③「失败边界是基座覆盖率」：Figure 7、Table 3–4，证据清楚且作者主动承认。

**核验限定**（原样合入核验报告）：
- +35%（Fig.1 +0.35）：Qwen3-8B，HardLCBv6，v0（不过滤任何候选）下的 mean@8 绝对提升；对比拒绝采样、FMV、ACE（摘要 p1；Fig.1 p1）
- HardLCBv6 只有 28 道 LiveCodeBench v6 题（MidHard 19 + VeryHard 9，Table 3–4 p16），样本小
- 「无验证器」指不用目标题的验证器；TTSP 训练时仍在出题方生成的合成题上用代码执行拿奖励（p17）
- 论文未给代码链接；CC BY 4.0

**打折提醒**：对外不要说「不需要任何验证就能提升 35%」，要说「在 28 道竞赛编程难题上、不用目标题验证器时，mean@8 绝对提升 0.35，训练仍靠合成题的代码执行」。也不要外推到数学证明或开放式写作等无法执行判分的任务。

## 7. 你可以怎么落地

**今天就能试**：不训练，只借它的「出题—做题」思路做诊断。挑一道你的代码 Agent 经常做错的题，让模型先写 3–5 道「解这道题需要用到的子技能」小题，每题附 Python 参考实现，执行参考实现生成测试输出；再让模型做这些小题，统计通过率。验收：如果小题通过率明显落在 0.1–0.8 之间，说明这道题正处在 TTSP 声称有效的「半会」区域，值得进一步投入；如果原题在多次采样里一次都没对过，按论文的边界，这类题别指望它。

**要有数据或机器再试**：需要能跑 8B 模型 LoRA 强化学习的 GPU、vLLM 推理和一个安全的代码沙箱。按 Table 6–7 的设置在你自己的 10–20 道「偶尔能做对」的难题上复刻，每题 50 步，先确认前 10 步就有提升（对应 Figure 4）。验收：在只给公开样例测试的条件下，比对 8 次直接采样后用样例筛选的正确率，并同时盯出题方是否开始出「刷奖励」的怪题（作者在第 10 页提醒的风险）。

**暂时别碰**：别把它用在没有可执行环境的任务上，合成题的判题全靠执行参考程序；也别用在基座几乎从没做对过的题上（mean@512 ≤ 0.1 时增益约为 0，Figure 7）。还要注意它是「每道题单独训一套适配器」，算力不能在题目之间摊销，批量线上请求场景不划算。

## 8. 和你已有知识的挂钩

它很像考前的「针对性刷题」：老师（出题方）根据你要考的那道大题，出一组难度刚好的分解练习，你做完再去考。也像强化学习里的自动课程学习，出题奖励在通过率 0.5 时最高，和「最大化学习进度」的思路一致。和最接近的 TTRL（测试集上用多数投票当伪标签做 RL）相比，最大区别是 TTSP 不从原题的投票里取信号，而是从可执行判分的合成题里取，所以正确答案不是最常见答案时它仍然有效。

## 9. 存疑与代价

**局限**：作者承认每道题单独适配、不能摊销算力；只覆盖「一致性」区间，基座覆盖接近 0 时无效；自博弈信号全部来自自生成内容，出题方可能钻奖励空子，做题方熵可能塌缩（第 10 页）。我读出来的：评测集小且按同一模型挑选；只测了一个模型和一个领域；没有等算力对比。**复现条件**：论文 CC BY 4.0，代码和权重未公开，超参在附录 B 较完整，提示词模板在附录 F。**成本**：每题 50 步，每步 48 道合成题各 8 条回答，再加出题方采样，单题 GPU 时长论文未报告。**出处**：ETH Zurich 与 Tufa Labs 的预印本，未经同行评审。

**论文没回答、但决定你要不要动手的 3 个问题**：单道题要多少 GPU 小时，和「多采样 + 人工看样例」比哪个更便宜？换成更大或更小的模型、换一套难题，+0.35 还剩多少？出题方钻空子时，有没有不依赖原题判题器的早停信号？
