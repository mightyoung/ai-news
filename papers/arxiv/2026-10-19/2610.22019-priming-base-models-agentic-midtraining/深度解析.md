## 1. 一句话要点与用处

在"预训练"和"SFT/RL 后训练"之间加一个**中训练（midtraining）**阶段：用 256K 上下文、几千亿 token 的"真实软件工程数据（整库代码、PR、提交历史、构建日志）+ 少量智能体轨迹"继续训练基座。结果：在**同样的 SFT** 之后，Nemotron 3.5 Lightning（30B-A3B）的 SWE-bench Verified 从 60.7 升到 64.5、Multilingual 55.8→62.8、Pro 32.0→35.5；更大的 Nemotron 3.5 Super（120B-A12B）上 DeepSWE 11.7→15.7、SWE-bench Verified 72.9→74.3。用处：给想训练"编程智能体"基座的团队一份**数据配比 + 消融**的参考；但数据与脚本目前**未放出**（见第 7 节）。

## 2. 实际痛点/场景

- 预训练通常在 4K–8K 上下文，几乎没有智能体交互数据；而软件工程里最有价值的数据（整个仓库、提交演化、PR、构建日志）动辄几万到几十万 token，**预训练放不下、短的长上下文扩展阶段又不够**。
- SFT 数据大多是合成对话，而且作者及其引用的工作都报告：**SFT 太长会削弱之后 RL 的收益**。
- 前沿编码模型（Qwen3-Coder-Next、GLM-5、Kimi-Dev、Composer 2）都有中训练阶段，但技术报告很少讲数据怎么造、怎么过滤、怎么配比、每个选择贡献多少。本文想补上这块。

## 3. 方案思路与步骤（白话）

1. **配比（图 1、表 1）**：约 20% 重放预训练数据（防遗忘）、5% 长上下文数据，其余约 75% 是软件工程数据：Issue–PR 约 41%（2169 亿唯一 token）、整库代码约 20%（1041 亿）、智能体轨迹约 10%（394 亿）、diff 数据约 3%、构建/CI 日志约 1.2%。500B token 的运行里自然数据大约只过 1 遍（0.95–0.97 个 epoch），轨迹约 1.28 遍。
2. **各类数据怎么造**：
   - **Issue–PR**：1210 万个已合并 PR（仓库至少 10 星），把仓库快照、PR 描述、关联 issue、评审讨论、补丁演化拼成序列，让模型"重建提交的修改"；有关联 issue 的用 LLM 评审检查"issue 与补丁是否匹配"（识别 7 类失败模式并修复或丢弃）。
   - **整库代码**：建 14 种语言的 import 图，只保留"至少 20% 文件引用了库内其他文件"的仓库（Ruby 10%），README 放最前、有依赖的文件相邻、打包到 256K，超长库按连通分量切。作者称依赖排序比字母序更能区分强弱模型。
   - **diff 数据**：多文件编辑（给出修改前文件，生成修改后）和"代码演化文档"（初始文件→一串真实提交→最终文件），训练长程状态跟踪。
   - **日志**：LogHub 系统日志、GitHub Actions 日志，加少量"日志窗口+诊断"。
   - **智能体轨迹**：约 39B token（超百万条轨迹、约 50 万个不同问题、3000 万次工具调用），来自 10 多种脚手架（OpenHands、OpenCode、SWE-agent、Codex、Claude Code、Terminus 等），含 Perplexity 作为合作方提供的一部分数据；只训练助手回合（含工具调用），**工具返回内容不进损失**。
3. **训练设置**：256K 上下文，学习率预热后恒定（Lightning 5e-5，Super 1e-5），20% 重放；从 1M 长上下文检查点开始（实验里为简化评测）；成熟流水线里中训练应放在最后的长上下文阶段之前。
4. **评测协议**：不看基座的代理指标，而是"对中训练前后的模型做**相同 SFT** 再比"：短 SFT（33B token）和完整 SFT（100B token）；基准为 SWE-bench Verified/Multilingual/Pro、DeepSWE、Terminal-Bench、BrowseComp 子集；同时记录 LoCoDiff、RepoBench、保留库上的 bits-per-byte 以及通用能力回归检查。

## 4. 如何读实验与识别夸大

**设置**：只用 Nemotron 3.5 两个模型（Lightning、Super）。对照 = 同一基座（无中训练）经**同样 SFT** 的结果。SWE-bench 用 OpenHands、每题 3 次 rollout，Terminal-Bench 用 Terminus-2、每题 8 次，DeepSWE 4 次；温度 1.0、top-p 0.95。全部为作者自测，**无第三方复现**。

| 论文说法 | 我核对到的 |
|---|---|
| "Lightning 经 500B token 中训练：SWE-V 60.7→64.5、Multilingual 55.8→62.8、Pro 32.0→35.5" | 表 3 一致（pass@1）。但**Terminal-Bench 只 +1.0（22.6→23.6）且在 300B 处最高**，论文也写"噪声更大"。pass@k 也都上升（+2.3 到 +4.7）。 |
| 收益来自哪里 | 表 2（100B 早期实验，Lightning-8K 起点）：**去掉轨迹的"仅自然数据"版本在完整 SFT 后 SWE-V 只比基座高不到 1 点，加入轨迹后高 3.0/2.5/6.6（SWE-V/Multilingual/TB）**——也就是多数收益来自约 10% 的智能体轨迹，而不是 PR/整库代码本身。这与"开放的是一份自然数据配方"的印象有出入。 |
| 500B token 有多少是必须的 | 表 3（Lightning，SWE-V pass@1）：0→60.7，100B→64.1，200B→64.3，300B→63.5，500B→64.5。**SWE-V 的绝大部分提升（+3.4 / 共 +3.8）在 100B 就出现了**，300B 反而回落 0.8，说明 500B 的"+3.8"里后 400B 贡献很小，且这些起伏没有重复运行可判断是不是噪声。Multilingual 则随 token 持续上升（100B 57.4、200B 59.7、300B 62.0、500B 62.8），不能一概而论。 |
| "收益在更大的 Super 上也成立" | 表 6：完整 SFT 后，DeepSWE 11.7→15.7、SWE-V 72.9→74.3、BrowseComp 61.8→64.8 提升；但 **SWE-bench Multilingual（−1.1）和 Pro（−2.1）低于基座**，65B 档 SWE-V 反而 72.5 低于 72.9。作者写明"不把它读作一致效应"，但**摘要只挑了 DeepSWE 和 SWE-V**。论文称 Super 上 SWE-V/Pro 的运行间波动约 1 点、DeepSWE 约 2 点，所以 SWE-V +1.4 与噪声同量级，DeepSWE +4.0 约为噪声的两倍。 |
| "Super 短 SFT 后跨脚手架平均 +8.6（SWE-V）、+6.8（TB 2.1）" | 表 7 一致，但这是 **65B token 中训练 + 短 SFT** 的设置，且基座在某些脚手架上很弱（如 Codex 48.4、OpenCode 54.4），"最大增益出现在基座最弱处"。OpenHands 一格在 Super 表里标 "–"（**论文未说明原因**；我的判断：OpenHands 是主表默认脚手架）。论文自己承认**无法区分"脚手架多样性"与"加入轨迹"各自的作用**。 |
| 长上下文 | 表 8（RULER）：只做中训练的 8K 基座在 128K 以内接近长上下文基座，256K 落后 14 点；之后再做长上下文阶段则在 64K–256K 反超。这是**单次运行**。 |
| 基座代理指标 | LoCoDiff 从 0 到 26.8%（精确重建）、RepoBench 70.09→72.41 等随中训练上升；表 5 显示 LoCoDiff 的增益主要来自 diff 数据（1.3%→29.8%，10B token 对照）。但作者明说**这些代理指标和 SFT 后结果"没有可靠相关"**，不能用来选配方。 |
| 种子/统计 | **每个比较都是单次运行**（论文自己在局限里写明），没有置信区间，一两分的差距（尤其 Terminal-Bench）可能只是噪声。SWE-bench Verified 500 题、Multilingual 300 题、Terminal-Bench 仅 89 题，作者自己指出 Terminal-Bench 上"掉了 6 道题"这类变化很小。 |
| 工具返回掩码 | 表 9：训练工具返回内容使 SWE-V 从 37.8 掉到 27.5（"约 10 点"）；用的是"早期版本的 SFT 配方"，且注明"没有开箱即用"，所以**不能推出"预测环境反馈一定有害"**，只能说在他们这套设置里不划算。 |
| 学习率与遗忘 | 表 11（Lightning-8K，100B token）：5e-5 下 MATH-500 从 79.7 掉到 61.7，MMLU 79.4→76.8；Lightning 因"偏向智能体收益"选了 5e-5，所以**通用能力有代价**，而 Super 用 1e-5。论文没给 Lightning 最终模型的完整通用能力回归表（我只看到 Super 的表 10：65B 内无退化，各组在 1.2 点内）。 |
| 与 RL 的关系 | 附录 D：从 Lightning-8K 的 SFT 检查点开始，仅做 **20 步 GRPO、单种子**；中训练模型起点高约 2 点并一直保持，训练奖励高 4.3%。作者明说"20 步测不出 RL 增益，只能说优势在 RL 开始时没丢"。**所以"保留 RL 可训练性"这一动机在本文没有被实证**（只引了别人的结论）。 |
| 缺少的对照 | 作者自己写明：**没有和"把同样的 token 花在更长的预训练或更长的 SFT 上"比较**；只在 Nemotron 模型上测，主要是编码任务。 |

## 5. 落地分层

**今天能试（小成本）**
- 借鉴数据配方思路（用 import 图过滤"真正相互引用的仓库"、按依赖顺序排文件、把 diff/提交演化做成长程状态跟踪任务、只对助手回合算损失并屏蔽 hash/时间戳等噪声）去改你已有的代码继续预训练数据。
- 借鉴评测方法：**用"相同的短 SFT"来比较不同中训练数据**，而不是看困惑度。
- 轨迹数据：用多种脚手架的轨迹而不是单一脚手架（论文引用 Qwen3-Coder-Next 的结论并在 Table 7 中支持"跨脚手架更稳"，但未做因果分离）。

**需要资源**
- 复现：需要 256K 上下文训练基础设施和 500B token 量级算力（论文未给总 GPU 小时；Lightning 500B、Super 280B token）。还需要 1000 万级 GitHub PR、LogHub、数十万条以上的智能体轨迹，以及一个 LLM 评审用于 issue–PR 匹配。
- 完整 SFT 为 100B token，评测要在多个脚手架上跑 SWE-bench、Terminal-Bench 等，成本也不低。

**可跳过/暂缓**
- 想直接获得"NVIDIA 的中训练权重"或"数据"：论文附录写"计划在未来版本发布数据处理脚本和训练集元数据"，**目前文中未给出下载链接**（我也没有在正文里看到代码或权重发布的说明）。
- 非编码领域或非 Nemotron 架构：论文没验证。

## 6. 与已知概念的挂钩

- **持续预训练 / 中训练（Qwen-Coder、Kimi-Dev、GLM-5、daVinci-Dev、Composer 2）**：本文是其中少数给出消融级细节的。
- **重放（replay）防遗忘**：20% 预训练数据重放；论文试了 40% 无明显额外收益。
- **长上下文扩展（RULER）**：中训练在 256K 下进行，顺带承担部分长上下文阶段的作用。
- **SFT→RL 交接 / SFT 过度会降低 RL 可塑性**：本文的动机来源（引用 Liu 等、Kang 等、Zhang 等），自己只做了很短的 RL 验证。
- **pass@k 与 RL 潜力（Yue 等）**：用 pass@k 提升说明"能解的题多了"，而不只是更稳。
- **与本批读过的论文关系**：与《Scaling Discovery Requires Forgetting》等无直接关联；与 Apertus 1.5 同属"公开训练配方"类工作，但 Apertus 公开了权重与数据，而本文目前只公开了描述。

## 7. 疑点、局限与成本

论文自述的局限：智能体基准噪声大、**每个比较都是单次运行**；没有和同 token 预算的更长预训练/SFT 比较；只测了 Nemotron；SFT 用的是偏智能体的 SFT 混合而非完整通用后训练；RL 结果有限（仅 20 步单种子）。

我的疑点：
1. **多数收益来自轨迹**：表 2 里自然数据本身带来的提升很小，"公开配方"的核心价值其实在那 10% 的轨迹，而轨迹语料（约 39B，含 Perplexity 合作数据与 SWE-Zero/Hero）**是否公开论文未说明**；脚本与元数据只承诺"未来版本发布"。
2. **摘要的选择性**：Super 上 Multilingual/Pro 在完整 SFT 后低于基座，而摘要只列 DeepSWE 和 SWE-V；65B 档 SWE-V 也略低。正文有写但摘要未体现。
3. **效应量与噪声同量级**：Terminal-Bench（89 题）、SWE-V 在 Super 上的 +1.4 都在论文自述的波动范围内。
4. **缺少关键对照**：没有"同 token 数更长 SFT / 更长预训练"的对比，因此无法回答"值不值得额外加这个阶段"。
5. **"保护 RL 可训练性"的动机未被验证**（见表 18 与附录 D 的自我限定）。
6. **500B 的必要性存疑**：Lightning 的 SWE-V 在 100B 已到 64.1（500B 为 64.5，300B 为 63.5），且 Lightning 没有给运行间波动（只有 Super 的波动：约 1 点/2 点），所以"500B 带来 +3.8"更准确的说法是"中训练带来约 +3 到 +4，token 数从 100B 加到 500B 的边际收益在 SWE-V 上看不出来"。
6. **通用能力代价**：Lightning 选 5e-5 偏向智能体；Lightning-8K 的实验里 MATH-500 掉到 61.7。最终发布版模型的完整通用能力数据论文里我没看到。
7. **工具返回掩码的结论依赖早期 SFT 配方**，不宜外推。
8. **成本**：Lightning 500B token、Super 280B token，加上 100B token 的完整 SFT 评测；总算力论文未说明。

**未核实项**：Nemotron 3.5 Lightning/Super 的官方技术报告及其数字（论文引用的 NVIDIA 2026a，我没有打开）；论文中引用的 2026 年工作（Qwen3-Coder-Next、GLM-5、Kimi-Dev、DeepSWE、daVinci-Dev 等）的具体数字；"计划发布的数据/脚本"后续是否已发布；附录 B 超参表和 A.4–A.5、E.2 的细节；图中曲线的逐点读数。
