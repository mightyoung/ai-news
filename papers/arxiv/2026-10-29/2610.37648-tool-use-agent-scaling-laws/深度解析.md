## 1. 一句话要点与用处

**做法**：用 LLM（Gemini-3.1 Pro）从零生成 64 个带数据库的 Python app，再在上面生成任务、校验器和标准解，得到 SynthAPI。生成时可以单独调四个旋钮：
- A：app 数
- T：每个 app 的任务数
- S：每条指令配几个初始数据库
- D：干扰数据量

然后用 GLM-5.2 采专家轨迹，蒸馏到 Qwen3.5 的 2B/4B/9B/27B 四种规模，共训练 849 个模型，再拟合一个"带数据组成"的缩放律。

**用处**：做 agent SFT 数据时，预算变大以后，应该把预算投到更多工具、更多数据库实例和更复杂的数据上，而不是同一批工具上堆更多任务。

## 2. 实际痛点/场景

- 用 LLM 模拟工具返回的合成数据（Nemotron-Agentic、SimSAT 一类），很难真实地模拟状态变化。
- 以往"可执行环境"类工作主要追求数量，没有回答"数据里哪种多样性最值钱"。

## 3. 方案思路与步骤

1. **建 app**：先生成元数据和功能列表，再生成 db.py（数据类）和 apis.py（只允许 CRUD 访问数据库）。最终 64 个 app，共 10,472 个 API（p5、p19）。
2. **生成任务**：每个任务包括指令 x、校验器 v、初始库 Db0 和标准解 π*。只保留满足 v(Db0)=0 且执行 π* 后 v=1 的任务。
3. **交互接口**：agent 写 Python 代码块，通过 list_apps / list_tools / get_tool_documentation 这几个元工具查工具，上限 32 步。所有任务都只涉及单个 app。
4. **训练**：GLM-5.2 每题最多尝试 4 次，保留第一次成功的轨迹。用 SFT 训练 1 个 epoch，按验证损失早停。全部数据共 5.9B token，其中 721M 是受监督的输出 token（p6）。
5. **缩放律**：式 4.2 的形式是 P̂ = σ(c0 + cA·log2(A·S·D)) · σ(b0 + bT·log2 T)^ν。按 6ML 估算 FLOPs，留出训练 FLOPs 最高的 25% 的运行做外推检验（p8）。

## 4. 如何读实验与识别夸大

**头条数字与设置**

- **外推误差**：在留出的高 FLOPs 区，式 4.2 的 MAE 是 0.0285，只看数据量的律是 0.1706（p2、p8）。
  - 指标是"归一化分数"：只在诊断集（AppWorld + 自建 Holdout）上算，并且用 849 个模型里观测到的最好成绩做上限归一化（p7）。
  - 图 3 画的是每个 FLOP 档的最优点。按规模拆开的外推 MAE：2B 0.004、4B 0.051、9B 0.026、27B 0.028（p21）。
  - "16 倍外推"是作者对留出区间的描述（p8）。
- **同预算配方对比**（表 1，p7）：
  - 都是 32,768 个任务：SubOpt 取 A=32、T=1024、S=1、D=2；Opt 取 A=64、T=128、S=4、D=4。
  - Opt 在 3 种规模 × 4 个基准的 12 格里全部更高，但有的格差距很小，例如 27B 的 AppWorld Test-C 是 73.8 → 74.1。
  - 27B 的 ASTRA-Bench 上，SubOpt 77.3 和 Opt 79.3 都低于零样本的 80.2，只有 Big（82.3）超过零样本。
- **对 Nemotron-Agentic**：只在 4B 和 9B 上做了，27B 没有 Nemotron 这一行。
  - "平均高 30.5 个点"是 SynthAPI-Big 对 Nemotron、在 AppWorld/ASTRA/BFCL 三个基准两种规模上的平均。我按表 1 复算，结果是 30.5，与论文一致。
  - 但 Big 用的是全部 458,752 个任务训练 4 个 epoch，节点数翻倍、算力约为 2 倍（p9、p21），数据量和训练量都不对等。
  - Nemotron 一行用的是 Nemotron-Agentic 全量数据（p9；该数据集约 335k 条轨迹，p3），数据量也和 Opt 的 32,768 个任务不同。
  - p9 原文说 Nemotron "even underperforms the zero-shot starting model in 5 of the 8 settings"。我按表 1（p7）复核，4B/9B × 四个基准的 8 个设置中，低于零样本的是：9B AppWorld Test-C（20.8 对 26.4）、4B ASTRA（54.4 对 57.4）、9B ASTRA（67.7 对 71.8）、4B BFCL（15.9 对 27.3）、9B Holdout（0.5 对 1.5），共 5 个，与原文一致。
- **对单基准的已有方法**（表 2，p9）：
  - AppWorld Test-C 上，Big 比 SimSAT 高 7.6 个点（4B）和 11.6 个点（9B）。
  - BFCL 上，Big 比最强基线高 2.0 个点（4B，对 EnvFactory）和 3.7 个点（8B，对 EnvScaler）。BFCL 这组实验另外在 Qwen3 上训练。
  - 基线数字都取自原论文，作者自己也承认训练方式不同（对方是 SFT+RL、数据更少），所以这组比较不能说明合成方法本身更好，也不能说明数据效率更高（p9）。

**群聊说法核对**

1. **作者是 Szot、Abnar、Toshev 等 8 人**：成立（p1，与 arXiv 一致）。
2. **458,752 个任务、849 个模型、4 种规模**：成立（p1、p5–6）。
3. **"多样性比任务数更有效"**：部分成立。前提是数据预算较大，且只在诊断集上测量。
   - 9B 上，A=8 在 64–512 个任务时最好，A=64 从 4096 个任务起才明显最好（p7）。
   - S 的规律相同：32–512 时 S=1 最好，512–4096 时 S=2 最好，4096 以上 S=4 最好（p8）。
   - 预算小的时候结论反过来。
4. **在四个基准上超过以往数据**：部分成立。
   - 对 Nemotron-Agentic，Opt 和 Big 在 4B、9B 的四个基准上都更高（表 1）。但四个基准里有一个是自建的 Holdout，27B 没有和 Nemotron 比。
   - 对其他已有方法，只比了 AppWorld 和 BFCL 两个基准，用的还是引用数字。

## 5. 落地分层

- **今天能试**：在做 agent SFT 数据时，固定预算下优先增加 app 和工具种类，给同一条指令配多份初始数据库，并加入干扰数据。这个思路不需要 SynthAPI 本身。
- **需要资源**：
  - 完整复现：生成环境需要 Gemini-3.1 Pro，专家采样需要 GLM-5.2，训练用 8×B200 节点；仅诊断集评测就要 180 万个 episode（p7）。
  - 代码和数据都没有公开。
- **可跳过**：需要和用户交互、或需要长文档检索的场景，作者明确说没有覆盖（p10）。

## 6. 与已知概念的挂钩

- Chinchilla 式的 6ND 算力估算和"固定预算怎么分配"问题，在这里从"参数 vs token"换成了"工具 vs 任务 vs 数据库"。
- 生成 app 的做法与 AppWorld 的环境设计、Agent World Model / EnvScaler 的可执行环境合成属于同一路线。
- 蒸馏专家轨迹属于拒绝采样式 SFT。

## 7. 疑点、局限与成本

- **无法估计训练方差**：每个配置只训练一次，没有种子和置信区间，有的格子差距只有零点几个点。
- **归一化有循环**：归一化分数的上限取自同一批模型里的最好成绩，而且诊断集包含作者自建的 Holdout。
- **27B 的结果不太好看**：ASTRA 上 SubOpt 和 Opt 都低于零样本；27B 拟合出的 ν=0.05、b0=−9.96（表 3，p21），形状和其他规模差别很大。
- **只验证了一条数据管线**（p10）。附录 E.3 在 SimSAT 上复现了"app 数分配"的趋势，但只覆盖 N≤1024、只看 AppWorld Test-C。
- **D=4 的大幅提升可能部分来自下游基准对数据库难度不敏感**，作者自己也提到了这一点（p8）。
