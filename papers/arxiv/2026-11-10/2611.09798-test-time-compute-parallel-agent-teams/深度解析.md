## 1. 一句话先懂它

同样请 100 个 AI 助手干一件能自动打分的长活，与其让 100 个各干各的再挑最好，或者让 100 个挤在一个大群里协作，不如分成 10 个十人小组，组内共享一个留言板，组间互不往来，最后挑最好的那组。这篇用实验和一个简单的统计账说明了为什么这样更划算。

## 2. 值不值得读：五个 C 速览

**类型**：测量分析，附带一个很简单的方法（并行小团队）和一个解释模型。**上下文**：接着两条线，一是 best-of-N（采 N 个、用评分器挑最好）的测试时扩展，如 Large Language Monkeys、Snell 等人的算力最优分配；二是多智能体协作，如 MetaGPT、ChatDev、上千个智能体的 MacNet。**关键假设**：任务有自动评分器，每次尝试都能打分，且只看最好的那个结果；这在 GPU 内核优化、形式化证明这类任务里成立，在没法自动判分的任务里不成立。**贡献**：①在 12 个长任务上系统比较「单兵并行、一个大团队、并行小团队」三种花法；②用「均值加方差收益」的统计模型解释为什么两头都输；③给出「贵的方法值不值」的判断公式。**清晰度**：正文短而清楚，实验细节、成本口径和提示词都在附录。建议**看到第 5 节**；如果你在跑多 Agent 并行任务，值得读原文第 3–4 节和附录 J。

## 3. 它在解决什么麻烦

想让一个固定模型在难题上表现更好，最常见的做法是多跑几次、挑最好的（best-of-N）。问题是它很快到顶：论文里 50 个单兵就已拿到 100 个单兵收益的 81% 到 100%（第 2 页）。另一种做法是把很多 Agent 组成一个大团队一起干，但团队越大不一定越好，大家容易收敛到同一个方案，多样性丢了。

你在用 Claude Code 或 opencode 时可能已经遇到过：一道难的性能优化或证明题，开五个窗口各跑一遍，结果差不多；再开五个也只是多几份差不多的答案。反过来，如果让它们共享一个笔记文件互相参考，前期进步快，但很快所有人都在抄同一个思路。在需要长时间探索的任务里（一次 12 小时），这两种浪费都很贵。

论文要回答的是：同样一笔「Agent 数量 × 时长」的预算，怎么切分最划算。如果答案是「中等规模的小组、多组并行」，那么你在调度并行 Agent 时就有了一个简单的默认配置，而且能用几次试跑的均值和标准差，提前算出加预算还值不值。

## 4. 他们怎么做的

**核心思路**：把每次「采样」看成一个随机分数。很多个样本里取最好，期望值约等于「单个样本的均值」加上「标准差 × 一个随样本数缓慢增长的系数」（第 5–6 页，式 2）。单兵的样本多，方差收益吃得足，但均值低；一个大团队均值高，但只有一个样本，方差收益为 0；小团队均值明显高于单兵，又还能凑出好几个样本，两头都占一点。

**三种花法**（第 3 页）：预算记为 B 个 Agent，每个跑同样的固定时长。团队规模为 k 时，预算能买 B/k 个团队；k=1 就是并行单兵，k=B 就是一个大团队，中间就是并行小团队，默认 k=10。

**团队怎么协作**（第 3 页，附录 E 第 18–19 页）：扁平团队，没有角色、没有经理、不分配任务。每个 Agent 有自己的沙箱和上下文，共享一个论坛，只能做三件事：发带标题的帖子、看标题索引（未读的有标记）、读一篇全文。提示词里只多一段说明，鼓励发清楚的成功和失败、附上具体改动和分数，读写全凭自愿。团队得分取所有成员里最好的一次有效提交。

**实验设置**（第 3 页、第 18 页）：12 个长时优化任务，来自 EdgeBench、MLS-Bench、ExploitBench、KernelBench、KernelBench-Verified、TopOpt，覆盖 GPU 内核、Lean 形式化证明、地球物理反演等；每个 Agent 在 Codex 命令行工具里跑 12 小时（Browser Exploit 为 6 小时）。主模型 Qwen3.8-27B，自己用 H200 部署；每个任务约 100 次独立单兵运行加 10 个十人团队。全研究超过 8,000 次 Agent 运行、约 95,000 Agent 小时。

**怎么估计「N 个里取最好」**（第 3 页）：不需要真的跑 N 次再挑，而是从一池 L 次运行里枚举所有 N 个的子集求平均最好分，有闭式公式。论文的例子：5 次运行得分 2、4、5、7、9，1 次的期望最好是 5.4，2 次是 7.1，5 次是 9。

**如果让你复现**，骨架大致如下：

```python
B, k = 100, 10                                  # 总预算 100 个 Agent，十人一组
teams = []
for t in range(B // k):                         # 组间完全独立
    forum = Forum()                             # 每组一个共享留言板
    runs = [Agent(task, forum, hours=12) for _ in range(k)]
    teams.append(max(r.best_verified_score() for r in runs))
result = max(teams)                             # 评分器挑最好的一组
# 预估：expected_best = mu + sigma * a(N)，用少量试跑估 mu、sigma 再决定 k
```

论坛服务、沙箱和评分器的具体实现论文只给了接口说明（附录 E、K），代码仓库当前打不开。

## 5. 证据怎么看、别被什么忽悠

**图一：Figure 2（第 2 页）和 Table 4（第 20 页），并行小团队对并行单兵。** 想证明：同等 Agent 预算下，十人小组取最好胜过单兵取最好。比法：Qwen3.8-27B，每个 Agent 12 小时，横轴是总 Agent 数，纵轴是期望最好分。结果：100 个 Agent 时，10 个十人队在 12 个任务中 10 个胜出；12 个任务平均，10 个 Agent 预算时高 10%，100 个时高 27%（第 2、4 页）。最大的差距在单兵很少成功的任务上：Carleson Formalization（Lean 证明）里 100 个单兵最好 19.0 分，10 个团队最好 54.8 分（Table 4）。单兵只在 Kimi-Linear Decode 和 Active Learning 上赢，后者差距很小。限定：团队池每个任务只有 10–11 次运行（第 10 页），100 个 Agent 预算下的「10 个团队取最好」基本就是整个池子的最大值。

**图二：Figure 1b 和 Figure 4（第 1、5 页），一个大团队行不行。** 想证明：团队不是越大越好。结果：在跑了大团队的 4 个任务上，团队规模从 64 加到 100 时分数全部下降；100 个 Agent 时，10 个十人队比一个百人队高 8% 到 30%，且有 2 个任务上百人队还不如 100 个单兵取最好（第 4 页）。Figure 4 固定 100 个 Agent 改团队规模，最优规模都在中间。限定：大团队每种规模只跑了 1–5 次，而且 64 人和 100 人的论坛索引只显示最新 100 个标题和未读帖（第 18 页），设置本身就和小团队不同。

**图三：Figure 5（第 5 页），和前沿闭源模型比钱。** 按 GPU 时间给 Qwen3.8-27B 定价（每次 Agent 运行 $18.16），GPT-5.6-sol 按 token 定价。在至少有 5 次 GPT-5.6-sol 运行的 8 个任务里，同价位下 Qwen 团队胜 4 个（第 5 页）。换成按 token 给 Qwen 定价，变成 8 个里胜 6 个（第 26 页）。说明这个结论对定价口径很敏感。

**统计模型验证**（Table 2，第 7 页）：所有 12 个任务上，十人队的均值都比单兵高 0.5 到 4.4 个标准差；但模型只在 9/12 个任务上预测对了增益的正负号，分数偏离正态（大量失败、触顶）时预测不准，作者自己说它在这些情况下只是定性的（第 10 页）。

**水分检查**：①没有误差条，团队样本小；②算力按「Agent × 小时」对齐，但团队成员读帖会多用 token（成员 token 用量是单兵的 1.0 到 2.2 倍，第 26 页），按 GPU 份额计费时这部分被抹平；③只用了一种 Agent 外壳（Codex 命令行工具）；④任务都有连续分数和自动评分器；⑤换成更强的 DeepSeek V4.1 Flash 后，团队在对它来说容易的任务上优势变小（Figure 9，第 8 页）；⑥「最后挑最好的一组」依赖评分器，没有评分器时挑选本身就是问题（第 10 页）。

## 6. 可信度与核验限定

**主张对照**：①「100 个 Agent 预算下 10/12 胜过并行单兵」：Figure 2、Table 4，证据对得上，但团队池每任务只有 10–11 次。②「4/4 胜过百人大团队」：Figure 1b、第 4 页，样本很小。③「同价胜过前沿模型一半任务」：Figure 5，结论依赖定价口径。④「统计模型解释了原因」：Table 2，机制方向一致，定量预测只在接近正态时准。

**核验限定**（原样合入核验报告）：
- 10/12 胜出：Qwen3.8-27B、100 个 agent 预算，十个十人队取最好 vs 100 个独立 agent 取最好，12 个带自动评分器的长任务（GPU 内核、形式化证明等），每任务约 100 次独立运行（摘要 p1；Fig.2 p2；Table 4 p20）
- 4/4 胜过 100 人大团队（领先 8%–30%）：只在 4 个任务上做了大团队对照，每种规模 1–5 次运行，样本很小（p4、p10、p18）
- 论文给的代码仓库 github.com/modal-projects/parallel-agent-teams-scaling 在 2026-11-10 查询为 404，暂时无法复现

**打折提醒**：对外别说「小团队永远比大团队好」，要说「在 4 个任务、每种规模 1–5 次运行里，十个十人队胜过一个百人队」。「27B 模型同价打赢前沿模型」要附上「8 个任务中 4 个，按 GPU 时间计价」。

## 7. 你可以怎么落地

**今天就能试**：不跑新实验，先算账。把你某个能自动打分的任务过去 5–10 次独立运行的分数拿出来，按第 3 页的子集平均法算出「N 次取最好」的期望曲线（例子：2、4、5、7、9 五次，1 次期望 5.4、2 次 7.1）。再估均值和标准差，看曲线是否已经变平。验收：如果再加一倍运行次数，期望最好分的提升小于你能接受的阈值，说明单纯多开窗口已经不值，该考虑「让每次尝试更好」（比如组队共享笔记），而不是继续加量。

**要有数据或机器再试**：前提是一个带自动评分器的长任务和能同时跑 10–20 个 Agent 的环境（沙箱加一个共享的笔记或论坛文件）。分两步：先用 2 组、每组 5 人，和 10 个单兵各跑一轮，对比「一组」与「同人数单兵取最好」（附录 F 显示 65 个任务与规模组合中 48 个团队更好，第 19 页）；再按 Table 2 的做法估两种方式的均值和标准差，用论文的判断式决定团队规模。验收：同样的 Agent 小时下，最好分提高且多跑几轮仍然成立。

**暂时别碰**：别搞「经理分活」的编排式团队，论文里它在 3 个任务上都不如扁平团队和单兵（Figure 10，第 9 页）。别直接上几十到上百人的大群，证据显示规模过大后反而下降。也别把「同价打赢前沿模型」当成采购依据，它强烈依赖定价口径。

## 8. 和你已有知识的挂钩

它像组织管理里的「多个小项目组并行做方案，最后评审挑一个」：组内沟通让质量上去，组间隔离保住了思路多样性。从统计上看，它就是投资组合的道理：期望最好分等于均值加上「方差 × 样本数带来的收益」。和最接近的 best-of-N 相比，最大区别是它不再把每个样本当成一个独立 Agent，而是把一个小团队当成一个样本，用协作抬高每个样本的均值。

## 9. 存疑与代价

**局限**：作者承认统计模型在大量失败或触顶时只是定性的；团队池每任务只有 10–11 次；大团队只在 4 个任务上跑 1–5 次；只用一种 Agent 外壳，长会话只在一个任务上测；没有评分器时「挑最好的团队」本身是难题（第 10 页）。我读出来的：12 个任务都有连续分数，换成只报成败的任务未测；「6 小时 Agent」其实是 12 小时运行在第 6 小时的截面（第 20 页）。**复现条件**：论文 CC BY 4.0；代码仓库当前 404；提示词全文在附录 K，论坛接口在附录 E。**成本**：全研究超过 8,000 次运行、约 95,000 Agent 小时；一个百人团队在 KDA Chunk Forward 上要同时占 100 个沙箱、100 张 H100 评分卡和 40 张 H200，持续 12 小时（第 18 页）。**出处**：Duke、Modal Labs、Princeton、NYU 的预印本，未经同行评审。

**论文没回答、但决定你要不要动手的 3 个问题**：在只报成败、没有连续分数的任务上，小团队还有优势吗？换成 Claude Code 等其他 Agent 外壳，最优团队规模会变吗？没有可靠评分器时，怎么从多个团队里挑出最好的结果？
