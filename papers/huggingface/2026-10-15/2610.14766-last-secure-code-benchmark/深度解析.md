## 一句话总结

LSCBench 用 150 个真实漏洞场景（共 450 个任务）测「vibe coding」下编码 agent 写出的代码是否安全：六个前沿 agent 的功能通过率为 73.6%–91.3%，但「既能用又安全」最高只有 25.1%。

## 研究问题与动机

AI 编码 agent 已写出大量上线代码，而用户通常只看功能是否可用，很少审查代码。一个文档导入功能可以正常处理普通压缩包，却让精心构造的压缩包写到目录之外，功能测试发现不了。已有安全代码生成基准在代码生成范围、语言覆盖或漏洞类别上至少有一项不足。论文要回答：在用户完全不提安全的情况下，agent 能否在各种 vibe-coding 范围内稳定写出安全代码。

## 核心方法（基准构建）

- **场景与任务**：150 个真实漏洞场景，每个场景切成三个粒度——Function（补全被遮蔽的函数）、File（实现含漏洞的源文件）、Repository（从零重建声明的源码树）——共 450 个任务；覆盖 Java、C、C++、JavaScript、Python、PHP、Go 七种语言，24 类 CWE（含 2025 年 CWE Top 25 中的 21 个、Top 10 KEV 中的 8 个）。
- **来源**：C/C++/Python/JS/Go/PHP 场景来自 CVE-Factory；Java 在其中不足 5%，所以由 5 位至少 3 年经验的安全专家根据所在公司代码库手工构造了 100 个 Java 应用场景。
- **规格只谈功能、不提安全**；评测用隐藏的功能测试与安全测试，安全测试是对运行中的程序重放 PoC 攻击，并在漏洞版与修复版代码上都做验证（比静态分析或 LLM 评审更依赖真实行为）。
- **构建三阶段**：建环境；用 Qwen3.8-Max（在看不到参考补丁的情况下）起草三种粒度的规格；再由「可见修复」的评审 agent 与五位安全专家修订，并用参考解和空解做门控，保证任务可执行且「无法作弊」。

## 实验设置与主要结果

- **被测对象**：Claude Fable 5、GPT-5.6-Sol、GLM-5.3、Qwen3.8-Max、DeepSeek-V4-Pro、Kimi-K3。其中五个跑在 Claude Code（v2.1.143），GPT-5.6-Sol 跑在原生 Codex（v0.154.0）；上限 500 回合、禁网络、最高推理强度；用 Harbor 的独立 verifier 模式评分；指标为 FuncPass、SecPass、Func∧Sec，均为 pass@1。
- **核心结果**：功能通过率 73.6%–91.3%（五个模型约 90%，仅 DeepSeek-V4-Pro 明显落后）；Func∧Sec 最好的 Claude Fable 5 为 25.1%，其余为 16.4%–24.7%；在同一漏洞的三个粒度上都安全的场景，最好也只有约 12%。
- **互补性**：六个模型合并后至少一个能做到安全的任务有 198/450（44.0%），单模型最好为 113（25.1%）；六个模型都安全的仅 19 个、恰好一个模型安全的 62 个；252 个任务（56.0%）与 57 个场景在所有粒度上无任何模型做到安全。
- **粒度**：范围越大功能完成率越低，但安全并不随之下降（Func∧Sec 对 GPT-5.6-Sol 等模型持平或上升，GPT-5.6-Sol 的 Repo 任务近三分之一安全）。
- **回合数**：更多回合不买来安全；回合最少的 Claude Fable 5 安全最多，Qwen3.8-Max、GLM-5.3、Kimi-K3 回合约为其两倍却更低。
- **漏洞类型**：内存安全最容易做到（边界、空指针、生命周期检查属于局部检查），其次是注入和路径处理（OS 命令注入约三分之一能避免，代码注入几乎都避免不了）；信息暴露与 SSRF 这类依赖未说明的策略的几乎没有模型能做到。语言上 C、Python、JavaScript 约 27%–30%，Java、Go、PHP 约 10%–18%，论文指出这很大程度来自各语言场景的漏洞类型构成。
- **失败模式**：安全专家审计了每个模型各 20 条失败轨迹（共 120 条）：Kimi-K3 把功能契约当作全部，自己的测试暴露异常时还会说服自己「测试太严」；GPT-5.6-Sol 常凭记忆复现上游实现连漏洞一起带上；DeepSeek-V4-Pro 防御基础差；GLM-5.3 在规格含糊时默认放行；Qwen3.8-Max 先写后跑，失败多为死锁、正则回溯等执行问题。
- **安全提醒实验**：对四个模型在 450 个任务上追加一句「要安全、无漏洞」，除 DeepSeek-V4-Pro 外 Func∧Sec 提升 15–21 个点，但多数任务仍不安全；反序列化、路径处理、内存安全约 50%，信息暴露与 SSRF 仍垫底。

## 局限与风险（据正文整理）

- Qwen3.8-Max 既参与撰写测试与规格又是被测模型，论文称其成绩居中，看不出受益，但这仍是构建上的利益相关点；
- 全部为 pass@1、单次尝试；安全测试按场景内的 PoC 判定，只覆盖已知漏洞；
- Java 场景是 5 位专家手工构造的；任务规格故意不提安全，结论针对「用户不提安全」的情形；
- 提醒实验只测了 4 个模型；Claude Fable 5 有部分尝试因内容安全拒绝而失败；
- 若某次尝试什么都没实现，安全测试也会通过，所以论文以 Func∧Sec 作为头条指标。

## 工程落地启示

- 不要把「测试通过」当作可上线的信号：agent 代码需要独立的安全审查或安全测试，尤其是授权、信息暴露、SSRF 这类「策略型」缺陷。
- 论文的数据支持「多模型交叉评审或集成」：单个最好模型只覆盖 25.1%，六模型合并为 44.0%。
- 在提示里加一句安全提醒是便宜的第一步（+15–21 点），但远不够；更有效的方向是论文建议的「实现→自写安全测试验证→修补」的端到端训练或流程。
- 值不值得复现/使用：想评估自家编码 agent 或模型的安全性，值得直接采用其任务与 Harbor 验证流程；构建 cookbook（门控、对照运行）也可借鉴到企业内部基准，尤其是用自家漏洞做私有评测以避免数据泄漏。

## 与相关工作的关系

- 功能类基准（HumanEval、MBPP、APPS、SWE-bench、NL2Repo-Bench）不问安全；早期研究发现约 40% 与安全相关的补全含漏洞。
- 片段级安全基准（SecurityEval、CodeLMSec、SALLM、CWEval、SeCodePLT、CODEGUARD+、SafeGenBench）局限于单个代码片段；仓库级的 BaxBench、A.S.E、SecureAgentBench、SUSVIBES 与之更近。LSCBench 的区别是同时覆盖七种语言、更多关键 CWE 和三种粒度（论文 Table 1 对比）。
- CyberGym、ExploitGym 关注 agent 能否复现漏洞或写利用，是攻击侧；LSCBench 关注防御侧「写出安全代码」。
