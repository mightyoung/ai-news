# 面向智能体的缓存工程（Cache Engineering）

- 英文标题：Cache Engineering for Agents
- arXiv：[2610.28577](https://arxiv.org/abs/2610.28577) · HF：[papers/2610.28577](https://huggingface.co/papers/2610.28577)
- HF 点赞：113（抓取于 2026-10-23 09:00 北京时间）
- 署名机构：Tsinghua University、The Chinese University of Hong Kong（HF 组织页为 Tsinghua-NICS-EFC）
- 代码：[github.com/thu-nics/AKV](https://github.com/thu-nics/AKV)

## 一句话总结
与其像「上下文工程」那样删改或总结历史文本（导致保留部分必须重新 prefill），不如让智能体直接操作 KV 缓存：用 drop 让部分缓存不再参与注意力、用 repos 重排位置编码；配套服务引擎 AKV 解决了这种操作带来的「同样 token 前缀、不同缓存状态」问题，在多个 agent 基准上同时提分和降本。

## 研究问题与动机
长程智能体动辄几百轮，KV 缓存的读取与存储成为主要成本（作者统计 KV 缓存读取占 API 总成本的 82.4%），同时注意力的 token 数或位置范围超出模型可靠处理范围时准确率会下降。现有做法是在达到阈值后裁剪或总结历史，但改动前缀会让后续缓存全部失效、触发重新 prefill；为了控制成本只能延迟、并一次性大幅压缩，又会丢信息。作者在 GPT-OSS-120B、BrowseComp-Plus 前 100 题上的测试表明：保留最近 12 轮工具结果的裁剪法成本是全上下文的 1.85 倍；48K 阈值总结法成本约降 7% 但准确率掉 5 个百分点；直接丢弃旧工具结果的缓存则能同时提准确率、降成本。

## 核心方法
- **三种缓存操作**：append（常规追加）、drop（把指定 token 的 KV 排除在后续注意力之外，不改文本轨迹和保留部分的位置编码）、repos（用 RoPE 旋转把保留的 key 重新编号为 0…r−1，值不变，无需重算）。
- **历史依赖**：同样的 token 与保留位置，在不同 drop/append 顺序下缓存状态不同（被保留的 KV 当初计算时可能看过已丢弃的内容），因此普通前缀匹配无法正确复用。
- **AKV 服务引擎**（基于 SGLang）：对外是无状态接口，在标准 messages 之外加一个 cache 字段描述 drop/repos 序列；内部用带 drop 节点和 reposition 节点的扩展基数树做正确复用，用 drop 感知的淘汰策略提前释放无人需要的缓存，用 segment-batch attention 在一次 prefill 内恢复缺失状态（只对注意力分段，FFN 整批算）。
- **策略**：主例是「工具结果滚动丢弃」，保留全部推理和最近 12 条工具结果的 KV；另外用递归自我改进（RSI）搜索缓存策略。

## 实验设置与主要结果
- 模型：MiniMax-M2.7、GPT-OSS-120B、MiroThinker-1.7-Mini；基准：BrowseComp-Plus、xbench-DeepSearch-2510、GAIA 纯文本 103 题验证集、SWE-bench Verified。
- 基线：Standard（模型相关的高阈值总结，96K 或 192K）与 Text Engineering（48K 阈值总结）。
- 与 Standard（高阈值触发总结）相比（Table 1），平均分提升 1.7 分、平均成本降低 27.7%（对 Text Engineering 降 21.9%）；作者把 repos 的 token 按缓存命中价计费，有意高估成本。
- 服务效率（8×A800，4 卡 prefill + 4 卡 decode）：各自峰值吞吐设置下，平均和 P95 请求延迟分别加速 1.36× 和 1.51×，输入/输出吞吐为 Standard 的 1.53× 和 1.18×；高并发下优势扩大，加速主要来自注意力时间减少。
- 在 SWE-bench Verified 前 100 题的在线评测中，AKV 用最少 GPU 时间达到最高最终通过率。
- RSI 搜索出的缓存策略比专家设计的 rolling-drop 再降本 7.1%（相对 Standard 降幅更大，约 15.6%/17.8%）。

## 局限与风险
- 作者列出的局限：更多缓存策略的探索、在该机制下训练智能体、支持线性注意力模型都还未做。
- drop 后保留的 KV 仍「间接带有」被丢弃内容的信息，这对可解释性和隐私删除（例如要求真正遗忘某段工具输出）是新问题。
- 依赖自建服务引擎，闭源 API 无法直接使用；成本按特定厂商价格计算，换价格体系结论可能变化。

## 工程落地启示
- 自建推理服务做长程智能体时，「滚动丢弃旧工具输出的 KV」是低风险高收益的默认策略，优于阈值触发的一次性总结。
- 如果你在调 Claude Code / Codex 一类 harness 的上下文压缩，本文给出了量化依据：越早、越细粒度地丢弃越好，前提是服务端能避免重新 prefill。
- 把缓存策略做成可编程接口后，可以让智能体自己搜索策略（RSI），这是「智能体优化自身运行时」的一个具体落点。

## 与相关工作的关系
与上下文工程（总结、裁剪）互补；与 StreamingLLM、H2O 等基于位置或注意力分数的 KV 淘汰不同，这里由智能体和 harness 按消息角色做高层决策；在系统层面扩展了 SGLang 的 RadixAttention 前缀缓存，使其支持依赖操作历史的缓存复用。
