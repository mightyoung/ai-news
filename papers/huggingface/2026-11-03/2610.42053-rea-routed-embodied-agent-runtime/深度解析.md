## 1. 一句话先懂它

让机器人「慢思考的大模型」和「快反应的动作程序」配合干活时，别让机器人停下来等大模型想完：事先测好每个动作程序在每类任务上的成功率，开跑时直接查表派活；只在一个程序跑完时，才请大模型看一眼前后两张图，判断活干完没有、要不要换个程序再试。

## 2. 值不值得读：五个 C 速览

**类型**：系统原型加一套统一评测协议。**上下文**：接着「代码即策略」（Code as Policies、ASPIRE，让大模型写机器人控制程序）和「双系统机器人」（GR00T N1、Helix，慢模型配快动作头）两条线，路由思路借自作者自己的 Agent-as-a-Router。**关键假设**：策略库里已经有几个能干活的候选程序，而且开发集上测出的成功率能代表测试集；在 LIBERO-Pro 仿真上看起来成立。**贡献**：①三层运行时，大模型、路由器、快策略接口统一；②路由表 + 边界触发的判定门 + 共享预算的升级梯子；③在同一批回合上对齐比较十几种方法。**清晰度**：主文密度很高，关键口径（哪组实验、几回合、是否同机）散在表注和附录 A–C。**建议**：看到第 5 节；做 Agent 编排的人值得读原文第 3 节和第 4.3–4.5 节。

## 3. 它在解决什么麻烦

现在让大模型参与机器人控制，大致两种接法。一种是大模型当主控，每一步都去调快策略，结果快策略总在等：论文里一个「每 8 段问一次」的阻塞式顾问（路由器必须等它回话才能继续），平均每回合让机器人干等 2.62 秒，占控制时间的 20%（第 9 页、表 4 第 19 页）。另一种是快策略当主控，出错才叫大模型，但大部分失败是「静默失败」（程序正常返回、没报错，活其实没干成）：一个靠异常触发的路由器在 590 个回合里只升级了 6 次，而失败的有 166 个（第 3 页）。

你在自己的 Agent 系统里也会撞上同样的问题：工具调用链里每步都同步问大模型，延迟和费用暴涨；只靠异常重试，又抓不住「返回成功但结果不对」的情况，还可能把已经做好的结果重跑坏。

如果 REA 这套做法成立，带来的不同是：大模型的贵算力挪到「事前写程序、事后验收」两头，执行过程不被打断；而且不同来源的策略（模型写的代码、学出来的 VLA，即视觉-语言-动作模型，看图听指令直接输出动作的模型）能在同一个运行时里按同一口径比较。

## 4. 他们怎么做的

核心思路：大模型擅长判断和写程序，不擅长连续控制。作者测过让视觉大模型直接逐步输出动作，1,987 个回合只成功 1 个，换成笛卡尔小步控制是 600 个回合 0 成功（第 3 页、附录 C.4 第 28–29 页）。所以干脆不让大模型进控制回路，只在回路外面做三件事。

系统分三层。System 0 是快策略：任何能从当前状态开始跑、跑完返回「用了多少步和秒、有没有异常、是否被截断」的控制器都行；在 LIBERO-Pro 上是编程 Agent 事先写好、冻结的 Python 程序，在沙箱里调用分割、抓取规划、逆运动学（由目标位置反推关节角度）等工具（第 6 页）。System 2 是大脑：离线为每个任务生成候选程序；在线只提供「判定」（输入开局帧、当前帧和指令，输出 done 或 not_done）和「建议」两种服务。System 1 是路由器，它自己不发任何动作，只管控制流。

路由器有三个部件。一是**路由表**（route memory）：正式评测前，每个候选程序在与测试种子不重叠的开发回合上各跑一遍，记下成功率和平均步数；测试时直接取成功率最高的，平手取步数少的，派活就是一次查表（第 7 页）。二是**边界触发的判定门**：每当一个程序跑完返回，就调用一次视觉判定；说 done 就结束，保护已完成的结果，说 not_done 就升级。三是**共享预算的升级梯子**：按路由表顺序排成「第一名、其他、第一名」，每次升级都从当前状态接着跑，所有运行和判定都从同一份步数与时间预算里扣，所以整个回合不会超过单个策略的预算（第 7 页、算法 1 第 22 页）。

实验里有三个变体：REA-M 只用路由表加异常门，完全不在线调用大模型；REA-A 让大模型在开局选程序；REA-V 用路由表加视觉判定门（第 5 页）。在 RoboTwin 上，路由表换成一个学出来的选择器：用 Qwen3.5-4B 加 LoRA（只训练少量附加参数的微调方式）读开局指令、图像和机器人状态，给每个候选策略打成功概率分，选最高的跑到底（第 7 页、附录 C.1 第 26 页）。

判定门的阈值和提示词在 216 条开发标注上定死后才开始测试（第 8 页、附录 B.5 第 25 页）。代码未公开，沙箱、各后端的适配层怎么写，论文未说明到可复现的程度。

**如果让你复现**（以 LIBERO-Pro 上的 REA-V 为例）：

```python
table = fit_route_memory(candidates, dev_seeds)  # 开发种子上测成功率和步数，排序
ladder = table.ladder(task)                      # [第一名, 其他, 第一名]
env.reset(seed); f0 = env.render(); budget = Budget(H=4000, W=900)
for k in range(K + 1):
    ret = run(ladder[min(k, len(ladder) - 1)], budget)  # 快策略跑到返回，扣预算
    verdict = judge(f0, env.render(), instruction, budget)  # 只在边界看前后两帧
    if verdict == "done" or budget.exhausted(): break
return env.score()                                # 成功判定只在最后读一次
```

## 5. 证据怎么看、别被什么忽悠

**表 1（第 8 页）：路由是否胜过每个单独方法。** 想证明收益来自路由而不是池子更大。设置是 LIBERO-Pro 全集 60 个任务 × 50 个测试种子 = 3,000 回合，仿真，所有方法用同样的初始状态、4,000 步和 900 秒预算。单独方法里最好的是 Agents SDK + GPT-6，94.7%；REA-M 95.9%，配对检验 86:51、p=0.004，95% 区间 [+0.4, +1.9]%（第 9 页）；事后挑最优的上限是 96.9%。在 37 个程序文件完全一致的任务上是 95.3% vs 93.7%（p=0.001）。每次成功所需步数 1,003 vs 1,343，这就是摘要里的「控制步数 −25%」。说明：提升是真的、统计上站得住，但只有 1.2 个百分点，离上限也只差 1 个点。

**图 4 与表 4（第 6、19 页）：查表能不能省掉等待。** 同一台主机、同一个 179 个程序的库，各 3,000 回合。阻塞式顾问控制时间每回合 13.33 秒，Agents SDK 程序 12.04 秒，REA-M 9.96 秒；对阻塞式顾问是 −25%，对 Agents SDK 是 −17%（区间 [−23, −11]%，第 10 页）。注意「时间 −17%」和「步数 −25%」口径不同，摘要把它们并列，很容易读成同一件事。

**表 7 与图 5（第 21、9 页）：判定门到底帮多少。** 在 ASPIRE 的 Fix 程序上（种子 1–10，590 回合），单程序 66.3%，加路由表 71.9%，再加视觉判定门 74.9%，判定门净增 3.1 个百分点（37:19，p=0.022），代价是每次成功的耗时变成 2.1 倍（第 10 页）。专挑难例的 72 回合子集上全路由器做到 48/72，但作者自己说那是压力测试，+3.1% 才是该预期的数（第 11 页）。判定器本身很吵：最终判定的准确率只比「永远说 done」略高甚至更低（0.72 vs 0.67、0.67 vs 0.75），帮得上忙是因为它说 done 时比较准（0.83、0.905）（第 11 页）。

**水分检查。** 主实验全在仿真；误差用配对精确检验和 Wilson 区间（二项比例的置信区间），这点比多数论文扎实。但 RoboTwin 的表 2（第 11 页）只有 100 回合，84/86 vs 80 只差 4–6 个回合，基线是不同时段跑的历史结果，MEDex 在另一台主机，且这 100 个场景早先用于 REA 的开发（附录 C.1 第 26 页）。200 场景的 RoboTwin 实验里，同一配置隔一晚重跑成功数差了 36 个（第 12 页），说明跨时段比较噪声很大。BEHAVIOR-1K 27/50 vs 25/50 作者自己说不显著；真机 Unitree G1 推椅子 8/10，由现场操作员判定，每个方法只有 10 次（第 12 页）。另一种同样合理的解释：收益主要来自「池子里本来就有互补的程序」，路由只是把它挑出来，所以策略库质量决定上限（作者第 13 页也承认方法间成功率差 20–47%，大脑定上限）。

## 6. 可信度与核验限定

**主张对照。** ①「在 LIBERO-Pro 上胜过池中每个单独方法」：表 1 第 8 页，配对检验支持，证据够。②「控制步数 −25%、控制时间 −17%」：数字都在，但口径不同，证据够、措辞要拆开。③「VLA 与代码策略可在同一运行时组合，84%/86% vs 80%」：表 2 第 11 页，样本小、跨时段，证据偏弱。④「迁移到 BEHAVIOR-1K 和真机」：只能算可行性演示。

**核验限定（原样合入核验报告）：**
- 95.9% vs 94.7%：LIBERO-Pro 60 任务×50 种子=3,000 回合，仿真，最强单一基线 Agents SDK + GPT-6，配对 p=0.004（表 1 p8；p9）
- 「控制步数 −25%」指每次成功所需步数 1,003 vs 1,343；「控制时间 −17%」来自种子 1–10 的单独实验（每方法 600 回合），CI [−23, −11]%（p9–p10）
- RoboTwin 2.0：100 回合中 84 / 86 vs MEDex 80，历史基线与 VLA 扩展不同时段运行、MEDex 用另一台主机，未报告显著性（表 2 p11）
- BEHAVIOR-1K 27/50 vs 25/50 作者注明不显著，Unitree G1 真机 8/10（p3–p4）；未见代码链接；论文 CC BY-NC-SA 4.0

**本例程读全文时的复核意见**：第二条里「−17% 来自种子 1–10 的单独实验（每方法 600 回合）」与我读到的不一致。−2.08 秒（−17%）正好等于表 4（第 19 页）的 12.04 − 9.96 秒，而表 4 和图 4 题注（第 6 页）都写明是同一主机、每方法 3,000 回合；种子 1–10、600 回合的是图 6 那组实验。建议核验流程复查这一条，在复查前对外引用 −17% 时写成「对 Agents SDK + GPT-6 的控制时间，非步数」。

**打折提醒**：对外别说「大幅超越」，只说「比最强单一方法高 1.2 个百分点，统计显著」；RoboTwin 和真机数字不要当成方法优劣的证据引用。

## 7. 你可以怎么落地

**今天就能试**：把「路由表 + 边界判定 + 共享预算」搬进你手上的 Agent 或自动化流程。最小步骤：从历史日志里按任务类型统计每种模型、提示词或工具链的成功率和耗时，做成一张表，开跑时查表选第一名；每个子任务跑完再用一个便宜模型对比「开始前 / 现在」做一次 done 判定，不通过就换表里第二名从当前状态接着跑，所有重试共用一个总超时。验收：留出 50–100 个没进表的任务，和「永远用单一最好配置」逐条配对比较，看成功率是否不降、平均耗时是否下降；同时统计判定器说 done 时的准确率，低于约 0.8 就先别开判定门。

**要有数据或机器再试**：装 LIBERO-Pro（MuJoCo/robosuite 仿真）和几个开源 VLA，给每个任务准备 2–3 个候选策略，先只做路由表（REA-M），用开发种子建表、测试种子评估。需要一张能跑仿真和 VLA 推理的 GPU，大约一两周；第一阶段只看路由表能否超过单一最好策略，第二阶段再加视觉判定门，并记录每次成功的耗时是否翻倍。

**暂时别碰**：让大模型直接逐步输出机器人动作（论文里 0/600）；把视觉判定器的结论当成成功标准（它本身准确率不高，论文只把它当升级开关）；按 RoboTwin 或真机的几回合差距去选型。

## 8. 和你已有知识的挂钩

它很像一个网关的「灰度路由 + 健康检查 + 超时预算」：路由表就是按历史成功率做的静态负载均衡，判定门是请求返回后的结果校验，升级梯子是带总超时的重试链。和 FrugalGPT 这类大模型级联路由比，最大的区别是：被路由的对象是会改变物理世界状态的长时间程序，所以重试必须从当前状态接着跑，还要防止把已经做成的事重做坏。

## 9. 存疑与代价

**局限**：作者没写单独的局限一节。我读出来的：主结论只在仿真；路由表要求每个候选程序在每个任务上都先跑开发回合，任务一多建表成本线性上涨；判定门在强策略库上反而掉点（图 6 第 10 页、正文第 11 页，用场景描述做判定掉 1.3–2.2 个百分点）；学出来的选择器在 RoboTwin 上开局选定后不再切换。**复现条件**：代码、权重都未公开，只有项目页；策略程序由 GPT-6 等闭源模型生成，跑一遍 Codex + GPT-6 生成 60 个任务的程序就用了 8,900 万输入 token（第 3 页）。**成本**：建表本身不花 token，用了 1,790 个开发回合（第 9 页）。**出处**：arXiv 预印本，未同行评审；论文 CC BY-NC-SA 4.0，非商用。

三个论文没回答、但决定你要不要动手的问题：①任务分布一变（新物体、新场景），开发集上测的成功率还准吗，要多久重建一次表？②没有现成的多个候选程序时，生成候选的成本和路由的收益怎么算账？③判定器换成更便宜或更贵的模型，+3.1% 的净收益会怎么变？
