## 1. 一句话先懂它

AI 智能体读网页、PDF、代码仓库时，往往把整个文件一股脑塞进上下文，而真正用得上的只有几段。这篇在智能体和文件之间加了一层「阅读管家」：智能体说清这一步要找什么，管家只递回相关片段并记下哪些已经找到、哪些还缺；读零碎片段不划算时，就退回读全文，而且保证总阅读量最多是全文的两倍。不改模型，就能省下大量 token 和时间。做 Agent 工程、在意 API 账单的人值得看。

## 2. 值不值得读：五个 C 速览

**类型**：系统原型（Agent 中间件）加测量分析。**上下文**：接着「给 Agent 的上下文减负」这条线：ACON 压缩观察和历史、观察遮蔽（只保留最近十条工具返回）、SWE-Pruner 按任务剪工具输出；也借了 ReadAgent「像人一样先看要点再查细节」的想法和经典的「租雪板问题」（ski rental：不知道要用多久时，先租、累计花费到一定程度再买）。**关键假设**：①大多数任务真正需要的证据只占原文很小一部分；②智能体能把「这一步要找什么」说清楚；③用于选读取方式的可靠性校准能迁移到真实任务。第一条有第 2 页的测量支持（长文档问答里证据中位数只占 3.17%），后两条在作者测的模型上看来成立。**贡献**：①Read Intent 协议：把「读整个文件」变成带意图、记覆盖的多次小读取；②可插拔的 Reader 后端：文本、PDF、表格、JSON、多文件各有专门的定位方式；③带预算的读取闸门（Budgeted Read Gate），证明单个文件的总暴露量不超过全文的两倍。**清晰度**：设计讲得清楚，Algorithm 1（第 5 页）可以直接照着写；但主实验重复次数没写，代码没放。建议**看到第 5 节**；做 Agent 框架的人值得自己读原文第 4 节和 Figure 4、Figure 8。

## 3. 它在解决什么麻烦

现在的 Agent 读外部内容，大多是「对象粒度」：调用一次读文件工具，整个文件进上下文；抓一个网页，整页进上下文。论文引用的前人统计说，Agent 轨迹里 60–80% 的 token 来自外部观察（第 1 页）。更糟的是，早先读进来的内容会在后面每一次模型调用里被重复携带，越往后越贵。作者把这叫「过度阅读」（over-reading）。

过度阅读不只是贵。第 2–3 页的成对实验显示，在证据很稀疏的任务上，不加控制的智能体最多多花 17.3 倍 token，分数却不更高；多余内容还会稀释关键证据，引出错误的工具调用、混淆出处、该停不停。

你在工程里会这样撞上它：让编程 Agent 审一个几十个文件的仓库，它把每个文件读全，十几轮后上下文爆了；让研究 Agent 读年报，它把两百页 PDF 全塞进去，只为找一个数字；做客服 Agent，一次查询把整份 JSON 日志读回来。已有的办法各管一段：RAG 只负责「找」；压缩方法在内容进来之后再删；KV 缓存压缩（把模型存的中间结果压小）只降显存，不决定该看什么。缺的是一个在「进上下文之前」就把关的统一层。如果它管用，同一个 Agent 框架、同一个模型，账单和延迟能直接打折，而且不用改模型。

## 4. 他们怎么做的

**核心思路**：像人读资料那样，先想清楚要找什么，看结构，聚焦相关段落，缺什么再补；同时设一条止损线，零碎读取的累计量一旦要超过全文，就直接给全文。这样最坏也只多读一倍，最好能少读九成。

**部件一：读取意图协议（Read Intent Protocol，第 4 页）。** 输入：智能体每次读取时给出一个结构化的「这一步需要什么证据」，加上从用户开场请求得出的会话意图（只用来补全细节，不覆盖新的子目标）。输出：一个 EvidencePack，包含带出处锚点的证据片段、处理了多大范围、暴露了多少字符、每个证据槽位「已找到 / 仍缺」。它只记录覆盖情况，不替智能体判断够不够，答还是继续读由智能体决定。智能体只用五个固定动作：scout（预览）、focus、collect、refine、verify。文件内容一变（SHA-256 指纹变化），之前记的证据全部作废。

**部件二：自适应读取后端（Adaptive Reader Backends，第 4–6 页）。** 每种 Reader 注册自己能处理的文件类型、支持的动作和成本。文本和 PDF 可用词法匹配、BM25（经典关键词打分检索）窗口或混合检索定位；表格可以只看某几列，也能扫全表算出一个求和，只把结果、行数和出处交给模型；JSON 和日志按键路径取值。选哪种配置：在可靠性达标的候选里挑估计成本最低的。可靠性用事先人工设计的校准请求估算，取 95% Wilson 区间下界（一种对小样本更保守的比例估计），阈值 0.6；校准请求不足 20 条的组不做自适应（附录 D，第 12 页）。

**部件三：带预算的读取闸门（Budgeted Read Gate，第 5 页）。** 设全文（或无损紧凑版全文）长度为 L 个字符。规则三条：必须看全文或没有合适 Reader 时直接给全文；小文件直接走原生读取；否则先稀疏读，每批交付前检查「已交付 + 这一批」是否超过 L，超了就扣下这一批、改给全文，并把之前的零碎片段从后续提示里撤掉。于是单个文件一次阅读的总暴露量不超过 2L（命题 4.1，证明在附录 A 第 10 页）。注意这个上界按字符计、不加权，不是对账单 token 或延迟的保证。

**接入方式**（第 5 页）：核心是一个共享运行时；NanoBot 直接注册工具，OpenCode、OpenClaw 用薄适配器暴露 `sro_preview`、`sro_read` 等工具，再配一份 SKILL.md 告诉模型何时先预览、何时定点读、何时回到原生读取。预算和意图校验在核心里强制执行，不依赖模型听话。

**如果让你复现**（以单个文件为例），最小骨架是：

```python
def read(obj, intent, ep):                       # ep：本文件本次阅读的状态
    if needs_full_view(intent) or small(obj): return full_view(obj)      # 小文件或必须看全文
    if vague(intent): return preview(obj)        # 意图不清先给目录或预览
    r = pick_reader(obj, intent)                 # 可靠性≥阈值里挑成本最低的
    batch = r.locate(obj, intent)                # 返回带出处锚点的片段
    if batch is None or ep.E + size(batch) > ep.L: return fallback_full(obj, ep)  # 超预算就给全文
    ep.E += size(batch); ep.record(batch, coverage(batch, intent))
    return EvidencePack(batch, ep.coverage, size(batch))   # 由智能体决定答、补读还是核对
```

Reader 的成本估计具体怎么算、跨多个文件的会话总预算怎么管，论文只给到组级别，后者未说明。

## 5. 证据怎么看、别被什么忽悠

**图一：Figure 6（第 6 页）与第 7 页 6.2 节，六个模型 × 五个场景。** 想证明：换模型、换场景都能省，而且不掉分。怎么测：在 NanoBot 框架上，六个模型（Qwen3.6-Plus、DeepSeek-V4-Flash、DeepSeek-V4-Pro、GLM-5.1、Kimi-K2.5、Claude Opus 5）跑五个场景：长文档阅读、多文件审计诊断、结构化数据分析、网页深度搜索、AI for Science（按 LAMMPS 分子模拟库写脚本），对照是原样不改的框架（Naive）。结果：token 降 15.7–92.9%，耗时降 23.0–89.0%。按核验限定：token 降 92.9%、耗时降 89.0% 是长上下文任务里的最好情形；30 个设置的中位数是 token 降 61.4%、耗时降 53.7%（p7）。分数「持平或更好」是 30 个设置中的 29 个，退步的是 GLM-5.1 的 AI for Science。网页深度搜索 token 降 31.0–43.0%、耗时降 23.0–37.0%，六个模型分数都涨 5–14 点，任务来自 FRAMES 和 BrowseComp-Plus（第 7 页）。说明：最强的 Opus 5 也省了 41.0–89.0% 的 token，强模型并不因为「会挑重点」就不需要它。

**图二：Figure 7（第 7 页），和检索、压缩比。** 想证明：比现成的「检索一次 / 迭代检索 / 压缩 / 遮蔽」更好。怎么测：三个场景 × 五个模型共 15 个设置，成本都端到端计，包括检索、重排序和压缩器自身的模型调用。结果：SparseRead 在全部 15 个设置里分数持平或更好，省 token 27.0–92.9%；但 token 最少只占 6 个设置、耗时最少占 9 个。一次性检索在 5 个网页设置里都更快，但 15 个里有 9 个分数低于 Naive；迭代检索 8 个掉分；ACON 5 个掉分、6 个反而更贵（第 7 页）。说明：SparseRead 的优势是「省而不掉分」，而不是在每一项上都最省。

**图三：Figure 8（第 8 页），三个部件的消融。** 意图：会话意图加单次意图一起用，每个任务重复读从 4.8 次降到 1.5 次，答不出因缺证据从 25% 降到 5%。定位方式：在 LooGLE 的 47 篇文档、741 个问题上，命中率词法 39.5%、BM25 60.1%、混合 65.3%，混合检索在几乎相同的暴露量下高 5.2 点；简单加大 BM25 窗口反而更差（56.7%）。闸门：交付后再检查会超出上界，到全文的 2.10–2.33 倍；交付前检查全部压在 1.62–1.93 倍（五个任务、各三次，DeepSeek-V4-Flash）。

**水分检查**：①主实验（Figure 6、7，Table 1）没写重复次数，也没有误差条；只有 Figure 8(c) 写了三次重复。②场景构成有调整：附录 C 写，原先的五场景矩阵里包含「原生读取就够」的对照任务，那时分数持平或更好的是 30 个中的 26 个；现在把这些对照挪出主矩阵、换成网页深度搜索，才得到 29/30（第 11 页）。③基线是作者自己配置的：RAG 用 512 token 分块、最多 8 块、4,096 token 预算（第 11 页），参数不同结论可能变。④有些分数涨幅大得反常，比如 NanoBot 上 Kimi-K2.5 分数 +0.598（Table 1，第 7 页），更像是原样框架在长文档上频繁失败，而不全是 SparseRead 的功劳，论文没解释。⑤强制稀疏读取在全局统计、规则编码类任务上 token 反而多 309%、210%（Figure 4c，第 3 页），全靠闸门判断兜底。⑥附录 C 的 Figure 9 题注写 DeepSeek-V4 Pro，正文写 DeepSeek-V4-Flash（第 11 页），有笔误。⑦BrowseComp-Plus 用的是固定语料，不是真实上网（第 11 页）。

## 6. 可信度与核验限定

**主张对照**：①「token 最多降 92.9%、耗时最多降 89.0%」：第 7 页有，但只是长上下文场景的最好值。②「97% 设置持平或更好」：Figure 6 与第 7 页支持，无重复次数。③「比检索、压缩更好」：Figure 7 支持「不掉分」，但不是每项都最省。④「可移植到三个框架」：Table 1（第 7 页）18 个设置全部省 token 和时间，15 个分数持平或更好；OpenClaw 上中位数只省 30.6%，明显低于另两个框架。

**核验限定**（原样合入核验报告）：
- 「97% 设置持平或更好」= 30 个设置（6 模型 × 5 场景，NanoBot 框架）中 29 个，退步的是 GLM-5.1 的 AI for Science（p7）
- token 降 92.9%、耗时降 89.0% 是长上下文任务里的最好情形；30 个设置的中位数是 token 降 61.4%、耗时降 53.7%（p7）
- 网页深度搜索 token 降 31.0–43.0%、耗时降 23.0–37.0%，任务来自 FRAMES 和 BrowseComp-Plus（p7）
- 这是 v2（2026-11-07 更新），归档与当前版本一致；PDF 里没找到代码链接，主实验重复次数未写；arXiv 默认许可（非 CC）

## 7. 你可以怎么落地

**今天就能试**：在你自己的 Agent 里加一层「读文件闸门」，不用等作者代码。规则照抄第 5 页：小于某个阈值（比如 8K 字符）的文件直接读全；大文件先返回目录或前几行预览，再按智能体给出的关键词返回带行号的片段；对每个文件累计已返回字符数，一旦下一批会超过全文长度，就直接给全文并停止零碎读取。同时在日志里加一个指标：每个任务里来自工具返回的 token 占比。验收：挑 20 个真实任务新旧各跑三次，看每任务总 token 和耗时的中位数，以及成功率；token 降、成功率不降才算有效。

**要有数据或机器再试**：想做到论文那样按文件类型自动选 Reader，需要一批人工设计的校准请求（每个「文件类型 × 大小档 × 意图类型」组至少 20 条，第 12 页），以及一个向量检索服务（论文基线用 BGE-M3 加 BGE-Reranker-v2-M3）。分阶段做：先只做文本和 PDF 的混合检索 Reader，在内部长文档问答上对比 BM25；再加表格 Reader 的「全表计算、只回结果」；最后再上自适应选择。不训练模型，主要成本是 API 调用和工程时间。

**暂时别碰**：别对所有读取强制走稀疏路径。全局统计、需要通读的规则类任务上，强制稀疏读取会让 token 多出 2–3 倍（Figure 4c，第 3 页）。也别把「省 92.9%」写进汇报或预算；论文没给重复次数和误差条，代码也没放，先在自己的任务上量出中位数再说。

## 8. 和你已有知识的挂钩

它像数据库的「谓词下推 + 投影」：不把整张表拉到应用层，而是在存储层先过滤、只取需要的列，必要时直接在存储层算好聚合再返回。闸门部分像熔断加止损：零碎读取的累计成本到了全文那么大就停，直接读全文。和 RAG 最大的区别：RAG 只管「找哪几段」；SparseRead 把找、暴露多少、记录覆盖、何时退回全文统一成一个协议，检索只是它可替换的一种后端。

## 9. 存疑与代价

**局限**：论文正文没有单独的局限性小节。作者在第 4–5 页承认，2L 上界只管单次阅读的未加权暴露量，不管账单 token、延迟和整个会话；回退时撤掉早先片段会破坏前缀缓存（重复前缀不用重算的机制）的复用。我读出的局限：主实验没写重复次数；分数提升有的大得反常，没解释；主矩阵场景有调整；AI for Science 只评脚本生成，不跑真实模拟验证（第 11 页）。**复现条件**：代码未公开；三个 Agent 框架（NanoBot、OpenCode、OpenClaw）是现成的；基准（LooGLE、QwenClawBench、SpreadsheetBench、FRAMES、BrowseComp-Plus、MDGYM）是公开的，但作者有改编。**成本**：不训练，主要是多出来的工具调用和校准请求的人工设计。**出处**：预印本，未同行评审；v2 版本与归档一致；单位按首页为中国科学院大学等三家。

**论文没回答、但决定你要不要动手的 3 个问题**：同一个任务跑多次，节省比例和分数的波动有多大？跨多个文件的整段会话总成本能不能也设上界？没有人工校准请求时，用默认 Reader 能拿到多少收益？
