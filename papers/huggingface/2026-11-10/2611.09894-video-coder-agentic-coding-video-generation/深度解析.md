## 1. 一句话先懂它

现在的视频生成模型常常数错物体、让东西凭空消失。这篇论文训练了一个会写 3D 建模代码的小模型：先根据文字在 Blender 里搭一个灰色的「白模动画」，确认物体数量、位置和运动都对，再交给现成的视频模型去上色和补细节。对你的启发是：难控制的生成任务，可以先让 Agent 写一份能执行、能检查的「草稿」，再交给生成模型。

## 2. 值不值得读：五个 C 速览

**类型**：新方法，附带数据集和训练环境。**上下文**：接着「用代码驱动视觉生成」这条线（GPT4Motion 用 Blender 脚本引导视频扩散，Video-CoCo 把代码当中间思考），以及多轮工具调用的 Agent 强化学习（Search-R1、ReTool）。和前作最大的不同是真的去训练模型，而不是给闭源大模型写提示词。**关键假设**：场景能用几何体加关键帧描述清楚；下游视频模型能接收草稿视频作为结构和运动的约束；用另一个视觉大模型给视频打分的奖励是可信的。前两条只在「物体、运动」类场景成立，作者自己也说材质类效果不好。**贡献**：一是 Video-Coder Harness（写代码、跑 Blender、回传错误和画面的交互环境）；二是 SFT 和 RL 两套数据；三是「执行奖励逐步退火、视频奖励逐步接管」的训练配方。**清晰度**：主体只有 9 页，思路清楚，但数字有几处前后不一致（见第 5、6 节）。建议**看到第 5 节**；如果你在做可控视频或 3D 内容生成，值得读原文附录 A 的系统提示词。

## 3. 它在解决什么麻烦

今天的文生视频模型（Sora、Kling、MiniMax 海螺这一类）画面很漂亮，但它们学的是像素层面的统计规律，并不真正理解三维世界。提示词里写「三个球从不同高度同时落下」「球滚下斜坡撞倒底部三块方块」，生成出来经常数量不对、方向不对、物体互相穿透或者突然消失（第 1 页）。而且结果没法精确修改，只能反复改提示词碰运气。

已有的补救办法是给视频模型加条件：深度图、运动轨迹、相机位姿，甚至物理仿真结果。但这些条件通常要人手提供，或者靠固定流水线拼出来（第 3 页）。也有工作让大模型写 Blender 代码，可大多是一次写完就用，不看运行结果，也不针对最终视频质量做优化。

你会在这些场景撞上它：做广告、教学或产品演示视频时，客户要求「三辆车并排驶过」「镜头从左侧环绕 90 度」，生成模型给出两辆车或镜头乱晃；做机器人或自动驾驶的合成数据时，需要精确控制物体数量和运动轨迹，纯生成模型不可靠。

如果这条路走通，「结构和运动」交给能执行、能复现的代码，「质感和外观」交给视频模型，两者分工。好处是可控、可查、可改：要改车的数量，改一行代码重渲染即可。

## 4. 他们怎么做的

**核心思路**：代码是精确、可执行、可组合的描述方式，一段短程序就能毫不含糊地规定物体、轨迹和镜头。让一个模型像程序员一样写、跑、改 Blender 脚本，渲染出只有灰色几何体的草稿视频，再让视频生成模型照着草稿出成片。

**Harness（训练和推理用的交互环境，第 5 页）**：输入是一段文字场景描述；模型在隔离沙箱里写 Python 脚本，可用两个工具：check_script 做快速静态检查，run_blender 实际执行并渲染。每次调用后返回三类反馈：执行报错（语法错误、缺相机、运行时异常）；内容检查（空帧、画面静止、物体出画）以及一段场景摘要；若干均匀抽取的渲染帧图片。所有场景用统一的灰色白模渲染设置，只保留结构和运动。提交时环境不直接相信结果，而是在干净目录里从头重跑一遍脚本，全部检查通过才算数（第 5 页）。

**数据（第 3–5 页）**：从公开视频数据集的描述里收集提示词，用大模型改写成写明物体数量、布局、运动和镜头的版本，并剔除依赖人脸表情、精细外观的提示词。用 Gemini 3.8 Flash 接入 harness 生成多轮写代码轨迹；把提示词加草稿视频送进 MiniMax-H3 合成「参考视频」；再按执行是否成功、草稿质量、提示词与草稿是否一致（由 Seed2.0 判断）三层过滤。

**训练（第 5–6 页）**：基座 Qwen3.5-9B。第一阶段 SFT（监督微调，照着老师模型的轨迹学）学会规划场景、写代码、调用工具、看反馈改代码；第二阶段用 GRPO（组相对策略优化：同一提示采 8 条轨迹，按组内相对得分决定奖惩）做多轮 Agent 强化学习。训练中视频生成器固定不动，只优化写代码的模型。

**奖励**：执行奖励是 0 或 1，工具格式全对、最终脚本跑通并通过所有检查才给 1；视频奖励由 Qwen3.8-omni-flash 对照文字、参考视频和生成视频，在物体、布局、运动、镜头四个维度打分，归一化到 0 到 1（第 6 页，提示词见 p15–16）。总奖励 = 0.5 × 视频奖励 + 退火系数 × 执行奖励，退火系数随训练步数按指数衰减。用流程话说：早期主要奖励「代码能跑」，后期主要奖励「视频对不对」，执行奖励的权重逐步变小但不归零。

**设置（第 6 页）**：8 张 H100 训练模型，另用 16 张 H100 部署 MiniMax-H3 生成 rollout 视频；组大小 8，最多 100 轮交互，上下文上限 120K；SFT 学习率 1×10⁻⁵，RL 学习率 1×10⁻⁶，batch 8；整个训练约 3 天。

**如果让你复现**，最小骨架是：

```python
policy = sft(load("Qwen3.5-9B"), sft_trajectories)          # 先模仿老师轨迹
for step in range(T):
    prompts = sample(rl_prompts)
    groups = [rollout_in_harness(policy, p, n=8, max_turns=100) for p in prompts]
    for traj in flatten(groups):
        draft = rerun_clean(traj.final_script)               # 干净目录重跑才算
        r_exe = 1 if draft.ok else 0
        r_vid = vlm_judge(prompt, ref_video, video_gen(prompt, draft)) if draft.ok else 0
        traj.reward = 0.5 * r_vid + exp(-step / T) * r_exe   # 执行奖励逐步退火
    policy = grpo_update(policy, groups)
```

执行失败时视频奖励如何处理、SFT 训了几轮，论文未说明。

## 5. 证据怎么看、别被什么忽悠

**表一：Table 1（第 7 页），PhyGenBench。** 想证明：加了代码草稿以后，视频的物理常识更好。怎么测：PhyGenBench 按力学、光学、热学、材料四类出题，官方协议用 GPT-4o 当裁判打 0 到 1 分（第 6 页）。结果：单独 MiniMax-H3 平均 0.61，加 Video-Coder-9B 草稿后 0.67，四类都是表中最高（第 7 页）。摘要说「约 7 分」，表里实际约 6 分，作者在消融一节也写的是 6 分（第 8 页）。换成 OmniWeaving 当生成器，从 0.48 到 0.51；但正文把这称作「提升 16.28 个点」，这个数字和表里对不上（第 7 页）。

**表二：Table 2（第 7 页），VBench-2.0 物理维度。** 结果：平均 54.58% → 78.19%，力学 67.59% → 88.67%；材料维度 75.02% 仍落后 CogVideoX-1.5 的 83.19%，作者解释是白模只编码结构和运动、不管质感（第 8 页）。说明：提升主要来自「运动对不对」，这正是代码最擅长描述的部分。

**表三：Table 3（第 9 页），消融。** 只做 SFT 是 0.63；RL 去掉退火 0.65，只用执行奖励 0.64，只用视频奖励 0.63；完整版 0.67。说明两种奖励和退火都有贡献，但每项差别只有 0.02 到 0.04。

**水分检查**：①没有误差条，也没说跑了几次，0.02 量级的差距可能落在噪声里。②自家生成器优势：RL 训练时的视频生成器就是 MiniMax-H3，参考视频也是 MiniMax-H3 生成的，评测的大提升也是在 MiniMax-H3 上；换生成器只测了 OmniWeaving 一个，而且只在 PhyGenBench 上。③裁判都是大模型：训练奖励用 Qwen3.8-omni-flash，评测用 GPT-4o（PhyGenBench），存在「学会讨好裁判」的风险。④基线数字大多像是从各自论文或榜单抄来的，作者没说明是否统一重跑；表 1 里 Video-CoCo 和 LTX-Video-2B 两行五个数字完全相同，疑似录入错误（第 7 页）。⑤前后不一致：数据集在摘要和方法里叫 SFT-6k、RL-2k（第 1、4–5 页），在训练细节和结论里却写成 SFT-10k、RL-4k（第 6、9 页）。⑥适用范围：提示词在构建时已剔除了依赖人脸和精细外观的内容，评测题偏重刚体运动，换到人物表演类视频不一定成立。

## 6. 可信度与核验限定

**主张对照**：①「明显提升 MiniMax-H3 的物理一致性」：Table 1–2 支持，方向清楚，但只有单次结果、无误差条。②「对不同生成器都有效」：只在 OmniWeaving 上测了一次，涨幅 0.03，正文的「16.28 个点」对不上，证据不够。③「两种奖励互补、退火有用」：Table 3 支持，差距小。④「完全开源」：核验报告确认模型、数据、代码公开，但 GitHub 仓库没有许可文件。

**核验限定**（原样合入核验报告）：
- 提升是「Video-Coder-9B 生成草稿 + Minimax-H3」对比单独 Minimax-H3：VBench-2.0 54.58%→78.19%，PhyGenBench 0.61→0.67（摘要称约 7 分，表中约 6 分）（Table 1–2 p7）
- RL 训练时使用的视频生成器就是 Minimax-H3（p6），在其他生成器上的增益需看论文其余对比

**打折提醒**：对外引用写「PhyGenBench 从 0.61 到 0.67」，不要用摘要的「约 7 分」；不要引用 OmniWeaving 的「16.28 个点」；数据规模写清是 6k/2k 还是 10k/4k 论文自相矛盾。

## 7. 你可以怎么落地

**今天就能试**：不需要 GPU。在本机装好 Blender，把论文附录 A（第 12–14 页）的系统提示词交给你手头的写代码 Agent（Claude、GPT 之类），挑 5 条「数量 + 运动 + 镜头」的提示词，让它写脚本、用无界面模式渲染灰色草稿。同时把论文里「提交后在干净目录从头重跑一遍才算数」的做法搬进你自己的代码 Agent 验收流程。验收：人工看 5 条草稿里物体数量和运动方向对了几条；重跑验收能拦下多少「本地能跑、换环境就挂」的提交。

**要有数据或机器再试**：如果你有一张能跑 9B 模型推理的显卡（具体显存需求论文未说明），可以直接下载开源的 Video-Coder-9B，在你的场景提示词上和通用大模型比较草稿正确率。如果你能调用某个支持「参考视频 / 运动条件」输入的视频生成服务，再把草稿接进去，对比有无草稿时成片的数量和运动是否正确。完整复现 RL 要 8 张 H100 训练、另 16 张 H100 跑生成器、约 3 天（第 6 页），一般团队不现实；先做推理对比，再考虑在自己数据上做 SFT。

**暂时别碰**：不要把它当成「通用视频提质方案」去替换现有流水线。证据集中在 MiniMax-H3 加刚体运动类题目上，换生成器的证据只有一组，人物、材质、流体这类场景草稿帮不上忙，论文自己的材料维度就落后于基线。

## 8. 和你已有知识的挂钩

它很像动画行业的「预演（previs）」或建筑的「白模」：先用灰盒子把机位、走位、时间定死，再交给美术上材质。工程上又像「配置与执行分离」：结构写成可执行、可版本管理的脚本，渲染器只负责外观。和 GPT4Motion 这类前作最大的区别是：它不只是给闭源模型写提示词让它出一次代码，而是用多轮执行反馈加强化学习，专门把一个 9B 小模型训练成会自我修正的「场景程序员」。

## 9. 存疑与代价

**局限**：作者承认材料类现象依赖精细外观，白模帮不上（第 8 页）。我读出来的：训练和评测都强依赖 MiniMax-H3 和大模型裁判；数据规模、OmniWeaving 涨幅等数字前后不一致；没有误差条；推理链路变长（多轮写代码、每次渲染 20–120 秒，见附录 A 第 13 页），生成一个视频的总耗时和成本论文未说明。**复现条件**：模型权重、数据、代码均已公开，模型 Apache-2.0，代码仓库缺许可文件；但完整复现 RL 需要能部署 MiniMax-H3 的条件，普通用户能否拿到同等接口论文未说明。**成本**：训练 8+16 张 H100、约 3 天。**出处**：预印本，未经同行评审；文中引用了作者团队自己的多篇前作（如 AdaTooler-V、V-Retrver），视频奖励和评测裁判也都是第三方大模型。

**论文没回答、但决定你要不要动手的 3 个问题**：一条视频从提示词到成片端到端要多久、多少钱？草稿交给 MiniMax-H3 时具体用的是什么输入接口，外部用户能不能复现？换一个没参与训练的主流生成器（例如 Wan 系列），在 VBench-2.0 上还能涨多少？
