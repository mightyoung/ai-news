## 一句话总结
把 Claude Code、Codex 这类「harness（模型外面那层运行框架）」本身当成被测系统，用 95 个机制导向任务和执行轨迹证据，分开评「任务做没做成」和「harness 机制有没有可靠工作」，发现两者经常不一致。

## 研究问题与动机
现有智能体基准大多只看最终答案、测试或环境状态，衡量的是模型和 harness 的合力。任务成功可能掩盖上下文丢失、工具结果误导或生命周期违规，任务失败也可能发生在 harness 忠实执行的情况下。即使固定模型，只看结果也说不清是哪个 harness 行为造成差异。

## 核心方法
- **七个可靠性维度**：上下文、执行、治理、生命周期、可观测性、工具、验证（基于已有 harness 分类法）。
- **95 个专家级任务**：每个任务对应具体 harness 机制，配可执行或基于状态的真值；跨 harness 适配器保持任务目标与评分一致，同时保留各 harness 原生行为。
- **轨迹追踪（TT）**：把各家原生执行记录重建到统一的 Trace IR 并保留出处。
- **多源证据获取（MEA）**：结合轨迹、工作区产物和环境状态，为基于 LLM 的评审提供分项证据。
- **两层评估 + 失败归因（FA）**：分别打 Agent 层与 Harness 层分数，再用预定义机制链把失败的 harness 条款与 agent 条款联系起来。

## 实验设置与主要结果
- 4 个 harness（Claude Code、Codex、DeepSeek Harness、OpenClaw）× 9 个模型 × 95 个任务，共 3,420 次运行。
- 各 harness 在 Harness 层的宏平均通过率在 59.8% 到 72.0% 之间（p16）。这是 Harness 层指标，不是总分。
- 31.1%（1,065/3,420）的运行在至少一条 Harness 标准未过的情况下仍完成任务。
- Agent 层成功率 39.5%，但两层每一项都通过的只有 8.4%（286/3,420）；两个汇总指标上领先的 harness 不同。
- 同一模型下不同 harness 的宏平均差距最高 16.2 分；在 1,700 个两层各至少有一条标准未过的运行中，842 个带有被激活的机制链；另有 1,065 个运行 Agent 层全部通过，但至少一条 Harness 标准未过。

## 局限与风险
- 作者自述：任务集是定向构造的，机制覆盖不均（例如 Verification 维度只有 1 个任务）；每个「任务-模型-harness」格子是挑出的一次执行，部分是替换重跑的（p14），无法说明重复运行稳定性或对真实工作负载的泛化。
- 任务版本、运行设置、评分预算的差异限制了对单个 harness 设计的因果结论。
- 1,339 条标准里有 430 条由 deepseek-v4-flash 评判，论文没有给出与人工的一致性估计（p13、p28）。
- 归因依赖 LLM 评审和预定义机制链，机制链被激活不等于真正验证了失败传播（作者也强调需进一步证据审查）。

## 工程落地启示
- 选型或自研 agent 框架时，只看任务成功率不够，应把上下文管理、权限治理、工具结果呈现、验证步骤等机制单独做断言测试。
- 统一的执行轨迹格式（类似 Trace IR）是做跨框架比较和回归测试的基础设施。
- 「成功但违规」的 31.1% 提醒：生产环境里要有独立于结果的合规与可观测检查。

## 与相关工作的关系
与 Terminal-Bench、τ-bench 等结果导向基准互补；延续了 harness 分类法与 harness 配置影响研究；作者还提出可把它用于 harness 自进化和递归自我改进（RSI）的评估反馈环。
