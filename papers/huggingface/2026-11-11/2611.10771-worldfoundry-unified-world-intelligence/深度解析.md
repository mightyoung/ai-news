## 1. 一句话先懂它

现在做视频生成、3D 重建、可交互「世界模型」、机器人动作模型的团队，各有各的脚本、格式和评测，结果很难放在一起比。这篇一方面给「什么才算世界模型」下了一个能检查的定义，另一方面做了一个开源的统一运行和评测框架，把每次运行的配置、产物和分数都留档。你要横向试很多生成模型时，可以直接拿它当「统一调度台」。

## 2. 值不值得读：五个 C 速览

**类型**：系统原型加立场性定义，不是新模型，也没有新的跑分。**上下文**：定义部分接着强化学习里的世界模型（World Models、PlaNet、DreamerV3）这条线；基础设施部分对标 OpenWorldLib、NVIDIA Cosmos、Genie Envisioner，以及 VBench、WorldScore、WorldArena 这类评测套件（Table 1，p5）。**关键假设**：不同模态的模型可以共用一套「请求—结果—产物」的数据格式，同时保留各自原生的输入和评测方式。从设计上看说得通，但论文没有给量化证据证明「经过框架跑出来的结果和原生代码一致」。**贡献**：一是用「状态是否持续、干预是否留下痕迹、新观测是否修正状态」三条来区分普通生成模型和世界模型；二是开源框架，把运行和评测通过落盘的产物解耦；三是把「收录」「能跑」「评测可比」「完整复现」分成不同等级的说法分别记录。**清晰度**：概念写得清楚，工程接口在 4.3–4.5 节；实验部分只有定性截图。建议**只看到本节和第 4 节**；如果你正要搭多模型评测平台，值得自己读原文第 4 节并去看代码仓库。

## 3. 它在解决什么麻烦

假设你在公司里负责评估「哪个视频生成模型适合做机器人仿真数据」。常见做法是：每个模型克隆一份官方仓库，各自配环境（Python、CUDA 版本经常冲突），各自写推理脚本，输出格式五花八门，再拿 VBench 之类的套件打分。这样做有三个坑。第一，两个模型分数不同，你说不清是模型本身的差别，还是预处理、帧率、随机种子这些「外围管线」的差别（p10）。第二，「支持某个模型」这个说法很含糊：是写进了列表、能跑通一次，还是在官方评测配置下复现了论文分数？很多平台把这几件事混成一句「已支持」（p10）。第三，可交互世界模型和机器人策略需要连续多步交互，一次性脚本很难把动作历史和状态留下来。

论文还指出一个更根本的问题：画面好看不等于模型真的「懂世界」。一个可交互世界模型能在你回头时还原刚才的房间，但不一定记得你刚打开的门还开着（p19）。现有评测多数测的是画质和单步可控性，很少测「干预的后果有没有持续」和「新观测有没有修正内部状态」（p23）。

如果这套框架真的好用，带来的不同是：同一份配置可以从命令行、网页或 Python 发起，产物和分数落盘留档，别人拿到你的结果目录就能重新打分或审计，不用重装模型；对外说「我们的模型在某基准上多少分」时，也能明确标出这是诊断性结果、可比结果，还是完整复现。

## 4. 他们怎么做的

**核心思路**：先在功能层面统一，不强求架构统一。作者把世界模型拆成三个操作：状态推断（从历史观测估计环境当前的隐状态，即模型内部对「世界现在什么样」的表示）、前向模拟（预测状态在自身规律和外部动作下怎么变）、交互响应（对不同动作给出不同的后续画面或输出）（p7，式 1）。判断一个系统算不算「生成式世界模型」，关键在于闭环：动作必须在状态里留下痕迹并约束之后的预测，新的观测必须能修正状态（p4）。在此之上，他们排出一条能力阶梯：感知落地是地基，持续状态建模、动力学预测、闭环交互是主干，可控编辑是独立的侧枝（Figure 3，p8）。

**框架的五个部件**（Figure 1，p3）：

第一，表层接口：终端菜单（TUI）、命令行（CLI）、浏览器工作台（Workspace / Studio）、Python API 和 MCP（Model Context Protocol，让外部智能体调用工具的标准接口）。所有入口都翻译成同一种规范化请求，保证不论从哪发起，结果可比（p11）。

第二，统一推理与交互：每个模型对应一个清单文件（manifest，声明来源、任务、依赖、所需权重、硬件和已知阻塞项）。解析器先做「预检」，检查环境和资产是否齐全，再把输入编码成 GenerationRequest（含输入、控制信号、模型原生参数如随机种子和帧率、期望输出格式），交给 WorldModelRunner。Runner 内部分两层：Operator 负责输入校验、前后处理和格式转换，Pipeline 负责加载权重、放到 GPU、分布式执行。交互式模型可以让 Pipeline 常驻，连续动作不用每次重新加载（p13–p14）。

第三，产物契约：每个输出用 ArtifactRef 描述（用途、存储地址、格式、大小、内容哈希）。一次运行会落下 execution_plan.json、requests.jsonl、results.jsonl、sample_ledger.jsonl（逐样本、逐阶段的状态和失败）、artifacts.jsonl 和 run_manifest.json。失败的请求也留在记录里，不会被悄悄丢掉（p14）。

第四，评测与证据：指标只算分，基准还规定数据、覆盖率、评测器和汇总规则。结果写进 metrics/per_sample.jsonl、metrics/summary.json，最终汇总成 scorecard.json，标明这次结果属于「诊断」「基准可比」还是「完整复现」。缺依赖时明确记为跳过或失败，不偷偷换替代品（p14–p15）。

第五，模型与基准动物园：270 个模型条目、74 个基准、62 个指标条目（p1；附录 B–D）。

**如果让你复现**这套「运行与评测解耦」的思路（不依赖他们的代码），最小骨架是：

```python
entry = load_manifest(model_id)                    # 清单：依赖、权重、任务、阻塞项
blockers = preflight(entry, env)                   # 预检：缺什么先报出来，不分配 GPU
if blockers: record(run_dir, status="blocked", why=blockers); exit()
for req in build_requests(benchmark, entry):       # 每个样本一个请求，保留原生参数
    res = runner.run(req)                           # Operator 适配 + Pipeline 执行
    append_jsonl(run_dir/"results.jsonl", res)      # 成功失败都落盘，带产物哈希
scores = evaluate(run_dir, metrics)                # 只读产物目录打分，不重载模型
write_scorecard(run_dir, scores, level=classify(coverage, protocol_match))
```

论文没有说明各模型接入时需要写多少代码、清单字段的完整定义，以及「诊断 / 可比 / 复现」三级的具体判定阈值，这些要去代码仓库看。

## 5. 证据怎么看、别被什么忽悠

**表一：Table 1（第 5 页），和同类平台的功能对比。** 想证明：WorldFoundry 是唯一同时覆盖视频、3D/4D、交互世界模型、具身动作，并把就绪度和结果出处挂钩的平台。怎么测：作者按「有没有公开文档化的工作流」给每个平台打勾、打叉或标「专项支持」。结果：WorldFoundry 一行除「训练」一列为叉外全部打勾，是表里唯一在评测证据（Evidence）一列拿到勾的系统。说明：这是作者自己做的功能清单对比，不是跑分，勾和叉的判定标准写在表下注释里，但没有外部复核。

**图一：Figure 10（第 22 页），OpenVLA 在 LIBERO-10 上的闭环演示。** 想证明：框架能把具身策略接进仿真闭环里跑。怎么测：OpenVLA（开源的视觉-语言-动作模型，看图听指令直接输出机械臂动作）在 LIBERO-10（机器人操作仿真基准）上，每个任务只录一个回合。结果：「把书放进收纳盒」在 179 步内完成；「两个物体放进篮子」和「碗放进抽屉再关上」都跑到 520 步上限没完成。说明：这能证明管线走通了，也说明作者没有挑「全成功」的样例；但三个回合不构成任何成功率统计。

**表二：Table 2（第 16 页）和附录 B–C，覆盖范围。** 想证明：框架接入面广。结果：模型按五类划分，附录给出 64 个视频生成、109 个世界模型、34 个 3D/4D、53 个具身、10 个托管 API 条目（p29），基准分 23 个具身、33 个视频、18 个世界模型（p35）。附录写所有 270 个模型条目都标为「Runner verified」，所有 74 个基准都标为「Integrated & Verified」，但同时声明验证范围只限对应的执行路线、模型变体和配置（p29，p35）。

**水分检查**：①第 5 节开头说会验证「框架结果与原生实现在相同条件下一致」「不同入口配置一致」，并测延迟、显存开销和接入新模型的工作量（p16），但正文后面只有定性截图（Figure 7–10），没有给出任何一致性数值、延迟或显存数据，这是最大的缺口。②视频、世界模型、3D 部分的「分析」大量引用各模型自己论文的结论（例如 Wan2.2、LingBot-Video 的改进是「published results」），不是在框架里重新测出来的（p17–p19）。③实验在 128 张 A100/H100 上做，其他硬件未评估（p17）。④「Runner verified」只说明参考流程能跑通，不等于评测分数复现。⑤Table 1 的对比是功能自评。整体看，这篇的价值在设计思想和开源代码，不在实验数字。

## 6. 可信度与核验限定

**主张对照**：①「给出世界模型的可操作定义」：第 3 节（p7–p10），定义清楚、可检查，但属于立场，没有实验去证明这个划分比别的更好。②「统一推理与评测基础设施」：第 4 节和代码仓库，接口设计写得具体，可信；但「保留原生语义、结果与原生一致」缺量化证据。③「270 个模型、74 个基准、62 个指标」：摘要（p1）和附录 B–D，对得上；是收录数。④「每个模型 Runner 都端到端验证过」（p4，p29）：论文给的是状态标记，没有附运行日志或耗时表，外部无法从论文本身核对。

**核验限定**（原样合入核验报告）：
- 这是基础设施与框架论文，「目录 270 个模型、74 个基准」是收录数，不等于都已跑通评测，论文说就绪度与执行证据分开记录（p1）

**打折提醒**：对外引用时说「收录 270 个模型条目」，不要说「评测了 270 个模型」；不要说「框架结果与原生实现一致」，论文没给数据；Figure 10 只是三个单回合演示，不能当 OpenVLA 的成功率引用。

## 7. 你可以怎么落地

**今天就能试**：不用跑任何模型，借它的「证据分级」思路改造你自己的评测记录。拿你最近一次模型对比的表格，每一行加一列「证据等级」：诊断（自己随便跑的）/ 可比（用了官方数据和评测器，但覆盖不全或配置有差异）/ 复现（官方配置完整跑完），再加一列「失败样本数」。验收：如果表里有超过一半的行说不清是哪一级，或者失败样本从没记录过，说明你现在的对比结论站不稳，值得引入类似 sample_ledger 的逐样本记录。

**要有数据或机器再试**：如果你有一张能跑得动目标模型的 GPU（具体显存要求看该模型的清单，论文未汇总），先克隆代码仓库，挑一个已标「Runner verified」的小模型跑一次它的参考流程，检查结果目录里是否真的生成了 run_manifest.json、results.jsonl 和 scorecard.json；再用同一模型的官方仓库在相同种子下跑一次，对比输出是否一致。这一步就是在补论文缺失的一致性验证。显存和耗时论文未给，需要你自己记录。之后再考虑把团队常用的两三个模型接进去。

**暂时别碰**：不要直接把它产出的分数当排行榜对外发布，除非 scorecard 明确标为复现级；不要指望用它训练模型，作者明确说训练还没做（p22）；也不要在 B200 之类新卡上默认它能跑，作者说主要只在 A100、H100 上验证过（p23）。

## 8. 和你已有知识的挂钩

它很像机器学习领域的「CI 流水线加制品库」：manifest 像依赖声明文件，预检像构建前的环境检查，ArtifactRef 加内容哈希像制品仓库，scorecard 像测试报告里「通过 / 跳过 / 失败」的分级。和最接近的 OpenWorldLib 相比，最大的区别是它把「收录、能跑、可比、复现」拆成独立的证据状态并强制落盘，而不是只提供统一的调用接口。

## 9. 存疑与代价

**局限**：作者承认各条目成熟度不一，依赖外部权重、受许可限制的数据集、托管服务和仿真资产；优化手段（FlashAttention、量化等）的效果没有系统测过；没有训练功能（p22–p23）。读出来、作者没明说的：一致性和开销没有量化；定义部分是概念框架，没有配套的新评测来测「干预是否持续」，作者把它列为未来工作（p23）。**复现条件**：代码公开、Apache-2.0；框架不带模型权重，各模型的权重许可要逐个看（清单里有记录）；托管 API 类模型要自己的密钥。**成本**：论文实验用了 128 张 80GB 的 A100/H100（p17），单个模型的成本论文未说明。**出处**：预印本、技术报告，未同行评审；作者跨 NTU、Princeton、UCSD、Nvidia、Adobe 等（p28），首页只署 OpenEnvision。

**论文没回答、但决定你要不要动手的 3 个问题**：经过框架运行的结果和原生代码的结果差多少？接入一个新模型要写多少代码、花多长时间？「Runner verified」的验证记录能不能在仓库里逐条查到？
